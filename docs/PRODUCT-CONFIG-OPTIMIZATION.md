# 配置重构与编排画布 · 产研优化需求 v0.1

日期：2026-10-26。状态：**产品视角的取舍方案与两版校准计划（提案）**。本文对[运营视角配置需求清单](OPERATOR-CONFIG-REQUIREMENTS.md)（R-01…R-22）与领域专家需求（D-01…D-08）逐条裁决，重梳专家配置项，并把**编排画布**定为一等交付物。不改 [PRODUCT](PRODUCT.md) 定位、不改 [ROADMAP](ROADMAP.md) 阶段与退出 Gate、不删[六层合同](CONFIGURATION-LAYERS.md)。落地前以本文作为 R1/R2 的范围输入，由产品决策确认。

决策前提（本轮由产品负责人指定，本文按此执行）：**画布/编排图必须做**；**专家配置项必须按用户任务重梳**；**不得为满足诉求牺牲既有产品优势**。

## 0. 三个判断

1. **运营清单 22 条，我采纳 12、部分采纳 7、改判 3、不采纳 0；但改了 6 处的落点。** 改判全部集中在"会让证据链变薄"的地方——那是我们唯一守得住的东西，不能拿它换配置速度。
2. **画布必须做，但理由不是"竞品都有"。** 它的正当性是：**业务承诺的唯一可视化契约**。竞品的画布画"流程"，我们的画布要画"承诺 + 守卫 + 证据"。画布若只画框和箭头，就是纯成本。
3. **配置项的问题不是"太多"，是"按平台对象分组"。** 重梳的方向是**默认四个入口、全量十二个对象、每层都有证据入口**：用户看到四个，合同一个不少。

## 1. 四条不可让的边界（先立规，再谈需求）

| # | 不可让 | 为什么不能为体验让步 | 对需求的约束 |
|---|---|---|---|
| **U1** | 来源与授权不可默认 | `PRODUCT.md` §准入条件第 2 条：缺 `source_ref`、权利范围、有效期、撤回入口任一，资料不得进快照 | 三键审阅可以，但"整批来源声明"必须显式做一次，不能被默认值吃掉 |
| **U2** | 硬规则在模型外、发布需人工审批 | 这是与 ElevenLabs / Delight 的结构性差别：它们"有装置但不强制" | 编辑动作可合并，评测与审批不可合并 |
| **U3** | 整包版本冻结 + 结果留证 | 没有冻结就没有回放，没有结果 ID 就没有"可验收" | 任何"即时试跑"必须留 RunEvent 与草稿哈希，标"非发布版本" |
| **U4** | 六层合同在代码与详细视图中完整 | 六层是运行时与审计的骨架，删了就无法归因"哪一层错了" | 只从**导航**里删，不从**合同**里删 |

## 2. 领域专家需求（新增，之前未被登记）

这里的"领域专家"指**业务口径的所有者**：客服主管、课程顾问负责人、解决方案顾问。他们不配界面，他们签字。之前所有文档只写了运营，漏了这批人——而画布的正当性主要来自他们。

| # | 需求 | 现状缺口 | 优先级 |
|---|---|---|---|
| **D-01** | 我要用业务语言写"什么算答对"，不学评测术语 | 案例字段是"期望状态/必须做/禁止做"，偏工程 | P0 |
| **D-02** | 我要看见我这句规矩在什么情况下会被触发 | 只能读条件摘要，无"给我一个输入，走哪条路"的推演 | P0 |
| **D-03** | 我说"这条答错了"时，只改这一处，别动别的 | 现状是整段 Skill 文本重写 | P0 |
| **D-04** | 我要能证明改完没变差 | 有配对回放设计，但无"同一批问题前后对比"的一屏视图 | P0 |
| **D-05** | 我要能把我的业务规矩画出来，交给别人评审或交接 | **无**。这是画布存在的第一理由 | P0 |
| **D-06** | 价格/政策口径归我，工程不能替我定 | 事实与 FAQ 文本混在一起，改价要改多处 | P0 |
| **D-07** | 我要知道现在线上是哪一版、谁批的、什么时候生效 | 有版本列表，缺"当前生效 + 审批链"的一眼视图 | P1 |
| **D-08** | 新人要能在 1 小时内接手我的配置 | 11 个模块 + 每模块 1–2 段免责声明，读不进去 | P1 |

**D-05 是本轮最重要的需求**：它同时解释了"为什么要画布"和"画布该画什么"。业务方不是要看流程图，是要看**"我承诺了什么、在什么条件下不承诺、出了问题看哪里"**——这三件事正因为画布能画，才值得投入。

## 4. 专家配置项重梳

### 4.1 问题诊断

现状 11 个模块（`views/editor.js:7-18` 十项 + 运营指南第 11 项）的问题不是数量，是**分组维度错了**：按平台对象（ContextSnapshot / RequestRouting / Skill / HardRule / ToolPolicy / Outcome）切，运营每配一样东西都要先做一次"我这件事属于哪一层"的翻译。

### 4.2 新结构：四资产 + 一装配（默认 4 个入口，全量 12 个对象）

| 资产 | 对象 | 用户要回答的问题 | 业务字段 | 六层映射 | 证据入口 |
|---|---|---|---|---|---|
| **知识包** | 事实 | 什么会变，变了影响谁 | 名称、值、生效期、出处 | ContextSnapshot | 被引用处 + 变更史 |
| | 问答 | 客户这么问，我这么答 | 问题、答复、引用事实、适用范围 | ContextSnapshot + Skill | 出处 + 试跑 |
| | 口径 | 政策原文与我的解释 | 原文、解释、适用场景、例外 | ContextSnapshot | 原文定位（页/行） |
| **规则包** | 平台锁定 | 哪些我永远不能碰 | 12 条内置，只读 | HardRule | 规则 ID + 来源 |
| | 业务红线 | 什么时候必须停/转/确认 | 当[字段][算子][值]→[动作] | HardRule | 命中记录 |
| | 转人工 | 什么时候交人、交给谁 | 条件、队列、等待、恢复检查 | HardRule + Routing | 接管与释放记录 |
| **动作包** | 工具 | 能办成什么事 | 动作名、需要信息、写入/只读、超时 | ToolPolicy | 调用与结果 ID |
| | 结果 | 什么算办成 | 完成/失败/未知定义 + 证据要求 | Outcome | 结果列表 |
| **装配** | **编排** | 客户进来走哪条路 | **画布**：入口/判断/办理/说话/交接 | RequestRouting + Skill | 路径回放 |
| | 模型与预算 | 用哪个模型、花多少 | 连接、预算、降级档 | AgentVersion | 用量 |
| | 入口 | 从哪进来 | Widget / 联系页 / 渠道 | Release 绑定 | 入口状态 |
| | 版本 | 现在线上是哪版、谁批的 | 冻结、审批、回滚、迁移 | AgentVersion / Release | 证据抽屉 |

**四个默认入口**：问答（A2）、业务红线（B2）、工具（C1）、编排（D1）。其余八个在详细视图里，按需下探。

### 4.3 与现状的逐项对照

| 现状模块 | 去向 | 处理 |
|---|---|---|
| 接待与回答 | 装配 · 编排的"说话"节点 + 规则包 | 人设/语气进节点属性，不单独成模块 |
| 依据资料 | 知识包（三对象） | 拆开：事实/问答/口径 |
| 服务流程 | **装配 · 编排（画布）** | 升级为图，保留清单投影 |
| 业务字段 | 知识包 · 事实（结构字段）+ 动作包 · 工具入参 | 字段归属按"谁用"分，不再单独成模块 |
| 处理策略 | 编排的节点内容 + 知识包的适用范围 | Skill 文本退到节点说明，不再与流程并列 |
| 必须遵守的约束 | 规则包（锁定 / 业务红线 / 转人工） | **拆三类**，业务红线可编辑 |
| 业务动作 | 动作包（工具 + 结果） | 补结果定义，不再与"证据"分家 |
| 结果与验收 | 动作包 · 结果 + 验收域 | 配置期只定义"什么算完成"，验收证据留验收域 |
| 模型与预算 | 装配 · 模型与预算 | 不变 |
| 版本与变更依据 | **证据抽屉**（常驻，不占导航） | 见 §3.1 R-20 改判 |
| 任务与主动服务 | 移出主流程 | 独立入口，Gate 通过后再开 |

## 5. 编排画布

### 5.1 为什么必须做（三条理由，第三条才是决定性的）

1. **业务方要签字。** 一张能指给人看的图，比 11 个表单更能让客服主管说"对，就是这个意思"（D-05）。
2. **多单元之后，清单不可读。** 5 个场景还能列表，20 个分支加异常出口就必须有拓扑视图；这是 R3 以后的硬需求。
3. **三家竞品都有画布，但都没画对。** ElevenLabs 的 Workflow 画节点与边，Delight 的 Actionbook 画条件块——**没有一家在图上标"这里必须停下""这里要人确认""这一步承诺了什么结果"**。我们的画布如果画这三样，就不是跟随，是差异。

### 5.2 画布画什么：三个图层，缺一不可

| 图层 | 画什么 | 数据来源 | 为什么必须有 |
|---|---|---|---|
| **业务路径** | 入口 / 判断 / 办理 / 说话 / 交接 五类节点 + 边 | 编排对象 | 这是所有人都会画的 |
| **守卫层** | 边上挂红线（可点开看规则 ID、作用域、命中记录）；节点上挂确认点 | 规则包 | **模型外裁决在图上可见**，这是与竞品的分水岭 |
| **证据层** | 节点标注"承诺什么结果、需要什么 ID、失败/未知怎么记"；运行叠加按真实 RunEvent 给路径着色 | 动作包 + 运行 | 让图能回答"出问题看哪里"，而不是"流程长什么样" |

**运行叠加**是 V2 的关键能力：一条边如果从没被走过，说明条件写错了；一条边总是走到失败，说明动作或资料有问题。这让画布从"配置工具"变成"诊断工具"。

### 5.3 V1 画布范围（能做的五件事）

1. 建/删/连线：五类节点，禁止万能节点与代码节点。
2. 边上挂守卫：从规则包选已有红线，不能在现场新建自由文本规则。
3. 节点挂结果承诺：从动作包选结果定义。
4. 保存前九条校验（沿用 [ROUTE-GRAPH](ROUTE-GRAPH-AND-UNITS.md) v1.0 合同），错误定位到具体节点/边。
5. 清单投影同步：同一份数据两种看法，表格视图可批量编辑、可键盘操作、可无障碍访问。

### 5.4 V1 明确不做

嵌套（单元展开成子图）、端口跳步、边界事件、运行叠加、边级 diff、坐标持久化为业务事实、画布即执行（画布只是配置投影，执行仍走 `Unit` 合同）。

### 5.5 V2 画布

嵌套与面包屑、端口与边界事件、运行叠加（按真实流量着色）、边级 diff（版本对比）、导出评审图（给业务方签字的 PDF/图片）。

### 5.6 反模式（写进规范，防止做成 Dify）

- 万能节点 / 任意代码节点 / 画布内写提示词长文。
- 把画布当唯一编辑面（必须保留清单投影）。
- 坐标进入业务合同（只存视图偏好）。
- 用画布替代规则：图上挂的红线必须引用规则包里的既有规则，不能在图里现写。

### 5.7 画布的否决条件（我的保留意见，写进 Gate）

V1 出口时测一次：目标角色在画布上完成"加一条转人工分支"的**成功率 <80%**，或**耗时超过清单投影 2 倍**，则 V1 画布**降级为只读评审视图**（不删、不废），V2 再决定是否恢复编辑能力。

理由：画布必须做，但"必须做"不等于"必须好用"。用数据决定深度，是对这条指令最负责的执行方式。

## 6. 两版校准计划

两版的目的不是"做完功能"，是**用真实配置把优化点校准掉**，避免按错误结构写一万行。所以每版都有"校准问题"和"否决条件"。

### 6.1 V1 · 校准一：一条业务贯通

**校准问题**：新结构（四资产 + 装配）能否让一个非工程角色独立完成一套真实业务的装载、编排、试跑与发布？画布与清单双投影是否成立？

| WP | 内容 | 依赖 | 出口证据 |
|---|---|---|---|
| WP-01 | 四资产 + 装配的对象与字段落地（12 对象，含事实表） | — | 字段表 + 单测 |
| WP-02 | 批量摄入（文本层 PDF/DOCX/XLSX/CSV/MD/URL）+ 候选生成 | WP-01 | 5 份资料解析成功率 ≥90% |
| WP-03 | 三键审阅 + 整批来源声明（U1 约束） | WP-02 | 137 条 ≤30 分钟 |
| WP-04 | 规则包：平台锁定 / 业务红线（三格 + 闭集）/ 转人工 | WP-01 | 20 条红线零表达式 |
| WP-05 | 动作包：一个真工具（可回滚沙盒）+ 结果定义 + 结果核验 | WP-01 | 结果 ID + 未知态 |
| WP-06 | **画布 v1**（五类节点 / 守卫 / 结果承诺 / 九条校验 / 清单投影） | WP-04、WP-05 | 加一条转人工分支成功率 ≥80% |
| WP-07 | 证据抽屉（五问：从哪来、哪版、谁改、影响谁、凭什么） | WP-01 | 五问一屏可答 |
| WP-08 | 影响面 v0（受影响几处 + 哪几条案例） | WP-06 | 改一次价格 9 处全同步 |
| WP-09 | IA 收敛 4 + 1；环境条（由能力状态推导）；缺项业务语言（复用 Gate 校验） | WP-01 | 首次路径不出现"任务/触达/频次" |
| WP-10 | OAT-1 跑测与证据归档 | 全部 | 见 §7 |

**不做**：冲突检测全量、就地改、嵌套画布、运行叠加、Task、记忆、物料、多云、第二场景。

**V1 否决条件**：OAT-1 六项里任一项不过，且归因是"结构不对"（不是"没做完"），则停止 V2 开工，先修结构。

### 6.2 V2 · 校准二：两条业务 + 治理闭环

**校准问题**：同一套包能否被第二个业务复用？从"发现答错"到"改好上线"能否压缩到一个屏，同时不牺牲评测与审批？

| WP | 内容 | 依赖 | 出口证据 |
|---|---|---|---|
| WP-11 | 冲突与缺口检测 5 类全量 | V1 WP-01 | 注入 15 例检出 ≥4/5 类、误报 ≤10% |
| WP-12 | 撤回连锁影响 + 事实变更传播 | WP-11 | 撤回一条显示三处影响 |
| WP-13 | 就地改：提名/标注/候选合一屏；评测与审批保留（U2） | WP-07 | 发现→发布 ≤5 分钟 |
| WP-14 | 画布 v2：嵌套 / 端口 / 边界事件 / 运行叠加 / 边级 diff / 评审图导出 | V1 WP-06 | 20 单元可读；跑通边界事件 |
| WP-15 | 第二场景复用（复制 + 包引用） | V1 WP-01 | ≤30 分钟可试用 |
| WP-16 | 专家侧：业务语言案例、触发推演、前后对比一屏 | WP-13 | D-01/02/04 各一次实跑 |
| WP-17 | 历史会话聚类（只出问题簇，不出答案） | WP-02 | 200 条会话 → ≥20 簇 |
| WP-18 | OAT-2 跑测与证据归档 | 全部 | 见 §7 |

**V2 否决条件**：若"就地改"路径上出现任何一次"未经评测即发布"，该 WP 整体打回——这不是体验问题，是 U2 破了。

## 8. 我不做的事，与理由

| # | 不做 | 谁在要 | 为什么不做 |
|---|---|---|---|
| N-1 | 把六层合同从文档和代码里删掉 | 运营（"太难懂"） | 删掉就无法归因"哪一层错了"，那是唯一差异点。只从导航删 |
| N-2 | 编辑后一键发布、跳过评测 | 运营（"太慢"） | 这是 Delight / ElevenLabs 的做法，也是它们被我们指出的结构缺口 |
| N-3 | 自动生成业务答案入库 | 运营（"让我少写点"） | 无出处事实违反 U1；只能生成"候选 + 待补出处" |
| N-4 | 完成度百分比 / 健康分 / AI 评分 | 运营（"想有个数"） | 假精确。要的是"哪一处不对"，不是"78 分" |
| N-5 | 画布内自由写规则或提示词长文 | 领域专家（"想就地写"） | 规则必须在规则包里有 ID、有作用域、有命中记录，否则图不可审计 |
| N-6 | 跨专家共享策略库 | 部分领域专家（"想统一口径"） | 已否决方向；共享的是**包**，不是可变策略 |
| N-7 | 用画布替代清单投影 | 视觉偏好 | 键盘、无障碍、批量编辑都要靠清单；双投影是硬要求 |
| N-8 | 取消红线分"平台锁定/业务可配"中的锁定部分 | 运营（"为什么我不能改"） | 安全与合规底线不可由业务方改，这是产品承诺 |
