# 语音架构决策记录 v1.0

状态：决策记录，2026-10-21 起，2026-10-23 增补 D-05。记录五项已定判断及其理由；**不新增产品范围、不改六层配置、不改阶段 Gate 划分**（D-03 只向 S2-c 增加验收项，D-04 只指定首次验收阶段，D-05 只约束媒体传输）。指标的操作定义与测量方法在[实时语音协同验证计划](VOICE-COORDINATION-VALIDATION.md)「全双工交互指标与登记口径」，本文件不复制表格；对照分析见[Qwen-Audio-3.1-Realtime 架构对照](QWEN-AUDIO-3.1-REALTIME-ALIGNMENT.md)。

## 1. D-01 全双工决策落点：harness 工程式

**判定（2026-10-21）**：是否/何时/如何说话由工程链路承担——Pipecat 轮次策略 + 自建播出回执；模型保持可替换。模型内全双工（Qwen-Audio-3.1-Realtime、GPT-Realtime 类）列为**后续兼容方向**，登记观察点（接口形态、成本、与 harness 决策的替换关系），不作当前主选。

**备选与不选理由**：模型内方案把话轮决策交给实时模型原生决定，交互质量上限更高，但把话轮逻辑绑死在单一供应商，与"模型经 Adapter 可替换"的项目前提冲突；模型换代即重做集成，成本结构不可比。

**理由**：当前阶段与各家 LLM 的兼容契合度优先；模型内全双工是未来方向，项目后续需考虑兼容。工程式与既有纪律（只维护一条默认生产语音链路、模型经 Adapter 接入）完全相容，不动 Pipecat 主线地位。

**影响**：
1. Pipecat 主线新增两项必验职责：smart turn 行为、自建客户端级播出回执（[参考项目](REFERENCE-PROJECTS.md) P0-2 已核该项缺失）。
2. 全双工指标测的是 harness 自身行为，验收必要性上升而非下降。
3. 语音交互策略必须有可配置、可评测的落点，否则等于把本该由训练获得的能力裸奔——落点待 Q2 定。

**不变**：六层执行顺序不变；硬规则仍在模型外裁决；电话 S4 独立 Gate 与"不是网页语音的开关"不变。

**2026-10-21 补注（读源码后收紧表述，不改判定）**：参照实现把"全双工决策"做了分层——**语义断句委托给 provider 的可配置模式**（`smart_turn`，"configured by the runtime; no manual VAD tuning is exposed"），harness 自持话轮、打断、播报窗口与结果插入。因此 D-01 的准确表述是"话轮与播出时序在 harness，语义断点在 provider 的可配置模式"，而非"全部自己实现"。影响：D-02 的停止时延须拆成"harness 指令下发 → 客户端停止"与"provider 决定段"分别登记。见[源码研读 §5.1–5.2](QWEN-AUDIO-AGENT-HARNESS-STUDY.md)。

## 2. D-02 全双工指标进门禁：按业务语义拆解，不照搬 benchmark

**判定**：三个原始指标（打断响应率、背景人声误响应率、附和延迟）不以 benchmark 形态进门禁；拆成业务口径后进门禁，并区分**确定性判据**与**统计判据**。

**四条理由**：

1. **语义不可比**。三个指标来自模型 benchmark，测的是模型内决策质量；我们已定 harness 工程式，测的是系统行为（harness + 模型 + 网络 + 设备）。同名不同物。
2. **"打断响应率越高越好"在业务里是错的**。打断后的正确第一反应是闭嘴听，不是说话。门禁应为：必须停止播报（触发 100% + 停止时延 p95 上限）+ 不播过期内容（0 容忍），而非"响应率"。
3. **附和的真实风险是归属误判，不是延迟**。把附和当打断（乱停、反复确认）或把打断当附和（用户说停还在说）。门禁为"非预期中断 = 0"，并配对登记**误中断率与误忽略率**——只压一边，另一边必然顶上来。
4. **背景人声误响应保留 0 容忍，但必须成对报漏响应率**。VAD 收紧可以刷低单边指标，代价是把用户真话滤掉。

**阈值纪律**：不照抄厂商数字（84.5% / 13.0% / 1.700s 为不同管线、不同语料、厂商自报且未复现）；先跑 S1 现有最小链路取基线，再登记绝对上限（p95）与零容忍项，遵守"测试前登记、不根据结果倒填"。语料自建：中文、客服/销售场景、固定设备与网络矩阵，不用英文 benchmark 音频代替。

**归属**：模态层 Gate，与业务内容 `EvalSet` 分开裁决（确定性 vs 软质量分离），避免一条混合分数掩盖确定性违规。

**阶段**：S1 语音退出 Gate 用本口径补齐现有残留（真实音频可懂度、首响、打断恢复）→ S2-c 语音应用验收复用 → S4 外呼复用并另加通话回执项。

## 3. D-03 播报窗口与播出回执：打断不等于失败，交付以播出为证

**判定（2026-10-21）**：三件事一并进 S2-c 语音验收，分档如下。

| # | 机制 | 档 | 判据 |
|---|---|---|---|
| 1 | **播报窗口**：三个布尔条件同时为否才允许插话——① 用户是否在**对助手**说话；② 本轮是否已完成；③ 是否仍有音频待播 | P0 | 插入时机可判定、可埋点，不靠启发式 |
| 2 | **打断与重投分流**：被用户打断 → 视为已送达（`confirm`），不重播；其他原因取消 → 重投（`retry`）；只有播出确已开始才发 `interrupted` | P0 | "播了一半算不算送达"有确定判据 |
| 3 | **客户端播出回执**：服务端生成完成 ≠ 已送达，以客户端 `playback.started` 为准 | P0 网页语音侧 / S4 电话侧 | 无设备级回执不得声称已播报 |

### 3.1 关键修正：第一条件是"用户在**对着助手**说话"

按简单发声检测（VAD）判定"用户在说"，会让助手在电视声、咳嗽、同事闲聊时不断闭嘴，体验是"它总是莫名其妙停下来"，非常假。要求是：

- **噪音与旁人说话不打断播报**；只有当前用户对助手发话才算打断；
- 这要求把"有没有声音"升级为**归属判断**：谁在说（说话人），以及在对谁说（语义）。

因此分三级，且**不允许把上一级的缺口当作已满足**：

| 级 | 覆盖 | 依赖 | 状态 |
|---|---|---|---|
| **P0 · 声学级** | 短促杂音、环境噪音、键盘声不打断（连续帧迟滞 + 最短语音时长 + 能量门限） | 链路内即可实现 | 确定可做 |
| **P1 · 说话人级** | 旁人（另一自然人）**有内容的说话**不打断（同事交谈、家中对话） | 说话人归属：provider 侧提供，或设备侧声纹/阵列 | 能力依赖，S2-c 内验证 |
| **P2 · 语义级** | 当前用户本人在说话，但话**不是说给助手的**也不打断——例如忽然对快递员说"放门口就行" | 语义归属判定：呼语、指代、话轮连续性、上一轮是否在与助手对话 | 能力依赖，S2-c 内验证；验不出退回 P1，**不得宣称已满足** |

P2 的两条底线（防止"判错"变成"叫不停"）：

1. **语义判定只决定"是否打断播报"，不决定"是否记录用户话语"。** 被判为"不是说给助手"的内容仍保留转写、可追溯，下一轮仍可作用户上下文；不静默丢话。
2. **必须有一条不依赖语义的硬打断路径**：称呼词（"你好""助手"）、明确指令词（"停""等一下"）、连续发声超阈值，任一命中即停且保持停，不由语义回退。

### 3.2 连带影响：D-02 要加一条配对指标

原口径只压"背景人声误响应"（把别人当用户去响应），现在必须成对加**"背景人声导致的非预期停播"**（把别人当用户去抢话）。两条是一枚硬币的两面，只压一头另一头必然顶上来——与 D-02 第 4 条同一逻辑。操作定义见[验证计划](VOICE-COORDINATION-VALIDATION.md)指标表。

**但要修正上一版把该项统一按"0 容忍"的写法（2026-10-21 同日）**：一旦采用"先停后判"（见 §3.3），误停就是设计的组成部分，统一 0 容忍会与策略自相矛盾。分层为：

| 层级 | 判据 |
|---|---|
| 声学级误停（噪音、杂音） | **0 容忍**——不该触发就根本不该停 |
| 说话人/语义级误停（旁人说、本人对旁人说） | **允许发生**，改登记三项：误停恢复时延 p95、**恢复后复读率（0 容忍，复读即违规）**、**漏判抢话（0 容忍）** |

只登记"误停次数"会奖励"该停不停"的保守实现；只登记"漏判"会奖励"见声就停"的迟钝实现。三项一起看，才逼出可用的折中。

### 3.3 处置策略：停—判—续

打断不是"停/不停"的二元问题。按"**停止即时、恢复依语义**"分三段：

| 段 | 动作 | 触发 | 依据 |
|---|---|---|---|
| **停** | 立即静音：不再发新音频，已排队音频作废 | 检出声学级"有人在发话"（P0 通过） | 安全侧确定性——宁可误停，不可抢话 |
| **判** | 在判定窗内做 P1 / P2 归属判断 | 停之后立即开始 | 归属不确定时**维持静音**，不赌 |
| **续** | 判定为"不是说给助手" → 恢复播报（从断点续，或按新信息重组） | 判定完成且结论为否 | 体验侧可逆 |

取舍写明白：**代价是"偶尔卡顿一下再说"成为设计的一部分**。替代方案（等语义判完再决定停不停）会抢话，与 P0 直接冲突，不采用；把判定窗开得很长则会显著拖慢真实打断的响应，判定窗默认取 800ms–1.5s 并随版本冻结，实测后再定。

**规格状态**：判定窗长度、续播方式（断点续 / 重组）、以及 P1/P2 是否上线，均为设计待验项，不构成对上游能力的承诺；验不出时按"退回上一级 + 验收记录写明未覆盖项"处理。

**不变**：D-01 的分层口径不变（语义断点在 provider 的可配置模式，话轮与播出时序在 harness）；不新增第七层配置；播报节流与判定窗等参数的归属见[配置合同 §2「语音交互行为的归属」](CONFIGURATION-LAYERS.md)（Q2 已定：四档，工程参数归产研、体验开关归策略运营、业务内容归搭建者、正确性归平台契约）。

## 4. D-04 前后台委派的首次验收阶段：S2-c

**判定（2026-10-21）**：通话中"派给后台干活、结果回来再播报"这一能力，**第一次在 S2-c 网页语音验收**；S4 外呼复用同一批判据，另加通话回执项。

**不选另外两条的理由**：

- **直接在 S4 验**：S4 本身是独立 Gate（授权、号码、合规、人工承接都要验）。两个未验能力同时上线，出问题分不清是委派链路坏还是外呼链路坏。
- **另立新 Gate**：验收更干净，但多一个阶段；而 S2-c 本来就要验播报窗口、打断分流与播出回执，委派与它们共用同一条时序，拆开验反而要造两套用例。

**S2-c 必须证明的四件事**：

1. 委派出去的活**不占通话的交互槽**：等待期间用户仍可正常对话、打断、挂断；
2. 结果回流的插入时机受播报窗口约束（D-03），**不在用户说话时插播**；
3. 结果**过期或失效不得播报**（与 D-02「不播过期内容」同一判据）；
4. 挂断 / 取消时，后台任务与语音会话的终态**分别裁决**，不互相冒充（沿用 Task 体系"尝试 / 事项 / 副作用"三层）。

**不变**：电话仍是 S4 独立 Gate，不因本条提前宣称支持电话委派。

## 5. D-05 媒体通道与业务通道分离：`final` 是句尾，不是"说完了"

**判定（2026-10-23，WP1-1 实现后定）**：浏览器与本地服务之间只开一条媒体通道（`/ws/voice`），它**只搬运声音**；识别出的文本回到浏览器后仍走 `POST /api/runs`，进同一个 `ExecutionService`。**语音不构成第二条执行路径。**

**五条实施细则**（每一条都对应一个已经发生的错误或一个不可回避的事实）：

1. **`final` 只表示"这一句结束"，不表示"用户说完了"。** 中文逗号处的停顿就会被服务端 VAD 判成句尾；实测一句 4.85 秒的话在一次会话里被判句尾、并把后半句丢掉。轮次结束必须由**独立信号**表示（当前是 `asr.closed`，由客户端发 `asr.stop` 触发）。任何"收到 final 就提交"的写法都会截断用户的话。
2. **背压必须读真实队列，不能自己累加发送量。** 累计计数器只增不减，几秒后会把已发出去的数据也算成积压，从而开始永久丢帧——表现是识别在固定时间点截断，看起来像服务端问题。当前用 SDK 内部待发队列的 `qsize()`，超限即丢并计数上报。
3. **一句一个 TTS 实例。** 按句合成才能按句打断；一个长连接跨句合成，打断时说不清停在哪一句，"不播过期内容"也就无从判定。
4. **凭据缺失显式失败，不回退浏览器合成。** 回退会把验收记录里的"服务端固定组合"变成假话——浏览器 `speechSynthesis` 无法登记版本。
5. **停止时延分两个数，不许合并。** 浏览器侧测的是"停止指令 → `AudioBufferSource` 停止"（毫秒级，不含硬件）；声学级停止还要加扬声器与系统混音缓冲，只能靠录音回采测。这与 D-02 拆"harness 指令下发 → 客户端停止"和"provider 决定段"是同一条要求。**只报客户端数就宣称"停止时延 p95"是口径造假。**

**不变**：D-01 的分层口径不变；不新增第七层配置；本条只约束媒体传输，不改任何业务合同、事项状态或 Gate 划分。
