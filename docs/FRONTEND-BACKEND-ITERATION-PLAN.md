## 2. 导航候选如何进入后续计划

当前可作为已验证原型基线的是**两平面关系与现有入口**，不是终态候选树整体。后续新增菜单必须等相应产品范围和服务能力进入计划后再做。

| 候选阶段 | 侧栏稿提出的界面变化 | 当前状态与规划边界 |
|---|---|---|
| S2-a | 专家列表；专家内 7 个工作面与专家设置；设置中的工具/连接、模型/语音聚合为工作区平台设置；变更仍放在单专家上线页 | 两平面与专家内 7+设置已部分实现；物料、模型连接、部署维护目前仍独立直达。平台设置聚合是候选，不与当前资源入口等同 |
| S2-b | 搜索与新建、完整摄入、流程画布、测试中的判据/人工评分 tab；不增加专家平面菜单数 | 当前部分 UI 已存在本地形态；搜索、正式摄入/索引、R3 画布与判据能力需按服务 Gate 验收。S2-b 与 R2 摄入的分期差异见 §6 |
| S2-c | 任务与主动服务菜单；真实办理、发布 Gate 与回滚留痕 | 本地配置/模拟不能替代 R4 业务执行、配对评测、审批与回滚 |
| S3 | 工作区级变更、完整平台设置、成员权限、系统诊断与首云 | 侧栏候选；按 R5a 范围和另行确认的导航决策实施 |
| S4 | 工作区/租户切换与多云扩展 | 不提前放入当前导航；对应 R5b 的独立验收 |

`S2-a/b/c` 描述产品与导航候选阶段；`R1/R2/R3/R4` 是有 Gate 的交付版本。只有 RELEASE-PLAN 与 Gate 矩阵可以确定正式版本顺序和退出条件。

## 3. 后续迭代计划

计划按依赖顺序推进。每批可做对应的前端连接与必要的交互修正，但不得为了让原型“看起来完整”而提前实现后续版本的可执行语义。

### I0 · 范围对齐与原型边界

**目的：** 明确哪些页面是服务客户端、哪些仍是独立演示。WP9 两平面导航范围与服务端版本工作面已完成本机联调；本阶段剩余重点是把字段映射和仍属本地演示的写入动作保留在边界清单中，不扩张后端能力范围。

| 工作 | 出口判据 |
|---|---|
| 按当前两平面路由、页面、状态和写入动作建立“页面/动作 → 应用服务用例或本地演示”映射；不预设每个 `dispatch` 都能一对一变成 API | 映射表覆盖配置保存、校验、冻结候选、知识/物料、测试、上线等现有写入动作；未映射项明确标本地演示或后续版本 |
| 对照 D3 字段目录、六层合同、R1-WP4 清单边界，标出不可映射字段 | 未确认/不可映射的数据只读保留，不静默丢弃或转换；`routeGraph` 不进入 R1 可执行配置 |
| 对齐 WP9 页面范围和侧栏候选的阶段划分 | RELEASE-PLAN 已记录当前两平面作为 R1 基线；平台设置聚合、S2-b 全量行为或 S3 入口仍按候选范围，不因 WP9 联调提前开放 |
| 给本地模拟的批准、发布、回滚、运行结果加清楚的演示边界；布局/键盘/无障碍修复可继续 | 原型可验证 UI，但任何本地状态变化均不被描述为服务端批准、发布或运行成功 |

- 两个版本分别留独立 Gate 证据；首云不能代替多云验收，多租户和跨专家知识也不因侧栏有相应入口而自动成立。

## 7. 风险与不做

- 不在 R1 把 `routeGraph` 当可执行配置；R1-WP4 仍是单元清单与规则，`Unit.body` 仅按权威计划预留，图工作面按 R3。
- 不把 localStorage、本地浏览器解析、测试快照、批准按钮或本地发布状态机作为后端验收证据。
- 不因侧栏候选增加“任务”“变更”“平台设置”入口就新增领域对象、授权、跨专家共享知识或服务承诺。
- 不用 R1 页面联调代替 R1 父 Gate；不把 S2-alpha UI 完整度称为正式 S2 退出。
- 不在服务、数据作用域与授权合同尚未验证前接入真实外部写入、生产发布或多租户。

主要风险是把“本地原型能力”误判为“后端已实现”，或因侧栏候选更新而出现一套菜单、另一套 Gate 的双重路线图。缓解方式是每个 UI 页面同时标明当前数据源、对应 R/WP、对应 Gate 证据与未实现状态。
