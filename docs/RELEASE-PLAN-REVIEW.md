# RELEASE-PLAN 与当前产品方向评审记录 v0.1

日期：2026-10-22。状态：多专业视角综合评审，供后续决策和计划修订参考。本文不新增产品或架构决策，不改变已确认产品范围，不替代 [ROADMAP](ROADMAP.md) 与[客服交付建设方案](CUSTOMER-SERVICE-DELIVERY-PLAN.md)的阶段 Gate。

本次评审依据工作区中的 [版本切分与核心交付 v0.1](RELEASE-PLAN.md) 及产品、架构、交付、体验和验收文档。结论只反映文档与已有验证证据，不将计划、原型或知识库研究当作已实现能力或市场证据。

## 结论

**长期产品方向有条件支持。RELEASE-PLAN 目前是有价值的阶段内切分草案，还不是可直接执行的交付与验收基线。**

产品方案的逻辑较连贯。从获授权资料开始，用户配置业务 Agent 并执行受控请求。系统保留运行证据，再通过评测、审批和回滚管理改动。把运行内核、权限与结果事实留在 Loomrise，把外部运行时留在 Adapter，也符合现行架构方向。

但文档没有证明首要买家、购买触发点或可重复的客户收益。R0 的语音退出判据、R2 的 S2-a Gate 覆盖、Unit 方案的采纳状态也未闭合。因此应先补齐决策和证据追踪，再把版本表当作团队执行基线。

## 评审视角

各视角使用不同的评价目标。以下意见是对项目材料的审查，不代表对应方向已经获批。

| 视角 | 评价目标 | 综合判断 |
|---|---|---|
| 产品经理 | 用户是否能完成一个有业务结果的完整任务，产品主张是否超出已验证事实 | 业务结果、运行证据和受控改进组成了有价值的长期主张。首个买家与任务仍需明确和验证 |
| 市场与定位 | 谁会采用和付费、什么事件促使购买、相对现有替代方案的理由是否明确 | 开源、可迁移和自有云可能吸引重视控制权的技术团队，但目前没有购买意愿、部署偏好或重复使用证据 |
| 系统架构 | 领域事实、权限、结果、版本和发布权威是否清楚，上游依赖能否替换 | Loomrise 的核心事实权威边界整体合理，但 Unit 提案状态与版本计划冲突，R0 的行为迁移风险也被"只改形状"弱化 |
| 平台研发 | 持久性、幂等、撤销、恢复和多入口写入能否由测试与运行工件证明 | 配置可信与运行可信分批是好取舍，但 R1 与 R2 的退出证据还未覆盖持久化、发送和恢复的全部要求 |
| 项目管理 | 依赖、工作包、责任与退出条件是否可追踪，是否存在无法判定的 Gate | R0–R4 排序大体有依据。R1 与 R2 需要拆出可单独验收的工作包，R5 需要恢复 S3 与 S4 两个检查点 |
| 产品设计 | 目标角色能否理解任务、状态和阻断原因，能否恢复，不同输入方式是否可用 | IA、渐进披露和先清单后画布方向合理，但版本计划缺少"角色 → 任务 → 页面 → 证据"映射，R1 与 R2 的状态体验尚未验证 |

## 方向的优势

1. **产品价值来自完整业务闭环。** 产品把配置、业务请求、持久结果、案例、回放、审批和回滚放进一条长期工作流。若能验证客户收益，这比单独提供 Prompt 编辑或聊天预览更有产品价值。依据见 [PRODUCT](PRODUCT.md) 与[产品形态与开放接入规范](PRODUCT-FORM-AND-INTEGRATION.md)。
2. **业务责任边界清楚。** 业务完成由持久结果及适用的外部结果 ID 证明；模型输出、消息发送和业务解决分开记录。授权、确认、幂等和取消也进入执行合同，适合高风险业务动作。
3. **版本顺序考虑了不同的验证方式。** R0 单列合同迁移，R1 验配置可信，R2 验运行可信，减少在同一验收批次中混合合同变更与客服能力开发的风险。
4. **编排图不是第一交付物。** 先用真实配置验证数据模型，再决定画布设计和实现，有机会减少模型与 UI 的返工。清单也为键盘用户保留了非画布操作路径。
5. **状态与证据边界已有基础。** ROADMAP、S1 验收报告和前端轮次报告明确区分历史实现、原型和计划。这个规则必须延续到版本报告和对外说明中。

## 需要优先处理的问题

### P0：确定执行基线前解决

1. **R0 的语音 Gate 仍不可判定。** [RELEASE-PLAN](RELEASE-PLAN.md) §1 仍称语音 Gate 没有可判定数字，但 ROADMAP 已按 D-03 更新了判据。[语音验证计划](VOICE-COORDINATION-VALIDATION.md)要求测试前登记阈值。停止时延 p95 上限仍待基线登记。R0 退出条件写"指标有数据"不足以说明通过。退出清单还应覆盖真实网页音频、固定媒体组合、中文可懂度、首响和真实模型 SSE，并明确哪些 P0 指标属于 S1，哪些 P1 与 P2 指标留在 S2-c。
2. **R2 摘要不能证明 S2-a Gate 全部通过。** [客服交付方案 §3](CUSTOMER-SERVICE-DELIVERY-PLAN.md)要求冻结配置、来源与权限检查、固定样例、人工批准、沙盒环境和入口版本绑定，并要求草稿不生效。它还要求物料原件及权限版本真实保存、支持格式恢复和下载，以及人工发送前重验会话占用和版本。R2 核心实现提到其中若干项，但"五组工件"没有逐项映射这些 Gate。应逐条列出要求、工件、正反例和通过条件后，再称 S2-a 全部关闭。
3. **Unit 方案尚未采纳，却进入 R1 的必要合同。** [路由与能力单元](ROUTE-GRAPH-AND-UNITS.md)标注"提案，未采纳"。[RELEASE-PLAN](RELEASE-PLAN.md) §3 将九字段 Unit 和空 `body` 预留列为 R1 内容。先明确采纳决定，再同步权威合同和版本计划。未决方案不应成为建库约束。
4. **R0 的合同变更有行为迁移风险。** `Verdict`、授权查询、路由结果和事项状态分层可能改变拒绝、确认、挂起、停止及 Adapter 投影行为。除保留既有 11/11 回归外，还需为新语义增加测试，并将结果绑定 schema、代码与 Adapter 版本。RELEASE-PLAN 一处要求先完成语音证据再迁移，另一处允许合同代码并行推进。计划应说明哪些代码和测试可以并行，何时应用迁移，以及哪些证据必须在迁移前或后生成。

### P1：进入对应版本前补齐

1. **R1 与 R2 的工作量和验收关系不够清楚。** R1 同时包含持久化、outbox、配置冻结、硬规则、Task、MCP 和后台写入一致性。R2 同时包含发布、摄入、物料、Widget、Inbox 和幂等运行时。拆分版本后仍需将它们拆成可并行、可独立验收的工作包，并明确各自负责人、依赖和证据位置。R1 还要覆盖事务失败、进程崩溃、恢复、outbox 重放，以及撤销事项不会在恢复后复活。
2. **版本计划缺少用户任务到页面的映射。** R1 的规则、Task 和 MCP 能力对应哪些用户角色、页面和配置深度尚不明确。当前本地工作台原型不含完整 Task 工作面，规则编辑与服务端功能也未实现。应在实施规格中列明每个版本的角色、主要任务、页面入口、状态和验收证据，并说明本地原型与正式服务的边界。
3. **R3 的"真实配置跑过一轮"没有合格标准。** 应定义真实配置包含哪些业务分支和权限边界，以及什么证据允许启动画布实现。画布上线前还应通过任务测试，比较用户查找路由错误、审阅边级差异和理解单元范围的时间与错误率。配置结构本身不足以证明画布有用。
4. **R4 的退出例子不覆盖完整 S2-c Gate。** 一条坏例跑完改进链路能证明端到端路径存在，但不能代替真实沙盒工具结果、确认与取消、未知状态对账、配对评测、权限边界、文件自动发送和回滚等要求。R4 应逐条引用 S2-c 权威 Gate 的工件。
5. **R5 合并了两个独立交付阶段。** 客服交付方案为 S3 首云部署和 S4 扩云设有不同依赖与退出条件。保留 R5 作为总览可以，但应增加 S3 与 S4 子里程碑、入口条件和各自 Gate，逐云验证安装、认证、网络、存储、升级与恢复。
6. **R2 的运行时证据需要覆盖重试与撤回。** 计划应定义幂等键对应的业务操作，并验证并发重复、跨渠道或重启重试、工具已受理但调用超时、迟到回执和未知状态对账。资料撤回后还应证明索引和缓存停止提供旧内容，并使受影响的发布版本或评测进入待重验状态。

### P2：在市场与范围规划中验证

1. **首要买家和购买任务未收敛。** 当前文档涵盖 AI 产品、解决方案、开发者、策略运营、一线坐席和访客，也覆盖客服、销售与跨行业场景。尚无项目材料记录目标客户访谈、付费、采用、续用或部署偏好的直接证据。
2. **两个可测试的市场假设不能合并为一个 ICP。** 一个假设是重复为客户交付网站客服的解决方案团队。另一个是假设是在线教育机构中处理课程咨询和预约的业务负责人。前者偏交付工具买家，后者偏业务运营买家；应分别验证触发点、预算、采购路径和当前替代方案。
3. **30 项参考机制不应变成隐性范围承诺。** RELEASE-PLAN 将 ElevenLabs 的 30 项借鉴机制映射到版本，但其中多项仍可跨版本调整。每项应关联具体用户问题和验收指标。没有证据支持的机制应保持候选，不为了清单完整而扩大平台范围。
4. **首个客户结果要与运行安全指标分开。** 试点可以从获授权资料答疑、无依据时转人工、可复核运行记录开始。除设置正确答复、恰当转人工等质量指标外，还应测首次有效答复耗时、每个解决事项的人力与模型成本，以及客户是否持续回来复盘和发布。指标目标应先登记，再跑试点。

这些市场建议只调整验证顺序，不自动缩减已确认产品范围。若项目要删改客服、任务、渠道或自有云范围，应另作产品决策并同步权威文件。

## 个人知识库带来的架构启发

个人知识库中的研究条目提供设计参照，不构成 Loomrise 的市场需求、技术选型或 ROI 证据。本节只记录可迁移的通用结论，不引用个人工作语境或私有材料。

- **DeepSeek Harness 与 Cordis 插件架构：** 运行时可通过 Provider 与 Consumer 边界替换能力；模型可见输入应能从持久事件中重建；工具调用应经过执行前授权、审批和沙箱，再规范化结果。它们支持 Loomrise 的 Adapter 与审计方向，但通用 Harness 本身不等同于面向业务的配置和运营产品。
- **Agent 能力 Seam：** 抽象应覆盖接口、实现与实际消费者，并验证替换 Provider 后业务链路仍能工作。边界过细会增加配置、排错和运维成本。因此每个 Adapter 或抽象都应有明确的替换收益和回归证据。
- **GEP、MCP 与 Skill 的分层比较：** 工具发现、任务指导和经验证能力复用是不同问题。Loomrise 可以借鉴能力资产的来源、验证和复用记录，但在自动评分、跨 Agent 传播或经济机制进入范围前，需要证明客户任务会因此更快或更可靠地完成。
- **EvoMap 企业案例研究：** 厂商案例可帮助提出“重复问题的已验证修复能降低后续成本”的测量假设。案例中的成本数字和预测属于厂商单例，不代表 Loomrise 的收益。

知识库没有提供 Loomrise 客户访谈、购买意愿、自托管需求或首个市场选择的直接证据。市场决定仍需由项目自己的客户研究与试点支持。
