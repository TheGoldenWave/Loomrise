# 硬规则表达模型 v0.2

状态：**已裁决（2026-10-22）**；2026-10-12 首版提案。§9 六问已全部定案，结论并入 §3.1 / §3.2 / §3.4。

本文定义 `HardRule` 的**表达能力与灵活性边界**——回答三个问题：规则能写到多灵活、**灵活从哪里来**、**哪里必须不灵活**。

- 六层职责与"不可自动修改边界"见[六层配置合同](CONFIGURATION-LAYERS.md) §2 / §7.4。
- 界面落点见[S2 平台信息架构与主菜单定义](S2-IA-NAV.md) §4.3.2「边界」tab · 硬性限制。
- 对象权威见[架构与对象权威](ARCHITECTURE.md)。
- 为什么现在就要定：规则形状直接决定三 tab 的**字段级配置规格**（启动方案 D3）与 `AgentSpec` 合同（K1）。

## 0. 结论

1. **诉求成立，但当前实现的问题不是"一成不变"，是"维度太少"。**
2. **灵活性的正确来源是「表达维度的完备」，不是「规则条数」。** 规则条数增长是**状态建模缺失的补丁**——实测样本里 74 条规则约 12 条在讲「别重复」，这就是条数膨胀的症状（IA-NAV §1.2-5）。
3. 因此本模型的目标是：**用更少的规则覆盖更多垂直场景**，而不是"允许写更多规则"。
4. 三条必须**保持不灵活**的底线见 §5——其中第 3 条是唯一的防膨胀闸门。

## 1. 现状审计（按代码说话）

依据 `loomrise/contracts.py` 的 `HardRule`：

| 字段 | 支持什么 | 缺什么 |
|---|---|---|
| `behavior` | `allow` / `deny` / `require_confirm` | **只有 3 值**。且 `allow` 语义上不属于"硬性限制"；与界面的四类（**禁止 / 必须 / 停止 / 去重**，IA-NAV §4.3.2）**对不上**——这是**文档与实现的一处真实不一致**。**2026-10-22 已裁决**：`allow` 不是少一类，是归错了层，见 §3.4 |
| `scope` | `global` / `task` / `skill` | 与三层作用域一致 ✅ |
| `when_arg_equals` | **对工具入参的精确等值**（`dict[str, Any]`） | **比较、集合、时间窗、计数、逻辑组合，全部没有**——刚性根源在此 |
| `tool` | 单个工具 ID | 不能表达"字段齐备度""路由步骤""召回结果"等非工具条件 |
| `requires_confirm` / `idempotent` | 两个布尔 | 无法表达确认的**升级路径**与幂等键的**组成方式** |
| — | — | 无 `priority`、无冲突裁决、无有效期、无严重级别、无命中留证要求 |

**结论**：当前模型能表达的最复杂规则是「调用工具 X 且参数 a 等于 b 时 → 拒绝 / 需确认」。这覆盖不了跨垂直的多数需求。

## 2. 跨垂直场景需要什么样的规则

抽象后的需求形态（不指向任何具体行业）：

| # | 需求形态 | 规则该怎么说 | 当前能否表达 |
|---|---|---|---|
| 1 | **数值阈值** | 某字段 > N 时必须人工确认 | 不能（只能等值） |
| 2 | **集合成员** | 涉及 A / B / C 类目时禁止 | 不能 |
| 3 | **时间窗** | 某时段内禁止某动作；活动期内放宽 | 不能 |
| 4 | **频次 / 冷却** | 同一对象 24h 内最多 N 次 | 不能（且这是**状态**，不只是规则） |
| 5 | **复合条件** | 首次接触 **且** 未确认身份 → 禁止承诺 | 不能 |
| 6 | **槽位齐备度** | 关键字段缺失时禁止执行写入 | 不能 |
| 7 | **跨对象引用** | 引用的知识已撤回 → 禁止引用该事实 | 不能 |
| 8 | **去重 / 幂等** | 同一业务请求只允许一次写入 | **能**（布尔） |
| 9 | **升级 / 转人工** | 连续两轮未解决 → 强制转人工 | 不能（需计数 + 组合） |
| 10 | **输出后校验** | 对客输出不得含某类数字 | 不能（属输出合同，但有硬性的一面） |

**10 类里 8 类表达不了。** 这就是"普适各类垂直业务"的真实差距。

## 3. 表达模型（提案）

把 `HardRule` 拆成三段：**`when`（什么时候触发）· `verdict`（裁决什么）· `enforce`（怎么执行与留证）**。

### 3.1 `when` —— 从「等值字典」升级为「可组合条件」

**三类条件原子**：

| 原子 | 判定什么 | 形态 |
|---|---|---|
| **`fact`** | 一个**已声明字段 / 事实**的取值 | `{ field, op, value }` |
| **`event`** | **本轮发生过什么** | `{ event, ... }`：`tool_call{tool,args}` · `route_step{step}` · `recall_hit{snippet_id}` · `input_matched{pattern}` · `channel` · `attempts` |
| **`state`** | **跨轮的计数 / 窗口状态** | `{ metric, window: session\|cycle\|24h\|forever, op, value }`（四种窗口见下） |

**`fact` 的算子集**：

```text
eq · ne · in · not_in · gt · gte · lt · lte · between
matches · exists · is_set · is_unset · changed_to
```

（`matches` 只做**确定性模式匹配**（枚举 / 关键词 / 正则），不做语义判断——见 §5-3。）

**组合算子**（可嵌套，**最多 2 层**）：

```text
all_of([...])   # AND
any_of([...])   # OR
none_of([...])  # NOT
```

> **上限 2 层是刻意的**：再深就说明这段逻辑应该被建模成一个字段或一个 Skill 步骤，而不是一条规则。

**这条上限同时管边条件（2026-10-22 定）。** [路由与能力单元](ROUTE-GRAPH-AND-UNITS.md) §3.4 的边 `condition` 与本节的 `when` **共用同一套算子**，因为硬规则与路由边在实现上是同一个判定器。既然共用算子，就必须共用深度——否则一份草稿里"写规则最多 2 层、写边条件可以写到没人看得懂"，是同一套语言两套规矩。

- **`llm` 叶不计入层数**：它是叶子（一个概率判定），不是组合。层数只数 `all_of` / `any_of` / `none_of`。
- **`routing.mode = deterministic` 不放松这条**：全规则路由的分支更多、条件更死，恰恰更容易写出"互斥性靠人记住"的深层条件。`routing.mode` 影响的是**闭集告警阈值**（[路由与能力单元](ROUTE-GRAPH-AND-UNITS.md) §4.0），不是条件深度。
- 超过 2 层：**保存允许、提交阻断**——草稿可以有中间态，但它不是一个可提交的形状。

**`state` 的四种窗口（2026-10-22 定，由三种改为四种）**

| 窗口 | 含义 | 典型用途 | 谁能选 |
|---|---|---|---|
| **`cycle`**（**默认**） | **同一服务周期 / 同一事项内** | 执行环重入次数（`max_rounds`）、同一单内的重试 | 业务作者 |
| **`24h`** | 滚动 24 小时，**横跨事项** | 触达频控（同一对象 24h 内最多 N 次） | 业务作者 |
| **`forever`** | 累计，永不重置 | 累计事实（"这个用户历史上投诉过几次"） | 业务作者，须显式声明 |
| **`session`** | **渠道级会话**（电话＝一通；IM＝同一 `conversation_id`） | 本轮追问次数 | **不暴露给业务作者**——它是工程参数（Q2 ②a），不是策略参数 |

**默认是 `cycle`，不是 `session`。** 理由：`session` 会在用户挂断重拨时重置，用它防环等于没防；`forever` 会让"这件事已经办完了"还在计数。**"同一件事"才是业务作者脑子里的那个单位。**

`max_rounds` 归 `cycle`——换一件事该重置，同一件事内不能无限转。`waits` 超时**不进 `state`**：它是事件不是计数；但它必须声明 `timeout_ms` 与超时去向，否则"等"没有终点。

**硬约束（这条决定整套设计能不能成立）**：

> **条件只能引用「已声明字段」**（人设 tab 的变量与字段表）**与系统事件枚举**，**禁止自由文本条件**。
>
> 收益有三：① 规则**可 Schema 校验**（字段不存在直接报错）；② 规则**可静态检测冲突**（同一字段被 禁止 ∧ 必须 同时约束）；③ 规则**可被回放复现**（条件里的每个字段值都在 `RunEvent` 里）。

### 3.2 `verdict` —— 四类裁决 × 动作

对齐 IA-NAV §4.3.2 的四类。**注意这里只有四类，不是五类**——`allow` 不在其中，原因见 §3.4。

| 类别 | 动作 | 必填 |
|---|---|---|
| **禁止** `deny` | 阻断动作 + **给出替代**（替代话术 / 替代路径） | `reason`、`fallback` |
| **必须** `require` | `require_confirm`（要求确认）· `require_field`（要求补字段）· `escalate`（要求升级 / 转人工） | `reason`、目标 |
| **停止** `stop` | 立即终止本轮 | `stop_reason` |
| **去重** `dedupe` | 声明幂等键的**组成方式**（不再只是一个布尔） | `idempotency_key` 表达式 |

**`allow` 必须移除，但它不是"少一类"，是"归错了层"**——见 §3.4。

### 3.3 `enforce` —— 执行、优先级与留证

| 字段 | 作用 |
|---|---|
| `scope` | `global` / `task` / `skill`（保留三级） |
| `priority` + **冲突偏序** | 不同类按固定偏序裁决：**禁止 > 停止 > 必须 > 去重**；同类按 specificity（条件越具体越优先） |
| `reason` | 内部理由（必填，供审计） |
| `customer_facing` | 该规则是否允许出现在对客解释 / 替代话术里 |
| `valid_from` / `valid_until` | 规则有效期（活动期规则的显式承载，替代"临时改规则"） |
| `severity` | `redline`（命中触发**自动回滚 / 停止暴露**）\| `normal`（记录 + 告警） |
| `evidence` | 命中必须写 `RunEvent`：`rule_id` + `content_hash` + **当时的字段值** + 判定路径 |

### 3.4 四种结局，只有一种叫裁决（2026-10-22 定）

一个输入进来，最后可能落在四种结局上。它们**性质不同，不能共用一个枚举**——这是 §1 那处"文档与实现不一致"的真正成因。

| 结局 | 取值 | 由谁产生 | 归谁 |
|---|---|---|---|
| **裁决** | `deny` / `require` / `stop` / `dedupe` | `HardRule`（模型外、前置） | `Verdict` |
| **授权** | 已登记（可调）/ 未登记（拒绝） | `ToolPolicy` 查表 | `ToolPolicy` |
| **路由去向** | 去某个单元 / 阻断 / **挂起** | G0 闸门 | `GateOutcome.route_to` |
| **事项状态** | 含 `reconciling`（待对账） | 事项状态机 | `TaskItem.state` |

**四条边界：**

1. **`allow` 不是裁决**。删除 `Verdict.allow`——"放行"由 `ToolPolicy` **登记即允许**表达；未登记即拒绝，这个默认值不需要一条规则来声明。它在实现里是真实产出（`rules.py` 的优先级链、`tests/test_s1.py` 的"只读放行"断言、`adapters/agentscope_runtime.py` 映射到 `PermissionBehavior.ALLOW`），但它表达的是**授权结果**。把它留在 `verdict` 里，等于让裁决器去回答"这个工具能不能调"。
   > 混缠的证据：`rules.py` 现在是 `if not hits: return DENY("工具未在 ToolPolicy 中登记")`——**理由是"没登记"，这是授权语言，却由裁决器在说。**

2. **"强制去哪"不是裁决**。[路由与能力单元](ROUTE-GRAPH-AND-UNITS.md) §2.4 曾写成"命中即决定（阻断 / 强制单元 / 强制转人工）"，那是把路由结果当裁决。它是 `GateOutcome.route_to`，与 `Verdict` **并列**而非从属。

3. **"挂起待对账"不是裁决**。`stop` 是终止本轮，`require.escalate` 是转人工，`reconciling` 是**不终止、不转人工、挂起等外部**。三者混在一起，就会出现"用一条 `stop` 规则表达'先别动、等对账'"——而那会真的停掉会话。

4. **外部 SDK 的 `ALLOW` 仍要产出**，但它是**授权层向适配器的投影**，取值来自 `ToolPolicy`，不来自 `Verdict`。

**一处命名后果**：`Decision` 从此只承载裁决，不再回答"允许吗"。授权查询与裁决查询是两次独立调用，顺序固定为 **先授权、后裁决**（未授权的工具连规则都不必跑）。

## 4. 灵活性从哪里来：三个机制

### 4.1 维度化（§3）

表达能力来自 `when` 的算子与组合，**不是来自条数**。同一场景下规则数应该**下降**，不是上升。

### 4.2 规则模板 `RuleTemplate`（按业务场景预置骨架）

新建专家时按场景**勾选**一套规则骨架（**首批骨架即定位锚定的两个场景：客服、销售**），生成本地规则。

**两条硬约束**：

1. **模板只给骨架，不预填阈值。** 阈值必须由人在初始化时确认——沿用"阈值人登记初始值"的既有原则。
2. **生成即本地**：模板产物是可以改的普通规则，不是继承关系。改模板不影响已建专家。

### 4.3 规则复用不复制

`rule_id` + `content_hash`（内容指纹）——同一规则只有一份定义、多对象引用。这是 IA-NAV §6.2-18 已建议引入 `content_hash` 的**主要收益兑现处**：它让"跨场景重复规则"可被检测，服务"反堆积优先于好维护"。

## 5. 三条必须「不灵活」的底线

灵活性必须有止境，否则会变成规则膨胀。

### 5.1 `HardRule` 始终在**模型外**执行

条件再复杂，裁决权也不交给模型。模型只接收**当前有效约束摘要**（`CONFIGURATION-LAYERS` §5）。

### 5.2 `CONFIGURATION-LAYERS` §7.4 的不可自动修改清单**不动**

自进化不得静默修改：权限 / 安全 / 停止条件、工具授权范围与副作用等级、确认要求、幂等策略、`Outcome` 语义、发布审批权、数据保留策略。**只能形成待审提案。**

> 推论：规则内部也要分 `locked` / `mutable` 段——**类别与红线属性是 `locked`**（改它等于改事故面），**条件与阈值可以是 `mutable`**（如活动期时长）。这与启动方案 A1 是同一套协议。

### 5.3 「确定性可判定」闸门（唯一的防膨胀闸门）

> **规则的条件必须是确定性可判定的。**
>
> 任何需要**语义判断**的条件——"用户是不是在犹豫""这句话是不是在投诉"——**不得写成规则**。

这类判断应进 **Skill / SOP** 或作为模型的**表达层决策**，并在 `RunEvent` 留下可观察证据；只有被证明稳定、可枚举、可复现的，才允许上提为确定性条件（如从"犹豫"收敛成"连续两轮未确认关键字段"）。

**这条闸门的作用**：把"加规则"的默认动作改成"先归因到正确的层"。这也正是 `CONFIGURATION-LAYERS` §5 与 IA-NAV §1.2-5 的既定判断。

## 6. 校验、安全与影子运行

灵活性带来的风险是"规则写错 → 直接阻断业务"。四道校验必须一起做：

| # | 机制 | 做什么 |
|---|---|---|
| 1 | **Schema 校验** | 条件只能引用已声明字段；算子与字段类型匹配；嵌套不超 2 层 |
| 2 | **静态冲突检测** | 同作用域内 禁止 ∧ 必须 冲突、条件不可达、`content_hash` 重复 → **提交时阻断**（沿"确定性冲突阻断、语义冲突只建议"的既有口径） |
| 3 | **影子运行** | 新规则先在案例集上跑「会命中哪些历史运行」，**列出命中清单供人判断**，不直接生效 |
| 4 | **回放** | 规则变更走 `golden` 关键回归 + 高风险规则走 Reserve Gate |

红线规则命中 → 沿用既有机制：全量自动回滚、灰度自动停止暴露，均留证且可被人推翻。

## 7. 界面影响（「边界」tab · 硬性限制）

现行形态：规则列表，按 **类别 × 作用域** 分组、**禁平表**（保留）。

需补六件：

1. **条件编辑器**——字段选择器（**从人设 tab 的字段表取**）+ 算子 + 值 + `all / any / none` 两层，**不允许手写自由文本**。
2. **冲突与覆盖提示**——同一字段被多条规则约束时高亮。
3. **规则详情**——命中证据（来自 `RunEvent`）+ 引用计数 + 最近命中。
4. **有效期**——活动期规则的起止（替代"临时改规则"）。
5. **红线标记**——哪些规则命中会触发自动回滚 / 停止暴露。
6. **规则数告警**——单专家规则数超阈值时提示"疑似该归因到状态建模或 Skill"，而不是继续加。

| **S3** | 外部审批类动作（需多角色，与登录权限体系一起） |

## 9. 六问裁决结果（2026-10-22）

| # | 问题 | 结论 | 落实处 |
|---|---|---|---|
| 1 | `Behavior.ALLOW` 与四类裁决不一致 | **原始问法不成立**——不是"删一个值"，而是**四种不同性质的结局被塞进一个枚举**。裁决（4 类）· 授权（登记即允许）· 路由去向（含挂起）· 事项状态（`reconciling`）**四层分开**；`Verdict.allow` 删除，"放行"由 `ToolPolicy` 登记表达 | §3.4 |
| 2 | 条件嵌套上限 | **2 层，且管到路由边 `condition`**（同一套算子必须同一深度）；**`llm` 叶不计层数**；`routing.mode` 不放松；超限保存允许、提交阻断 | §3.1 |
| 3 | 条件能否引用**平台级**事实 | 按原建议：**允许只读引用，须显式声明来源**。不阻塞（S2-b） | §3.1 硬约束 |
| 4 | `state` 窗口 | **由三种改为四种**，新增 **`cycle`（服务周期 / 同一事项）并作默认**；`session` 降为工程参数、不暴露给业务作者；`max_rounds` 归 `cycle` | §3.1 |
| 5 | `RuleTemplate` 首批骨架 | **已定**：客服、销售各一套（见[产品定义 §定位](PRODUCT.md)） | — |
| 6 | 规则数告警阈值 | 按原建议：初始 30 条 / 专家，超阈值必答"为什么不用 Skill 或字段表达" | — |

**这三条（1/2/4）就是原 IA-NAV §6.4 里标为"阻塞出稿"的 38-1 / 38-2 / 38-4，已闭合。**
