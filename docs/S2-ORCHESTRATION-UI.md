## 1. 技术选型：`@xyflow/react`（React Flow v12）

### 1.1 先修正一处口径

RG-1 当时写"进 S2 → IA 17 页变 18 页"，**按实际 IA 是错的**：配置挂在**版本详情的三个 tab** 里，`§4.3` 明确"不进主菜单"。所以本次**不新增二级页，17 页 / 23 面口径不变**——改的是「流程」tab 的内部结构。同类先例见 §4.2 ③ 的"评测缺口入口不新增二级页"。

### 1.2 选型表（按我们的设计逐条比，不按库的卖点比）

| 需求 | 强度 | React Flow | AntV X6 | LogicFlow |
|---|---|---|---|---|
| **节点内嵌复杂 UI**（端口、段型徽标、覆盖继承标记、校验角标、运行数） | **必须** | 节点就是 React 组件，零成本 | 需走 HTML 节点扩展 | 需自定义节点 + 扩展 |
| **多端口锚点**（每单元 ≤3 入、≤3 出，端口是一等对象） | **必须** | 多个 `<Handle>`，天然 | 支持（ports 配置） | 支持 |
| **逐层独立画布 + 面包屑下钻**（不用嵌套子图） | **必须** | 换数据即换图，简单 | 同 | 同 |
| **只读态叠运行数据 / 版本 diff 叠加** | **必须** | 自定义节点/边直接渲染 | 可行但更绕 | 弱 |
| **保存前校验 + 字段路径级定位** | **必须** | 外部校验器 + 节点高亮 | 同 | 同 |
| **自动布局**（位置不是语义） | **必须** | 配 dagre 即可 | 内置布局更全 | 需插件 |
| 数千节点性能 / 框选 / 对齐线 / BPMN 插件 | **不需要** | 一般 | **强项** | 强项（BPMN） |
| 内置 Undo/Redo | **不要**（见 1.4） | 无 | **强项** | 有 |
| 小地图 | 不需要（单层 ≤12） | 有 | 有 | 有 |
| 技术栈匹配 | — | **React（栈已定）** | 框架无关 | 框架无关 |

### 1.3 四条理由

1. **栈已经定了 React + Vite + TS**（IA §5.1-T1）。X6 / LogicFlow 的"框架无关"在这里**不折现**，只多一层包装与心智负担。
2. **我们的图是故意做小的**：单层 ≤12 节点、默认深度 3（RG-6）。X6 的护城河正好是"大图、框选、对齐线、BPMN"——**用不上**。付它整套 API 的学习成本，却不花它的长处，是最不划算的选择。
3. **真正吃紧的是"节点复杂度"，不是"图规模"**。一个单元卡片要同时显示：端口（带 `requires`/`completion` 提示）、段型（`locked`/`mutable`）、覆盖继承标记、校验错误、版本 diff 徽标、运行数角标。**这些在 React Flow 里就是一个函数组件**；在 X6 里要写 HTML 节点 + 生命周期桥接。
4. **它唯一缺的 Undo/Redo，对我们不是缺口**。见 1.4。

### 1.4 为什么"画布级 undo"我们本来就不能用

ElevenLabs 的教训是：**草稿 autosave、刷新即失去 undo**。它的 undo 只覆盖画布内的操作栈，而我们要撤销的是**跨 tab、跨页面、与草稿 revision 绑定**的改动（改了人设、又改了流程、再撤销一步）。

所以：**撤销栈放在草稿层，不在画布层**。撤销单位是"草稿快照"，不是"画布操作"。这条一旦定下，X6 内置 History 就从"优势"变成"用不上的东西"。

### 1.5 不选另两个的具体理由

- **AntV X6**：能力过剩。它的价值在"图编辑引擎"，我们只需要"一个能放卡片的小画布"。选它等于为用不到的能力付学习与升级成本。
- **LogicFlow**：定位是**审批流**，节点形态固化（矩形 / 菱形 / 圆）+ BPMN 插件。我们的节点是"带契约层与端口的卡片"，没有 BPMN 诉求；它的强项与我们的强项不重叠。

### 1.6 依赖与许可证

| 依赖 | 用途 | 许可证 | 备注 |
|---|---|---|---|
| `@xyflow/react` v12 | 画布 | MIT | **用 v12 的新包名**，不用 v11 的 `reactflow` |
| `@dagrejs/dagre` | 层级自动布局 | MIT | 只做布局，不参与语义 |
| `zustand` | 画布视图态（选中、折叠、悬停、下钻栈） | MIT | **只存视图态**；配置真值在草稿，不经 zustand 落库 |

**许可证边界**：只用 MIT 运行时依赖；**不引入 xyflow Pro 的示例/组件**（付费示例集，非运行时依赖）。新增依赖按 `VERSION-PINS.md` 登记。

## 2. 页面落点：「流程」tab 的三分

| 视图 | 回答什么 | 形态 | 默认 |
|---|---|---|---|
| **编排图** | 一件事在这里是怎么被分流的 | 画布（单层 ≤12 节点） | ✓ |
| **单元清单** | 一共有哪些能力单元、各自被谁引用 | 表格（`unit_id` / 目标 / 段型 / 引用数 / 校验态） | — |
| **判定规则** | 什么条件下不许做、必须做什么 | 分组列表（G0 闸门 / 硬规则 / 兜底） | — |

**为什么合并旧的「主流程 / 应答能力 / 示例片段」**：三者本就是同一对象的不同属性——**顺序**（主流程）、**并发**（应答能力）、**例句**（L2 内容）。合并进单元后，"改一次生效 N 处"才成立。

> **但「主流程 ≠ 应答能力」这条判断不取消**（§4.7 八个别再搞混 #6）。它变成单元上的一个字段：`load_mode: routed | concurrent`。**routed 单元画进图；concurrent 单元不进图**——它们不参与分流，进了图只会污染结构。并发单元放在图外的"可并发加载"槽位（右侧栏，按相关性排序、受上限约束）。

**三个视图共用同一个选中态**：在图上点 `U-退款` → 清单行高亮 → 右侧检视器打开；从清单进也一样。**不做三份数据**。

### 2.1 分期：画布晚一期

| 期 | 「流程」tab 交付 | 理由 |
|---|---|---|
| **S2-a（alpha）** | **单元清单 + 判定规则**，无画布 | 清单已能完整表达配置（图只是同一数据的另一种投影），先交付"能配完、能校验、能提交" |
| **S2-b** | **编排图**（含下钻、端口、事件、运行叠加、版本 diff） | 数据模型已被真实配置验证过一轮，画布上马时不必再改结构 |

反着做（先画布后清单）的代价：UI 逻辑会压在画布上，数据模型一改就要改画布——而画布是最贵的组件。

## 3. 四种视图态（同一画布，不同可写性）

| 态 | 数据来源 | 可写 | 画布表现 |
|---|---|---|---|
| **编辑** | 本版本草稿 | ✓ 写草稿 | 端口可拖、边可连、错误高亮、未保存标记 |
| **只读** | 已生效 / 已归档版本 | ✗ | 无 handle，只显示；顶部"从这一版新建草稿" |
| **对比** | 版本 A × 版本 B | ✗ | 新增 / 删除 / 修改 三种描边 + 分段 diff 侧栏 |
| **运行叠加** | 只读版本 + 已聚合的 `RunEvent` | ✗ | 节点角标（进入数 / 停留 / 终止）+ 边流量；**不改布局** |

**对比态的一条硬规矩**：**端口与边的 diff 不能折叠进"节点已修改"**。ElevenLabs 的字段级 diff 只到"字段"，改成端口后必须做到"端口级"——否则"核验节点加了一个 `from_verified` 入口"这种最危险的变化，会被显示成一句"U-核验身份 已修改"。

## 4. 画布交互模型

### 4.1 布局：自动排，位置不是语义

**决定：坐标不持久化**。默认按拓扑层 + `edge_order` 稳定排序，dagre 分层布局。

三条理由：

1. 位置若进版本，**每次 diff 都会被布局噪声淹没**（挪一个节点 = 一片红绿）。
2. 位置若只存本地，**两个人看到的图不一样**，评审时无法指着说"这一步在这里"。
3. 单层 ≤12 节点，**自动布局的质量足够**，不需要人来摆。

代价与让步：允许**会话内拖拽**（切走即重排），用于临时看清楚；**不允许"固定位置"**（RG-F2）。

### 4.2 收起 / 展开与下钻

- **一层一画布**。绝不把父子两层画进同一张图（**不用** React Flow 的 `parentNode` / subflow）——那会让"收起"退化成一个视觉开关，而它本来是个**语义边界**。
- 下钻：双击节点 → 面包屑追加一层 → 画布换成该单元的 body。返回用 `Esc` 或面包屑回点。
- 面包屑形如：`课程咨询顾问 / v12 草稿 / 编排 / U-退款 / n2`，**每级可点**。
- **父层上下文**放在画布左上角的窄条里（父单元名 + 本层 3 条出口端口），避免"我在哪一层"要靠记忆。

### 4.3 端口：唯一能跨层的抓手

| 要素 | 做法 |
|---|---|
| 位置 | 入口在左、出口在右；同侧多端口纵向均分 |
| 标签 | 端口名（`from_verified` / `need_human`），**不缩写**——名字就是契约的一部分 |
| 悬停 | 显示 `requires`（入口）或 `completion`（出口）的字段清单 |
| 条件 | **端口只声明 `requires`（进入前必须就绪的字段），不写 `when`**。「要不要来」在边的 `condition`，「能不能进」在门的 `requires`——两处都能写就会互相矛盾 |
| 连边 | 从外层拖到目标的**端口**才成立；拖到节点主体 = **不允许**（UI 层就拦住，不等保存报错） |
| 超限 | **不按端口数硬限**。告警量的是**本层闭集大小**（出口边指向的去重目标数），阈值随 `routing.mode` 分档，两级提示、不阻断（§10.2） |

### 4.4 边

- 边标签 = 条件摘要（默认一行，点开折叠显示表达式全文）。
- 同一节点的多条出边**按 `edge_order` 编号显示 1/2/3**——顺序即优先级，必须可见。
- **执行环**：虚线 + `max_rounds ×N` 徽标 + 悬停显示 `exit` 去处。
- **裸跨层边**：连边时目标选择器里**不出现**内部节点，只出现本层单元与端口（第 8 条校验前置成 UI 约束）。

### 4.5 边界事件：不画成边

事件不是"从某处到某处"，画成边会让人以为它有固定起点。

**作用域三级**（`scope`）：`self`（只在本单元内触发）· `subtree`（本包子树）· `global`（整个专家版本）。`global` **只能声明在专家版本层**，且 `goto` 只能指向顶层单元或端口——**不能穿进包里**，否则它就是一条隐蔽的跨层边。

两个落点：

- **卡片右上角"事件"角标**：hover 列出该单元声明的 `on_event`。
- **右侧「事件」分区**：全层清单（事件 → 去处 → 作用域），可点跳到目标节点。
- 目标节点左上角一个小旗标记 = "这里有事件落进来"。

### 4.6 运行叠加

三档开关：**关 / 进入数 / 停留与终止**。数据**服务端聚合**后再下发（前端不聚合 `RunEvent`），且**必须标注时间窗与版本**，否则数字会被误读成"这个版本一直如此"。

### 4.7 版本 diff

三类对象各自比对，缺一不可：

| 对象 | 比对内容 |
|---|---|
| 节点 | 增 / 删 / 改（改到哪一段） |
| **端口** | 增 / 删 / `requires`·`completion` 变化 |
| **边** | 增 / 删 / 条件变化 / **`edge_order` 变化** |

`edge_order` 变化要单独标出来——它改的是优先级，diff 里却只表现为"顺序变了"，最容易被审批者略过。

---

### 4.8 `waits`：会停下来的地方必须看得见

`waits` 既不是边（它是「停在这里等」，不是条件跳转），也不是边界事件（不挂任意节点），它是**单元的属性**。但「这里会停 120 秒」是最该被看见的运行事实之一，不能只存不显。

两个落点：

- **节点角标**：`⏱ 等审批 ≤120s`，长等待在角标上直接写时长。
- **超时虚线边**：超时后要去的那条边用虚线 + 时钟标记，与普通条件边区分。

**不新造节点类型**——一旦有「等待节点」，就会有人把等待当步骤编排，节点类型也开始增长。

## 5. 校验与错误定位（九条校验怎么落到界面上）

| 落点 | 内容 |
|---|---|
| **画布** | 出错节点红描边、出错边红虚线、出错端口红点；右上角错误计数徽标 |
| **检视器** | **字段路径 + 一句话 + "定位"按钮**，如 `units[2].entry_ports[1].requires` → "该入口要求的 `user.verified` 未被任何上游写过" |
| **底部校验条** | 按九条校验分组计数；点一组只高亮那一类 |

**阻断策略（借 ElevenLabs 的互锁，但更严一点）**：

| 动作 | 有错时 |
|---|---|
| 保存草稿 | **允许**（中间态合法；否则长流程没法分段编辑） |
| 提交审批 / 试用这一版 | **双禁用**（不是只灰一个） |
| **孤立单元**（无任何边指向、也非入口） | 保存**允许**、**提交阻断**；清单标「未接入」并计入校验 |
| 引用未知 schema（前向兼容） | **只读展示 + 阻止覆盖**（§8.6 已有规则，这里落地） |

> 保存允许、提交阻断，这两条必须成对。只做"保存阻断"会让作者不敢分段保存；只做"提交允许"就等于门禁失效。

## 6. 前端视图模型（画布只吃这一层）

```ts
type UnitRef = { unitId: string; version: number };

type EntryPort = { port: string; requires: string[]; goto?: string };   // 只声明前提，意图在边上
type BoundaryEvent = { event: string; goto: string; scope: 'self' | 'subtree' | 'global' };
type WaitSpec = { on: string; timeoutMs?: number; timeoutTo?: string };
type ExitPort  = { port: string; completion: Completion; exits: UnitRef[] };

type UnitNode = {
  id: string;
  unitRef: UnitRef;
  goal: string;
  loadMode: 'routed' | 'concurrent';       // concurrent 不进图
  entryPorts: EntryPort[];
  exitPorts: ExitPort[];
  events: BoundaryEvent[];
  waits: WaitSpec[];                        // 「停在这里等」：角标 + 超时虚线边
  segments: SegmentBadge[];                 // 段型徽标：locked / mutable 计数
  validation: ValidationIssue[];            // 来自九条校验
};

type GraphEdge = {
  from: string;                             // node id | `${unitId}.${port}`
  to: string;                               // node id | `${unitId}.${port}` | `self.${port}`
  order: number;                            // edge_order，列表位置即优先级
  conditionSummary: string;
  loop?: { maxRounds: number; exit: string };
};

type LevelGraph = {
  owner: string;
  routingMode: 'deterministic' | 'llm' | 'hybrid';   // 逐层必填，阈值与提示语挂它
  nodes: UnitNode[];
  edges: GraphEdge[];
  fallback?: UnitRef;
};
```

**关键约束**：画布**只加载当前一层**（契约层 + 一层的 body 概要），不递归拉取子树。子层内容进下钻时才取。这是"分形不撑爆上下文"在前端的对应做法。

## 8. 无障碍与键盘（不是加分项）

- 节点是 DOM，**Tab 可达**：`Enter` 下钻、`Esc` 返回、`↑↓` 在出边间移动。
- **边不可聚焦** → 因此**必须**有"清单投影"作为等价路径：键盘用户从清单能看到全部条件与优先级。这是三视图并存的一个真实理由，不只是审美。
- 增 / 删 / 改**不能只靠颜色**：配图标或文字，颜色是第三重线索。

> ElevenLabs 的三档测试、四类护栏都很完整，但整份语料对键盘与屏幕阅读器**零提及**——这一点上不必参考它。

## 9. 不做什么

| 不做 | 原因 |
|---|---|
| **不用 `parentNode` / subflow 把两层画进一张图** | "收起"是语义边界，不是视觉开关 |
| **不持久化坐标** | 位置进版本会淹没 diff；只存本地会让两人看到不同的图 |
| **不画边界事件为边** | 它没有固定起点，画成边就变成"只有这一条路能触发" |
| **不做画布级 undo** | 撤销单位是草稿快照，跨 tab 跨页面 |
| **不允许在画布上写提示全文** | 画布只到契约层；改内容进单元工作面（段型决定门禁） |
| **不做自由连线**（拖到节点主体也能连） | 会绕过端口，第 8 条校验当场失效 |
| **不引入 xyflow Pro 示例** | 只锁 MIT 运行时依赖 |

| **RG-F1**（=RG-8） | 应答能力（并发加载）怎么安放 | **同一对象 + 开关**：契约层加 `load_mode: routed \| concurrent`；concurrent **不进图**，放图外托盘，带「加载范围」与并发上限；**不允许 both**。理由：同一对象才能"改一次生效 N 处"，一个开关才能分清"被选中"（路由）与"被召回"（相关性） |

| **RG-F4** | 端口超限怎么处置 | **不挡发布、只做软提示**；且**量的是闭集大小而非端口数**，阈值随 `routing.mode` 分档（§10.2）。三种路由方式的风险不同：规则路由死板、模型路由难准 |

| **RG-F6** | 编辑器是否前置"这张图是否必要" | **非阻断提示 + 忽略留痕**。提示**给事实不给判断**："这 4 个分支的 `tool_scope` 与 `knowledge_view` 完全相同，目前只有提示词差异" |

### 10.1 为什么量"闭集"，不量"端口"

端口多只是表象。模型在某层要做的事是**从候选里挑一个去当下一步**——候选集合就是本层的**闭集**（所有出口边指向的目标去重）。

- 一个单元 3 个出口端口、各指向 2 个单元 → 闭集 6
- 一个单元 2 个出口端口、都指向同一批 → 闭集仍可能是 5

**只量端口会漏报**第一种情况，也会误报第二种。所以度量 = **闭集大小 + 边条数**，端口数只在卡片上顺带显示。

### 10.2 阈值随 `routing.mode` 分档

`routing.mode` 逐层必填、默认 `hybrid`、**不可从条件推断**（推断规则本身就是隐式语义）。

| `routing.mode` | 谁在选 | 闭集变大意味着 | 提示阈值 | 提示语该说什么 |
|---|---|---|---|---|
| `deterministic` | 表达式 + `edge_order` | 准确性几乎不受影响，但**条件要人工保证互斥 / 穷尽** | 闭集 > 8 | "分支已多，确认条件互斥与兜底仍可读" |
| `llm` | 模型在闭集里选 | **选择准确率随闭集增大而下降**（主要风险） | > 5 提示 · > 8 强提示 | "本层由模型选择，N 个候选已超出稳定区间" |
| `hybrid`（默认） | 先确定性筛，再模型选 | 取决于筛完剩几个 | 筛后 > 5 | "筛后仍有 N 个候选"，并显示筛前筛后两组数 |

**两级提示，都不阻断保存与发布**（用户明确要求）。但提示必须**同时给替代**，否则等于只报错不给出路：

1. 合并入口（两个门背后前置条件几乎相同）
2. 拆包（入口职责确实不同）
3. 把本层改成 `deterministic`（分支确定、只是多）
4. 两段式：先分大类，再在类内选（每段闭集都小）

忽略要有留痕（谁忽略、当时的闭集数），并进评审摘要——与 RG-F6 用同一套机制。
