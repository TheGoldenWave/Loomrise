## 1. 来源与借鉴边界

EvoOntology 是面向 **Data Agent** 的自进化本体层：把异构表、文件、库上的业务语义抽成版本化的 Ontology Layer，经 MCP 按需暴露，再按「诊断 → 归因 → 补丁 → Parent/Candidate 门控评估 → 发布」循环演进。

| 维度 | EvoOntology | Loomrise |
|---|---|---|
| 语义对象 | 表、字段、指标口径、映射、约束（数据语义） | 话术、示例、执行策略、硬规则、工具策略（业务语义） |
| 真值来源 | benchmark Ground Truth | 人工审定的业务真值（黄金集） |
| 门控裁决 | 系统自动 Accept 并发布 `vN+1` | **人工审批**；系统只汇总证据 |
| 循环节奏 | 固定 benchmark 或持续轨迹流 | 低流量场景包，改进按需发起 |

**判断：机制可抄，语义模型与发布权不可抄。** 它的自动 Accept 直接撞 S2 不做清单第 5 条（不自动发布），LLM Judge 当 Gate 撞第 24 条（提名信号不含模型自评）。以下四条是在不违反既有决策的前提下可以吸收的部分。

## 2. 决策一（已确认）：Gate Reserve——发布用样本不回流诊断与补丁

它的 `fixed_split` 模式把数据切成 Construction Pool（构建/诊断可用）与 Validation Reserve（**只用于最终 Gate，不能回流到构建、诊断或补丁生成**）。

Loomrise 已有 `golden` / `pending` / `blind` 三层，但缺一条硬规矩：同一批案例可以无限次进入调参循环。50+ 例的规模下，反复回放会把候选「调」到这批案例上，通过率不再代表泛化能力。

### 两个池子的职责分离（已确认）

| 池子 | 由谁组成 | 使用方式 | 回答的问题 |
|---|---|---|---|
| **回归池** | `golden` + `pending` | 每次候选必跑，可反复用 | 有没有退步 |
| **Gate Reserve** | `blind` 的一批抽样 | 只在最终 Gate 跑一次，用过即归档 | 改善是不是真的 |

由此产生一条**零成本的硬规矩**，它比「切 reserve」更关键：

> **`golden` 上的通过率只作为「不退步」的证据，不得作为「改善」的证据。** 审批页上这两栏必须分开显示，改善只能由 Reserve（与关键回归之外的泛化证据）支撑。

这条直接掐掉过拟合的主路径：既然 golden 不负责证明改善，把 golden 调到 100% 也就不能用来论证「变好了」。

### Reserve 从哪儿划：已定方案 B（blind 批次）

| 方案 | 做法 | 代价 | 结论 |
|---|---|---|---|
| **A. 从 `golden` 切 20%**（约 10 例）标 `gate_only` | 判定强，能证明业务语义真的改善 | golden 只剩约 40 例做关键回归，哨兵变少；这 10 例 Gate 跑完即「见过」，需补 10 例**人工审定**新案例才能继续，补新速度直接卡住发布节奏 | 不采用 |
| **B. 从 `blind` 划一批** | 便宜、可持续补、天然新鲜，测的是泛化 | 判定弱：多数 blind 只做确定性裁决（越权、重复写入、结果缺失），话术与澄清顺序的改善看不出来 | **采用** |

选定 B 的理由：EvoOntology 切 GT 的 20% 是因为它有上千条 benchmark 真值，切得起；Loomrise 的 golden 只有 50+ 例且每例人工审定，是最稀缺的资源，不该拿它去干 blind 也能干的事。而 blind 的「新鲜、可持续」正是固定 benchmark 环境没有的资源。

**方案 B 已知的弱点与缓解**（接受 B 即接受这套缓解，不另设补救机制）：一是 blind 的业务语义抽检比例（已定不低于 20%）按需上调，给 Gate 供业务信号；二是改善的最终判断权仍在人工审批，Reserve 只负责挡住「把调参得到的通过率当成改善」。

### 具体规则（随方案 B 一并确认）

1. **`blind` 按批次消费**：每批盲测集只服务一次发布 Gate，用过即标记 `consumed` 并归档，下一批重新抽样（承接 S2 待定项「盲测集抽样方法」）。诊断、归因、候选生成、迭代回放一律不得引用未消费的当前批次。
2. **`golden` 不做批次消费，保留全部 50+ 例做关键回归**，但按上文规矩：它的结论只判不退步。
3. **Reserve 的表现差不构成修改案例的理由**：不得因为候选在 reserve 上失败就回填真值、把案例移出 reserve 或降级为 pending。真值修正仍只允许源于业务判断变化或当初标注错误（范围记录第 16 条）。
4. **批次消耗后强制补新**：Gate 用掉一批 blind，就要抽一批新的补齐，否则下一轮 Gate 无独立样本。抽样是系统可做、成本低的动作；涉及人工真值的部分由人承担。
5. **若某个场景的 blind 供给不足**（低流量场景包的现实情况），允许临时改用方案 A：从 `golden` 划一次 `gate_only` 切片，但必须显式记录理由与回补计划，且不得成为常态。

> 与范围记录第 15/16 条的关系：三层样本的用途不变，新增的是**用途标记 `usage`** 这一维度（可诊断 / 仅 Gate）、**批次消费**规则，以及**「golden 只判不退步」**这条结论边界。不改变「黄金集只用于一票否决与关键回归」的定位。

## 3. 建议二：Parent/Candidate 同条件配对评估

它的门控要求 Candidate 与 Parent 在**相同数据、相同 Agent、相同解码配置、相同交互预算**下比较，且「可复现地优于」才发布。Loomrise 流程 C 已有「旧版与候选版配对批量回放」，但没钉死「同条件」与「可复现」。

**建议在 `EvalResult`（或新增 `EvalRun`）上冻结四元组并写入报告：**

| 冻结项 | 内容 | 为什么必须冻结 |
|---|---|---|
| 数据 | 案例集版本 + 批次号（含 reserve 批号） | 否则历史结论不可比 |
| Agent | 模型与版本、解码配置、`AgentVersion` | 换模型跑出来的差异不能算候选的功劳 |
| 环境 | 资料版本、工具模拟版本、档位版本 | 已有 `case_set_version` / `policy_profile_version` / `threshold_snapshot`，补齐资料与工具版本 |
| 预算 | 轮次上限、上下文预算、超时 | 靠更多轮次或更大预算换来的改善不算改善 |

**判定顺序不变**（一票否决 → 确定性裁决 → 关键回归不退步 → 目标维度改善），新增两条：

- **可复现性**：同一 Parent/Candidate 在冻结四元组下重跑，结论一致；不一致则本次评估作废，不进入审批。
- **归因标注**：每个改善或退步案例标注归因层（路由 / Skill / 工具 / 硬规则 / 片段 / 资料），一个 Candidate 只验证一个主要假设，与范围记录第 13 条「按共同原因归并」对齐。

审批页的证据链因此从「改了什么」升级为「在同一批样本、同一环境下确实更好」。

## 4. 建议三：改进 run 的预算与状态机

它把一次改进循环做成有预算、有终态的 `EvolutionSession`。Loomrise 的审批流目前没有「预算」与「终态」，容易变成无休止修修补补。

**关键映射差异**：它的 Accept 直接发布；Loomrise 的 Accept 只等于「生成候选版本并送人工审批」，**批准后才推进 checkpoint**。发布权始终在人。

```text
                 ┌──────────────── 人工驳回 ────────────────┐
                 ▼                                          │
running ──Reject──▶ running（同一 run 内设计下一个 Candidate，消耗一轮预算）
   │
   ├──Candidate 通过门控──▶ proposed（生成 ChangeProposal 送审）
   │                            └── 人工批准 ──▶ closed + 推进 checkpoint（发布）
   ├──预算耗尽──▶ exhausted（关闭留档，坏例回池，不发布）
   └──数据缺失 / 评估不可靠 / 外部阻断──▶ blocked（判断性停止）
```

新增对象 `ImprovementRun`：

| 字段 | 说明 | 默认值建议 |
|---|---|---|
| `id` / `target_cases` | 本次 run 要解决的已确认坏例，**开始时冻结** | — |
| `budget` | Candidate 轮数上限，确认后冻结；加轮需再次确认 | 8 |
| `rejects_count` | 已正式 Reject 的 Candidate 数 | — |
| `min_rejects_before_blocked` | 判断性停止前的最少正式 Reject 数 | 2 |
| `status` | `running` / `proposed` / `exhausted` / `blocked` / `closed` | — |
| `checkpoint_ref` | 起始基线（已发布版本 + 案例集批次） | 当前生效版本 |

两条可抄的细节：**Reject 不是终止，是下一轮的输入**（写轮次摘要与归因，继续搜）；**判断性停止必须先有 ≥2 次正式 Reject**，避免一句「评估不可靠」就把 run 关掉。

**触发阈值做成一等状态**：它的默认触发是「checkpoint 后新增 ≥30 个任务或 ≥7 天」。Loomrise 是低流量场景包，30 个坏例可能长期不达标，因此建议——阈值按场景登记（**默认建议：≥10 个已确认坏例 或 ≥14 天**），且**人工可随时发起 run**，系统只做提醒不自动开 run（与「不自动切换、不自动发布」一致）。

## 5. 建议四（附带）：轨迹粒度与证据阻断收口

两条小改动，都属于把既有约束收口，不引入新概念：

1. **`RunEvent` 按 Tool Call 粒度落盘，不写思维链。** 它明确「轨迹以 Tool Call 粒度写入，不存思维链」。Loomrise 的 `RunEvent` 已是事件账本，但需明确：模型中间推理默认不入库；需要时走开发者模式且产物不出本机。成本、隐私、可复现三者都更干净。
2. **「无证据」升级为确定性阻断。** 它把 Evidence 做成必须挂可复现证据的一等对象。Loomrise 摄入侧已有硬约束（`source_ref` + 权利范围 + 有效期 + 撤销入口），但它是「摄入时要求」，不是「提交时阻断」。建议把它并入范围记录第 6 条：缺 `source_ref`、缺权利范围或已过有效期的条目，在**候选提交校验时确定性阻断**，而不是留到审批页靠人眼发现。

## 6. 明确不采用

| 它的机制 | 不采用的理由 |
|---|---|
| 系统自动 Accept 并发布 `vN+1` | 撞 S2 不做清单第 5 条（不自动发布）与「放宽方向必须人工」 |
| LLM Judge 作为无 GT 时的 Gate | 撞第 24 条（提名信号不含模型自评）与「不由模型独自裁定业务真值」；最多作为人工审批前的**排序建议** |
| 五类语义对象（Term / Mapping / Relation / Constraint / Evidence）与 Schema 层 | 那是数据语义的组织方式，与 Loomrise 六层配置不同源；照搬会引入一套平行概念 |
| `rolling_trajectory` 的自动轨迹积累与自动 checkpoint | Loomrise 场景流量低，自动节奏不触发；改进入口必须保留人工发起 |
| 它的 MCP 只读/按需检索（`browse_semantics` / `resolve_semantics` + session manifest） | **方向可借鉴**，但已由 ExampleSnippet 召回（标签过滤 → 语义排序 → 取前 N）承担，不另起一套；S2 验收第 16 条已覆盖召回路径 |

## 8. 建议新增的验收项

在 [S2 设计草案](S2-DESIGN.md) 现有 16 条之后追加：

17. **Reserve 不回流，且 golden 不充当改善证据**：诊断、归因与候选迭代过程中不出现当前未消费的 `gate_only` 批次；Gate 用后标记 `consumed` 并强制补抽新批次；不存在因 reserve 表现差而修改或移出案例的记录；审批页把「不退步（golden）」与「有改善（Reserve）」分两栏显示，golden 通过率不得作为改善证据。
18. **配对评估可复现**：同一 Parent/Candidate 在冻结四元组下重跑结论一致；评估报告写明案例集版本与批次、模型与解码配置、资料与工具版本、轮次与预算；不一致时本次评估作废。
19. **改进 run 有预算与终态**：一次 run 的 Candidate 轮数不超过已确认预算；判断性停止需先有 ≥2 次正式 Reject；`exhausted` / `blocked` 均留档且坏例可追溯回池。
