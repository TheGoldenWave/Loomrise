## 定位

**一句话**：Loomrise 是一个面向**客服、销售**的开源 Agent 交付平台，提供配置与验收工作台、完整网页客服应用和统一业务执行服务；帮助团队把授权资料与流程做成可办理业务、可验收、可持续改进的 Agent，通过统一 Task 体系管理跨会话服务义务，以独立模块治理用户记忆、画像与上下文，并支持快捷部署到用户自己的云。完整产品仍待建设。

**「开源」是承诺，不只是措辞**：Loomrise **真的开源**，采用 **`Apache-2.0`**（完整原文见仓库根目录 `LICENSE`，署名见 `NOTICE`）。核心开源；未来若出现确需商业化的**独立模块**，**另建仓库**按其自有许可发布，现有开源核心不改协议。公开仓库只发布可脱离个人语境独立理解的结论，分类与晋升规则、选型理由与协议排序见[开源与私有工作区边界](OPEN-SOURCE-BOUNDARY.md) §开源协议。

### 完整网页客服应用与增强能力（方向已确认，规划未实现）

以 [Knocket 的官方客服能力](https://knocket.trtc.io/tutorials/add-ai-assistant-to-website/)作为网页客服覆盖基线，Loomrise 官方提供可直接部署的客服应用。覆盖按功能与运行验收定义，不沿用对方的账户配额、界面或私有协议；具体基线见[建设方案](CUSTOMER-SERVICE-DELIVERY-PLAN.md)。

| 能力域 | 规划覆盖 |
|---|---|
| AI 接待与连接 | 名称、头像、欢迎语、接待入口与时段、Prompt、BYOK、模型与地址、连接测试、配置旁试用 |
| 知识答疑 | FAQ、URL、文件摄入、解析与索引、同步/失败状态、可引用知识、更新与撤回；保留 CLI 接入 |
| Web Widget | 外观与语言、欢迎页、在线时间、访客字段与必填校验、历史消息、FAQ/预约/社交外链、安装代码及检测 |
| 人工 Inbox | 会话队列与筛选、访客资料、人工回复、图片/视频/文档发送、转人工与恢复、摘要和回复辅助、一线反馈 |
| Contact Page | 模板、编辑与 AI 辅助生成、预览、草稿、发布、分享与停用 |

在此基础上增加 Loomrise 的**业务办理、验收与持续改进**：在授权与确认后调用业务工具、保存实际结果；冻结配置/知识/工具版本进行案例回放；由运行证据形成改动提案，经独立评测和人工审批发布，并可回滚。权限、幂等、取消、预算与结果证据从最小客服闭环起进入内核，完整产品流程在 S2-c 验收。

Knocket 标为规划的 WhatsApp、Instagram、Messenger、Facebook 不算已提供能力；TRTC Voice Agent 属于另一产品。Loomrise 网页语音是自己的应用能力，按独立媒体 Gate 验收。对标不构成对方所有功能已实测或本项目已兼容的声明。

### 独立物料库与文件交付（方向已确认，后端规划未实现）

业务通过独立物料库录入常发图片、视频与文档，维护名称、简介/用途、标签、来源授权、有效期及可用专家/环节。知识资料负责事实答疑，物料负责文件交付；经审阅的简介/标签可以帮助 Agent 检索定位物料，摘要不会自动变成业务事实。初始化先完成资料答疑，物料按需补充。

原件、压缩/封面等派生文件、内容理解候选、人工审阅和索引状态分别管理。真实后处理规划支持图片/视频压缩及 OCR、转写或多模态理解；不丢原件，生成简介需业务审阅后使用。人工可直接写简介、选择原件或可用派生版本；Agent 自动发送默认关闭，必须同时满足物料授权、专家发送策略、当前 AI 会话占用、请求/适用条件、数量与渠道限制。正式发送使用批准版本并在执行前重验，撤回、过期、范围、版本或占用代次变化均使旧选择失效。

发送保存文件/简介快照和回执关联，不等同于已送达或问题解决。本轮前端只扩展 IndexedDB 原件缓存、本地简介筛选及人工/Agent 隔离发送仿真；压缩、理解候选为明确演示，真实处理、检索和外部发送尚未接入。需求和阶段 Gate 见[物料库与文件发送](MATERIAL-LIBRARY-AND-DELIVERY.md)，实际验证见[前端报告](S2-FRONTEND-ROUND2.md)。

### 统一 Task 与用户上下文（方向已确认，规划未实现）

客服与销售既要回答当前问题，也要管理未来服务义务。运营预配置策略、会话中 Agent 提出的 TODO、业务事件和人工安排进入同一任务体系；持久事项暂称 `TaskItem`，不覆盖 `ServiceRequest` 或上游计划对象。Task 管来源、计划、负责人、停止与协同，执行及业务结果仍由统一内核留证。主动触达是获授权任务的一种方式，内部核查、等待结果和提醒人工也能进入体系。

默认任务和主动触达策略是专家配置的一部分，建议置于 `AgentSpec.task_blueprints`，与该专家的 Skill、工具、规则和结果要求共同冻结进 AgentVersion、评测、发布及回滚，**不做跨智能体共享策略库**。确定主体的服务周期初始化时，按批准规则幂等登记适用的低风险内部事项；触达先形成候选，再经采用和执行前许可检查，不因重复会话或版本升级重建清单。

Agent 可在运营批准的范围内建议或调整单个事项的时间、步骤与处理方式，保护人工锁定安排；改变蓝图、触达许可/次数、价格承诺、硬规则或发布权必须形成专家候选版本并评测审批。在途任务保留来源/执行版本，升级需明确迁移或继续/暂停决定，回滚不复活取消、退订或重置联系计数。创建 TODO 不自动授权对外联系，原事项可靠阻断后才激活替代。电话仍按 S4 独立授权试点验收。具体合同与状态见[Task 设计](TASK-SYSTEM-DESIGN.md)。

工具面按领域语义保持精简：系统先装配有界任务摘要，按需展开必要事实、蓝图/Skill、工具 Schema 与证据，通过受限任务意图操作完成提出/调整/请求取消；不把每个 CRUD 拆成工具，也不提供万能执行入口。渐进披露贯穿在线 Agent、外部创作和后台 Harness，但三类角色权限隔离，发现能力不授予生产写入权。

独立用户上下文模块共享主体、来源、用途、有效期与撤销治理：记忆保存有依据的陈述/经历，画像是当前有效信息的派生视图，上下文是本次实际加载快照；事项/授权/业务结果仍分别由其权威掌握。系统业务事实不由模型推断覆盖，资料与个人记忆不自动互转。更正、forget与迟到/备份恢复要影响检索、派生视图及关联任务检查。职责与 Provider 对照见[用户上下文设计](USER-CONTEXT-DESIGN.md)。

先补稳定业务用户身份、事件 envelope、严格时间和持久化合同，再验证内部 TODO/只读记忆切片、受限调度与主动服务沙盒。[联合计划](TASK-MEMORY-INTEGRATION-PLAN.md)管理整体依赖，[首片实施计划](superpowers/plans/2026-10-16-expert-task-harness.md)先验蓝图、幂等初始化、受限决策和工作集，不依赖完整记忆或真实渠道。本轮没有实现这些服务，不把现有本地前端或 S1 历史验收计为通过。初次手动/助手创建仍先做授权资料答疑，不要求先配置画像或主动策略。

### 垂类口径：锚定「客服」「销售」两类业务场景，不锚定行业

Loomrise **不做通用角色智能体**（不是通用助手，也不是开放式问答），同时**不锚定具体行业**。锚定的对象是**跨行业的业务职能场景**：**客服**与**销售**。

- **选职能，不选行业**：教育、汽车、保险、医美的客服与销售都能落在同一套结构里。行业拓展不受限，场景包生态不会被圈小。
- **两个场景共享同一执行内核与六层配置**，差异落在场景包与 `AgentSpec`，不落在架构。
- 现有两个虚构验证载体**已经落在这两个场景内**（成人在线课程咨询 + 模拟试听预约 = 销售与预约；虚构二手车预约 = 销售与预约），无需改动。

**准入条件**（两个场景**内部**的筛选，须同时满足）：

| # | 条件 | 为什么它是准入条件 |
|---|---|---|
| 1 | 有**预先定义、可留证的任务结果与验收标准**：受授权资料约束的答疑、人工承接，或工单/预约/订单等业务结果 | 答疑无需制造业务写入；按事实、引用、范围及未解决升级验收。答复生成、送达与问题解决分别记录；有副作用的业务办理必须保存实际结果及适用的外部结果 ID |
| 2 | 业务资料**可获授权**，带 `source_ref`、权利范围、有效期与撤销入口 | 缺任一项的资料不得进入 `ContextSnapshot`（硬约束，见[产品形态与开放接入规范](PRODUCT-FORM-AND-INTEGRATION.md)） |
| 3 | 关键约束**可确定性裁决**（身份、权限、金额、时段、频次、去重） | 只有确定性条件才能进模型外 `HardRule` 与发布门禁；只能靠语义判断的约束归 Skill / 表达层，见[硬规则表达模型](HARD-RULE-MODEL.md) §5.3 |

**合规排除**：保险、牙科、医美等只处理经确认的一般信息与预约转接，**不做诊断、疗效、收益或价格承诺**。不做通用 CRM、批量营销外呼、未授权数据摄入。

### 交互模态：文字与语音并列一等

| 模态 | 地位与阶段 |
|---|---|
| **网页文字** | **一等入口**。S1 已实现 |
| **网页语音** | **一等入口**。S1 已有最小链路（浏览器 Web Speech + 浏览器合成，**非云端 ASR/TTS**），真实音频可懂度、首响、打断恢复**未验收**。与网页文字共享同一 `ServiceRequest`、权限、版本与业务结果 |
| 结构化组件（表单 / 对比表 / 确认卡片 / 结果摘要） | 由**受约束组件**生成，**不执行模型产出的 HTML 或脚本**。它是承载面，与模态不同层 |
| 消息桥接与 IM 渠道 | Telegram/邮箱列入 S2-b 的授权沙盒验收；其他 IM 逐类进入 S4，供应商与兼容性独立验证 |
| 电话呼入 / 呼出 | S4 **独立授权试点**。**不是网页语音的一个开关**——触达授权与适用规则、号码/时段限制、回执乱序与去重、录音与数据保留、人工接管与撤销均须独立验证 |

**两根独立的轴，不要混**：

- **模态轴**：文字 / 语音 / IM / 电话。
- **发起模式轴**：**被动响应**（用户发起；S1 范围）与**主动触达**（`OutreachPolicy`：触发条件、优先级、冷却、授权、去重、停止条件、发送回执；S1 只保留边界，不实现调度）。批量营销外呼不是首版目标。
- **AG-UI / SSE 是投影协议，不是面向用户的模态。**

### 使用者分层：工作台与客服应用

角色分工已确认；官方客服应用为新增规划，现有工作台原型不代表该应用已实现：

| 角色 | 使用界面 | 做什么 |
|---|---|---|
| **AI 产品 / 产研、解决方案人员** | 交付工作台 | 搭建场景、提供工具与数据源、接入业务、验收与部署 |
| **策略运营** | 交付工作台 | 对 Agent 效果负责：人评、标注、运行与成本分析、改动提案、审批与回滚；工作台中的“运营”仍指策略运营 |
| **一线客服 / 销售** | 官方客服应用的 Inbox，或已接入的业务应用 | 实时回复、人工接管与一线反馈；依据角色权限操作，不因此获得配置和发布权 |
| **访客 / 最终客户** | Widget、Contact Page、移动端入口或已接入渠道 | 咨询、提交信息、确认业务动作、查看结果与请求人工服务 |

#### 三种「人工」不要混

本节最容易做错的地方：三种人工介入**做的不是同一件事，产物也不是同一样东西**。

| # | 形态 | 谁做 | 在哪 | 时效 | 产物 / 回流 |
|---|---|---|---|---|---|
| **A** | **人评与标注**——对 Agent 回复内容的持续修正 | **策略运营** | 交付工作台 | 异步、持续 | 校对后的真值（→ **验收域 · 案例标注**）、软质量人评与被修正的内容（→ **验收域 · 人评与修正**），以及由此产生的改动提案 |
| **B** | **人工实时接管**——转人工后由人实时回复 | 一线客服 / 销售 | 官方客服应用或已接入业务应用 | **实时** | 接管、承接、回复与释放事实回流，供运行审计与归因使用 |
| **C** | **一线坏例反馈**——标记「这条答错了」 | 一线客服 / 销售 | 官方客服应用或已接入业务应用 | 异步 | 回流为**提名**（`CaseNomination`），**不等于真值** |

一条分界线：**C 只是提名，A 才是判定。** 一线的点踩 / 标记说明"这里有疑问"，但真值必须由策略运营在 Loomrise 里标注——这与既定的「案例标注只填业务真值、不填配置归因」是同一条原则。**B 与 A / C 都不同**：它是实时应答，不是评价。

**四条推论，都落到设计上**：

1. **Loomrise 官方提供一线客服操作面，交付工作台保留配置与治理职责**——实时接管、人工回复和反馈位于客服应用；策略运营的人评与标注位于工作台。二者可同一部署，仍按角色与权限区分。
2. **B 与 C 都必须回流为 `RunEvent`**——归因分层（合理静默 / **人工抢答** / 业务禁回 / 路由失败 / 工程失败）要求：即使操作在业务应用侧，人工接管与一线反馈也必须经**同一 `ServiceRequest` / `RunEvent`** 回流。否则数据看板会把"人工已经答了"误读成"路由失败"，优化方向被带偏。
3. **A 的页面归属已确定，真实业务流程尚未实现**——A 的两类产物各有其页，都在**验收域**：**确定性真值**落**「案例标注」**（填期望状态 / 必须做 / 禁止做，进 `EvalSet`，服务发布门禁）；**软质量人评 + 修正后的内容**落**「人评与修正」**（2026-10-12 决定独立成页，见 [S2-IA-NAV](S2-IA-NAV.md) §4.2 ③ / §6.4-39）。二者**性质不同、禁止合并**：判"对不对"去案例标注，评"好不好、怎么改"去人评与修正。内容所有权与权限细节仍见[配置化后台启动方案](S2-CONSOLE-KICKOFF.md) §4.3 Q4。
4. **Loomrise 提供扩展点，不为单个业务定制功能**——二次开发的载体是工具、数据源与适配器，不是一个可任意改写的定制后台（见[产品形态与开放接入规范](PRODUCT-FORM-AND-INTEGRATION.md) 的接入分类与最小规范）。

（`README` 早期版本的"业务 PM／运营"是一处含糊表述，已按角色拆开并把「运营」统一为**策略运营**；「开源」用词已确认保留，不再作为待确认项。）

## 用户与价值主张

核心使用者是希望把 Agent 能力做成真实交付物的 **AI 产品经理、解决方案人员和小团队开发者**。他们需要把一个业务问题转换成可运行、可解释、可验收的应用，而不是只得到一段 Prompt、画布或无法交接的 Demo。

**策略运营**与**AI 产品 / 产研**共同使用和验收交付工作台；一线客服使用官方客服应用或已接入的业务应用。人工接管与坏例提名经关联的 `ServiceRequest/RunEvent` 回流，策略运营复核后才能成为评测真值或改动依据。

> 从一份获授权的业务资料开始，交付“场景包 → AgentSpec → 文字/语音试用 → 真实业务请求 → 可解释运行记录 → 坏例诊断 → 受控改动 → 回放验证 → 人工发布/回滚 → 可导出交付包”。

核心优势不是接最多模型、画布节点最多或能生成一个通用聊天壳，而是**更快得到完整场景、业务动作真实可见、每次改动有证据、交付物可以迁移**。

对外措辞上，Loomrise 交付的是可验收、可回滚的业务 Agent 版本，不是「数字员工」式的人设角色；这条链路做的是岗位定义、培训材料、质检与上岗审批，而不是让 Agent 更像人。是否把「数字员工」用作面向业务方的通俗类比仍待确认，论证与待决策项见[初始化与摄入通道](INTAKE-AND-INITIALIZATION.md)。

## 最终产品形态与双路径

已确认采用**交付工作台 + 官方网页客服应用 + 统一执行内核 + 分类适配器**，首版以单 Agent、单租户实例为交付目标。工作台聚合“场景、接入、试用、验收、发布”；客服应用提供 Widget、Contact Page 与 Inbox，也允许接入用户已有应用。各入口共用已发布的 `AgentVersion`、关联的 `ServiceRequest` 与结果；一段会话可以关联多个业务请求，不另外创造业务编排权威。

S2-a/b 的入口只绑定已冻结、通过最小来源/权限/固定样例检查并经人工批准的沙盒版本，明确显示测试环境，不能引用可变草稿，业务写入工具仍用模拟实现。此最小试用发布不替代 S2-c 的完整评测、提案审批、发布与回滚；授权测试所需外部地址或渠道回调不构成 S3 的真实用户公网发行验收。

- **先试用客服**：使用自己的获授权资料和有效模型连接，先验证资料内答疑、资料外处理与转人工，再接业务工具。虚构示例与脚本模拟为可选体验，不要求先完成模拟预约，也不以模拟结果证明真实答疑质量。
- **再接业务工具与入口**：在已有资料授权和来源检查上，扩充外部信息源、渠道与自定义工具，做映射、沙盒测试和就绪检查，再发布真实业务版本。新增资料仍需授权，接入不把生产凭据或客户数据带进示例包。
- **持续验收**：坏例、版本 Diff 与固定测评集的旧版/候选版批量回放在同一工作台呈现。硬规则违规阻断；机评只评软质量并由人工校准，发布须人工审批和可回滚。

S1 先把线上 Agent 配置中最有迁移价值的结构抽象为六层：上下文快照、任务路由、Skill/SOP、模型外硬规则、工具策略和业务结果。六层职责与最小字段见[六层配置合同](CONFIGURATION-LAYERS.md)。这样可以验证“当前阶段 → 唯一下一步 → 工具确认 → 可核验结果”的被动响应闭环。上下文采用渐进式加载：常驻基线、当前任务/Skill、按需知识与工具结果分层进入模型；加载策略是横切执行机制，不新增第七层配置。主动触达的条件、频控和停止策略不在 S1 执行，只作为后续 `OutreachPolicy` 接入同一任务与事件体系的边界。

## 首个完整场景

首个完整应用为**网页客服应用**，以下黄金路径采用其中的**虚构成人在线职业技能课程咨询场景包**。这是目标体验，S1 只实现最小纵向切片：

1. 用户选择“课程咨询 + 模拟试听预约”场景包，替换或补充有权使用的课程资料、服务边界、预约字段和人工转接条件。
2. 系统生成可审阅的 `AgentSpec` 草稿，以及规则、Skill、知识和工具权限的版本化配置。
3. 用户在网页文字或网页语音入口完成咨询；两类入口调用同一业务服务、任务状态、工具权限和结果落库逻辑。
4. 系统根据条件比较课程、询问缺失信息、展示待确认动作，并在用户确认后创建可追踪的**模拟预约**结果。
5. 用户把一次失败或资料缺失标记为坏例；系统展示来源运行、预期与实际结果，并提出作用域受控的 `ChangeProposal`。
6. 使用固定样本与硬规则回放旧版和候选版；验收结果由独立规则和人工复核确认，用户批准、灰度或拒绝，并可恢复旧版本。
7. 配置、模拟数据、评测与依赖清单可导出到干净实例重新运行。真实密钥与真实客户数据不进入导出包。

`Case` 的人工审定 ground truth 应记录预期状态、必须/禁止的动作、持久副作用与结果 ID，而非只规定标准话术；固定的 `EvalSet` 必须区分开发、验证和盲测，旧版与候选版使用同一模拟环境回放。S1 建立少量正反例与单次回放样例，并记录上下文加载是否遗漏、冗余或超预算；S2 将批量回放、独立裁决及人工审批变为候选发布的必要门禁。离线通过不等于真实渠道已验证。

第二模板为**虚构二手车预约**，重点不是增加功能，而是验证只替换场景配置、字段、资料和少量组件后，核心运行、追踪、评测与发布流程仍能复用。

## 用户体验原则

前端轮次说明（2026-10-14）：[第二轮前端交付与评审](S2-FRONTEND-ROUND2.md)已落实完整人工配置与渐进式下探的本地交互。协助面板仅预留用户自带 Agent 的任务/候选审阅，本轮不做平台内 Worker；MCP/Skills、真实模型与后台服务仍按原计划验收，前端模拟不构成实现这些服务。

第三方 Agent 接入补充（2026-10-14，方向与高优先级排期已确认、未实现）：统一应用服务／API、MCP + 配套 Skills 与可选 CLI 共用配置、来源、版本和权限合同，先支持外部 Agent 创建受限客服草稿及候选建议，再接失败诊断与受控改进。通用 harness 可作为后台创建／改进 Worker 的可替换 Provider；在线客服保持有限业务执行，验收、批准与发布由 Loomrise 和获授权的人掌握。初次用户不必选择框架或安装外部 Agent，完整手动路径仍独立可用。任务与验收见[第三方 Agent 接入开发计划](AGENT-INTEGRATION-PLAN.md)。

配置体验补充（2026-10-14，原则已确认、未实现）：**初始化助手是可选辅助流程，用户可完全手动创建和配置**。首个成果是用自己的授权资料试用客服，再逐步接通业务工具。业务概览、日常配置与完整详细视图共用同一草稿/版本；助手负责整理与候选建议，人工保有控制权。资料授权、业务承诺、工具权限、验收真值与发布不能由助手代为批准。具体布局和需求分期为提案，见[配置后台体验优化](CONFIGURATION-UX-OPTIMIZATION.md)。

- 首屏先展示场景、示例结果和费用影响，不让第一次使用的人面对完整 Agent 框架概念。
- 用户始终能分清“等待输入、后台执行、等待确认、取消中、成功、失败、已取消”。
- 客服会话另外显示 AI/人工接待、等待承接与恢复状态；不把接管等同于业务取消，也不因固定时间过去就自动重用旧确认执行业务动作。
- 工具写入前确认，写入后展示真实业务结果 ID；模型口头表示“已完成”不构成完成证据。
- 对比表、参数表单、确认卡片、预约摘要和资料引用由受约束组件生成，不执行模型生成的任意 HTML 或脚本。
- 技术 Trace 可展开，但默认视图回答业务问题：依据是什么、做了什么、为什么等待、实际结果是什么、代价是什么。

## ScenarioPack 与交付包

`ScenarioPack` 是用户可以带走的交付单元，计划包含：

- 业务目标、`AgentSpec`、示例资料与来源标记；
- 版本化任务模板/策略引用、用户上下文字段与用途规则；真实用户记忆、画像与在途任务不混入公开示例包，迁移须独立授权与校验；
- 工具定义及模拟实现、`SkillManifest`、决策策略；
- 交互组件 Schema、渠道映射、验收集与期望副作用；
- 获授权的物料版本/派生引用、审阅简介与发送策略；真实文件和历史附件迁移须独立授权，不混入公开示例；
- 就绪检查、部署清单、固定依赖版本与成本假设。

标准应用发行物与场景包分别版本化：前者提供客服应用、执行服务、必要的存储与 Worker；后者提供业务配置与验收资产。云部署模板引用固定发行版本，模板不复制一套 Agent 配置。迁移真实业务数据须有独立授权与校验，不混入公开示例交付包。

## 用户自有云快捷交付（方向已确认，规划未实现）

用户可把完整客服服务部署到自己的云账号，独立管理运行、配置、数据和升级；日常服务不强制依赖 Loomrise 托管控制面。先提供统一 Linux/容器发行与单租户部署，再通过厂商模板创建计算、持久存储、网络、密钥引用和访问入口。腾讯云、阿里云为优先候选，AWS、Azure 为后续候选；具体入口、兼容性与支持清单以真实验收为准。

部署体验为“选择云与地域 → 查看资源、权限和云端费用预览 → 在用户账号授权创建 → 自动检查 → 获得工作台、客服 Inbox 地址与嵌入代码”。可重复部署、失败清理、备份恢复、升级兼容和数据迁移属于交付范围。模型、语音、通知或检索 API 的外部数据流必须可见；服务部署在用户云不代表所有数据处理均在该云。

自托管与可迁移是核心交付差异之一；开源许可和云厂商入口本身不构成快捷部署、独占能力或生产就绪证据。

## 分阶段建设与实现状态

| 阶段 | 建设目标 | 当前状态 |
|---|---|---|
| S1 | 已有纵向样例，补齐音频与真实模型 SSE 等剩余 Gate | 最小切片已实现，退出 Gate 未全通过 |
| S2-a | 持久化基础、配置版本与知识摄入、独立物料资产/原件与最小人工文件交付、沙盒发布及 Widget—Inbox 闭环 | 规划；已有工作台本地原型仅用于设计评审 |
| S2-b | 完整网页客服覆盖、联系页、Telegram/邮箱、通知、统计、移动 WebView 与物料后处理/已审简介检索 | 规划，按覆盖矩阵逐项验收 |
| S2-c | 业务工具沙盒、策略化 Agent 文件发送、固定评测、提案/审批/发布/回滚、持续改进及文字/语音应用验收 | 规划；护栏与版本证据从 S2-a 建设 |
| S3 | 标准发行、首个云快捷交付、认证与备份恢复、升级及端到端验收 | 规划，云厂商入口待验证 |
| S4 | 多云模板扩展、其他渠道；多租户与电话独立立项和验收 | 规划，不作为单租户云交付前置条件 |

阶段依赖、退出 Gate 和完整能力矩阵以[建设方案](CUSTOMER-SERVICE-DELIVERY-PLAN.md)与[验证路线](ROADMAP.md)为准，不承诺工时、日期或未测性能。

发布时冻结 `AgentVersion`，绑定提示词、模型引用、知识快照、Skill 目录、专家任务/触达蓝图、决策策略、工具和评测集版本。知识库是可审阅事实，会话记忆是带来源、有效期和删除入口的上下文，两者不能互相自动升级；动态许可按实际执行时的最新有效记录重验。

工具的业务语义不变时复用合同、另建供应商 Adapter；有新动作或副作用才定义新工具。Skill 是有条件、有边界的版本化执行策略，不授予工具权限；仅在子任务能隔离、限权、验收和回退时才考虑子 Agent。这些能力面向业务接入的规范化扩展，不意味着首版建设插件市场或多 Agent 群体。

## 成功指标（待基线实测，不预写达标结果）

- 冷启动：从开始创建到首个有有效资料依据的真实模型客服答疑，记录耗时、完成率和求助次数，分别报告手动、助手与混合路径；脚本模拟另计，接入工具后的首个业务办理结果另计，不混用终点或排除无模板用户。
- 任务可理解性：用户对当前状态、下一步和取消后果的判断正确率。
- 业务完成：约束满足度、确认准确率、模拟预约真实落库与重复写入数。
- 跨入口复用：文字与语音是否使用同一业务请求、权限、版本与结果；配置是否可导出到新实例。
- 可验证改进：受限候选通过率、固定集前后差异、退步案例、回滚成功率与硬规则违规数。
- 成本与体验：首有效响应、语音打断恢复、单位成功任务成本、人工复核率。
- 客服覆盖：知识引用准确与撤回生效、访客消息送达、人工承接与恢复、已回复与已解决分别统计。
- 物料交付：简介审阅/定位准确、撤回和过期失效、派生文件可用、版本/占用变化拒发、重复发送与回执未知；不以检索命中或本地消息记录证明送达。
- 自有云交付：干净账号部署通过、失败重试收敛、重启后幂等与接管状态保留、备份恢复与升级兼容、跨云迁移校验。
- 任务协同：正确执行/避让、错误放行/阻断、义务完成证据、重复触达、取消未生效与未知对账；不以发送量代替业务结果。
- 用户上下文：字段证据、精确读取、更正/冲突/过期/撤销、跨主体误读、迟到复活与压缩保护项；质量、时延和用量在固定条件下验收。

## 非目标与边界

不做通用 CRM、全功能节点画布、插件市场、多 Agent 群体、在线训练、公开任意代码执行、批量营销外呼或未授权数据摄入。S1 不实现主动触达调度、条件触达引擎、自动优化或复杂上下文记忆优化；只验证最小渐进式加载和可审计记录。后续自进化必须经过候选 Skill、独立评测、审批和可回滚发布，不能静默修改权限、硬规则、工具副作用或结果语义。首版不承诺生产级高可用，不把聊天界面、语音和可视化改动历史宣传为独占能力。

网页语音、消息桥接与 PSTN 电话分别验收：网页文字/语音应用在 S2-c 完成完整链路验收；Telegram/邮箱桥接在 S2-b 授权沙盒中验证；真实用户公网发行与首云交付在 S3；其他 IM、多租户及电话按 S4 的独立 Gate 推进。保险、牙科、医美等只处理经确认的一般信息与预约转接，不做诊断、疗效、收益或价格承诺。

**独立性**：Loomrise 是业务 Agent 配置、任务运行、评测与发布的权威。其他长期上下文或记忆系统只能作为经治理的数据来源，不运行或编排 Loomrise Agent。工作经历只能抽象为公开方法，不能移植私有代码、Prompt、数据或品牌。
