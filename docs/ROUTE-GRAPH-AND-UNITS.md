## 0. 一句话

**图只管"去哪"，不管"说什么"；模型在闭集里选，工程定闭集是什么。**

补一条 v0.2 才成立的前提：**"图"和"单元"不是两种东西，是同一对象的两个缩放级别。收起是节点，展开是图。** 所以"三层路由 + 可复用单元"不是两个功能拼起来，而是同一条结构的两个视图。

## 1. 先看清三个方案各自把图当什么

| 维度         | ElevenLabs                           | 虾宝（作业帮 AI 托管）                                       | Loomrise 现状                             | 融合取舍                       |
| ---------- | ------------------------------------ | --------------------------------------------------- | --------------------------------------- | -------------------------- |
| **图是什么**   | 对话流程：节点＝一次接管（换提示/工具/知识/模型/音色）        | 任务 → **动作节点**序列；动作内部还有执行策略                          | 没有图：单 Agent + 事项 + 硬规则                  | **图只做路由**，不做对话脚本           |
| **单元**     | 节点内联全部配置，**不可复用**（只有 Procedure 有 ID） | 动作节点属于某任务；**动作内还有策略层**                              | Skill 蓝图可复用                             | **单元外置、可分层打包、可被多条边指向**     |
| **本层可否再分** | 不能（节点是叶）                             | 能（动作内有策略）                                           | —                                       | **能，且收起后与上层节点同构**          |
| **判定**     | 边条件四类（含 AST 里混 `llm` 叶子）             | 交互策略多为自然语言提示                                        | 硬规则确定性 + 人评                             | **LLM 在闭集内选 + 工程闸门前置**     |
| **加载**     | 节点级覆盖 + 只保留最近 5 条流程                  | Skill / 知识渐进加载                                      | L0–L2 已定（`AGENT-INTEGRATION-PLAN` §1.2） | **L0 逐层给路由表摘要**            |
| **版本**     | 整棵树一个快照                              | `locked`/`current`/`candidate` + 段落级 locked/mutable | `AgentVersion` 不可变                      | 图 / 单元 / 规则**同一版本冻结**      |
| **失败**     | 成功或失败两态，失败可挂断                        | 有 Badcase 回流                                        | `reconciling`（副作用未知）                    | 保留 `reconciling`，**不引入两态** |

**结论**：ElevenLabs 的图**形式**值得用（路由确实适合画），但它的**单元定义**不能照抄——它把内容内联进节点，导致"改一处要改多处、单元无法单测、单元无独立版本"；它的**扁平**又导致节点只能表示一次接管，装不下"动作内部还有策略"。

> 你说的那句"节点单元 / 节点配置内容 / 节点的定义可以不同"，在这一版落成了结构：**借它的图，不借它的节点，也不接受它只有一层。**

## 2. 核心：一种对象，两个层

```
                    ┌──────────────────────────────────────┐
                    │  Unit（唯一对象）                      │
                    │  ┌────────────────────────────────┐  │
                    │  │ 契约层  entry/reads/writes/     │  │
                    │  │        exit_ports/fallback     │  │
                    │  │        on_event/max_rounds      │  │
                    │  └────────────────────────────────┘  │
                    │  ┌────────────────────────────────┐  │
                    │  │ 内容层  子图（图） | 原子（一步） │  │
                    │  └────────────────────────────────┘  │
                    └──────────────────────────────────────┘
                          收起 ↑            ↓ 展开
                       一个节点            一张图
```

### 2.1 契约层：只有路由信息

| 字段                    | 说明                                                                                           |
| --------------------- | -------------------------------------------------------------------------------------------- |
| `unit_id` + `version` | 稳定 ID；版本冻结，不是"最新"                                                                            |
| `load_mode` | `routed`（参与分流，进图）或 `concurrent`（按相关性召回，**不进图**）。**不允许 both**——混在一起就无法归因「选错路」还是「召错内容」 |
| `entry_ports` | **入口端口**：每个带 `requires`（进入前必须就绪的字段）。默认一个 `from_start`，可增——**跳步由此支持**（§3.2）。**端口只声明前提、不写意图条件**——「要不要来」在边的 `condition`（RG-F7） |
| `reads`               | 本单元需要读的字段（必须已被上游声明或系统注入）                                                                     |
| `writes`              | 本单元会写的字段（保存前校验"确实会被赋值"）                                                                      |
| `exit_ports`          | **出口端口**：每个带自己的 `completion` 与候选 `exits`——**一个出口 = 一个完成条件**（ElevenLabs 只有整图一个 `end.outcome`） |
| `on_event`            | **边界事件**（挂断/超时/副作用未知/接管），声明在包上、作用域不逃逸（§3.3）                                                  |
| `fallback`            | 无匹配时的兜底（澄清 / 默认单元 / 转人工）                                                                     |
| `max_rounds`          | 被重复进入时的次数上限与退出目的地。**窗口 = `cycle`**（同一服务周期 / 同一事项内），换一件事重置——不是 `session`，否则挂断重拨就重置（[硬规则模型](HARD-RULE-MODEL.md) §3.1） |

**契约层里没有**：提示词、工具清单、知识文档、音色、模型。这些全部在内容层。

→ 收起时暴露的就是这九个字段。因为它足够小，**上层永远不需要看下层的措辞**——这正是我们要的隔离。

### 2.2 内容层：子图 或 原子

| 形态     | 是什么                      | 例子                          |
| ------ | ------------------------ | --------------------------- |
| **子图** | 本层的边指向下一层单元              | "退款处理"内含：核验身份 → 确认订单 → 发起退款 |
| **原子** | 只有一步，端口退化为"做了没"（单入口、单出口） | 见下                          |

**原子四型**（这是唯一允许的枚举扩张点，每一项都要有存在理由）：

| 类型      | 是什么          | 为什么必须存在                |
| ------- | ------------ | ---------------------- |
| `tool`  | 单次工具调用       | 最小执行单位                 |
| `judge` | 单次确定性判定（表达式） | 硬规则在模型外的最小载体           |
| `speak` | 单次自由表达       | 模型组织语言的最小单位            |
| `say`   | 单次**逐字**话术   | 法律披露、确认复述——**不能靠模型转述** |

> `say` 是唯一有"退化风险"的原子：一旦滥用就变成对话脚本。准入条件写死——**必须声明 `verbatim_reason`（为什么不能改字），无此字段拒绝保存**。这条是"不做对话脚本"的守门人。

**底在哪**：原子层不是图（只有一步，"是否串行"无意义）。"最小不可分割的策略单元**之上**全都是图"——就是这句。

### 2.3 收起与展开是同一份数据的两种投影

|      | 收起                | 展开                    |
| ---- | ----------------- | --------------------- |
| 看到什么 | 契约层八字段            | 内容层的图（节点 + 边）         |
| 谁能改  | 契约层               | 内容层                   |
| 被谁引用 | 上层边按 `unit_id` 指向 | **外层边不得指向内部节点**（§3.2） |

这与 ElevenLabs 的关键差别：**它的"编译"是单向的**（步骤 → 图，产物只读，要改必须回另一个页面）。我们的收起/展开**只是同一对象的两个视图，任一处改都写同一草稿**，不产生第二份真相。

### 2.4 判定单元仍然是独立引用物

- **硬规则（Guard）**：确定性、在模型外、**前置**。**它只产出裁决**（`deny` / `require` / `stop` / `dedupe`），**不产出"去哪"**——「强制去哪 / 挂起」是 `GateOutcome` 的事，不是 `Verdict` 的事（[硬规则模型](HARD-RULE-MODEL.md) §3.4，2026-10-22 定）。不进人评、不可协商。
- **软判据（Criterion）**：进评测、可三值（`success`/`failure`/`unknown`）、版本化。

两者都有 ID，可被任意层的 `entry_ports`/`exit_ports` 引用，也可被测试用例引用。**能被引用的，必须先被声明**——沿用 `HARD-RULE-MODEL`，不新增原则。

## 3. 连接与事件：跨层需求怎么表达

"环"和"跨层"这两个词在这个结构下都太粗。必须拆成五类连接，否则要么禁掉了该允许的，要么放过了该禁的。

### 3.1 五类连接

| # | 类型                 | 例子                                                  | 处置                       |
| - | ------------------ | --------------------------------------------------- | ------------------------ |
| 1 | **同层边（含跳步）**       | 图内从 n1 直接到 n3，跳过 n2                                 | **允许**，跳步本来就不是特殊情况       |
| 2 | **端口边（跨层）**        | 外层边 → `U-退款.from_verified`；包内节点 → `self.need_human` | **允许**，这是跨层的唯一正规通道       |
| 3 | **边界事件（跨层、无固定起点）** | 任意节点遇用户挂断 → `U-留资`；任意节点遇副作用未知 → `U-对账` | **允许**，但必须声明在包上、作用域不得逃逸 |
| 4 | **组合环**            | A 的 body 含 B，B 的 body 含 A                           | **禁止**                   |
| 5 | **裸跨层边**           | 外层的一条边直接落到包内部第 3 个节点                                | **禁止**（但用第 2、3 行能满足同样需求） |

> 一句话：**跨层的需求是真的，但跨层不应该是一条"通道"，应该是一个"端口"或一个"事件"。**

### 3.2 端口：跨层唯一的正规通道

类比先说清：**端口 = 函数签名；裸跨层边 = goto 进函数第 3 行。** 前者能被调用方安全使用，后者让函数内部的每一步都变成公开 API。

```yaml
entry_ports:
  - port: from_start            # 默认入口，走完整流程
    requires: []
  - port: from_verified         # 允许外部直接进"已核验"这一步，跳过核验节点
    requires: [user.verified, order.status == "paid"]

exit_ports:
  - port: done                  # 正常完成
    completion: { deterministic: refund.case_id != null }
    exits: [U-退款-已受理, U-结束]
  - port: need_human            # 提前离开
    completion: { deterministic: 已说明转人工原因 }
    exits: [U-转人工]
```

三条性质：

1. **端口属于契约层**，收起时可见——所以"跨层"不破坏隔离，只是让接口多了一个入口或出口。
2. **入口带 `requires`，出口带 `completion`**。于是"完成条件"从单元级**下沉到出口级**：**一个出口 = 一个完成条件**。这比 ElevenLabs 那个唯一的 `end.outcome` 更细——它整张图只有一次成败判定，我们每个出口各有一次。
3. **端口数量本身就是设计压力**：入口 >3 或出口 >3，说明这个包切错了（职责不单一），该拆包，而不是该放开。

### 3.3 边界事件：不是边，是"从任何地方都能触发"

一半的"跨层"需求其实不是边。区别就在这句话：

> **边是"从某处到某处"；事件是"从任何地方都能触发"。**

写成边要写 N 条（每个内部节点各一条），写成事件只要一条。所以异常、超时、挂断、接管这类需求**必须用事件，不能用边**——用边写，图会瞬间爆炸。

| 事件                    | 典型触发          | 去处                   |
| --------------------- | ------------- | -------------------- |
| `user_hangup`         | 任意节点用户挂断      | 留资 / 结束              |
| `side_effect_unknown` | 任意工具返回未知      | 对账（事项 `reconciling`） |
| `timeout`             | 任意 `waits` 超时 | 等待提示 / 转人工           |
| `handoff`             | 任意节点人工接管      | 交回业务应用               |

两条约束：

- **作用域三级**：`self`（本单元内）· `subtree`（本包子树）· `global`（整个专家版本）。`global` 只能声明在专家版本层，且 `goto` 只能指向顶层单元或端口——**不得穿进包里**，否则又变成一条隐式跨层边（RG-F8）。
- **优先级固定**：`G0 闸门 > 边界事件 > 边`。闸门命中时连事件都不判——闸门是确定性裁决，事件还带着条件。

### 3.4 特殊路由规则归到哪（对照表）

| 你想要的                       | 用哪个                             |
| -------------------------- | ------------------------------- |
| 跳过中间某个节点                   | **同层边**，直接指向目标                  |
| 进包内某一步（不从头走）               | **入口端口**                        |
| 从包内提前离开                    | **出口端口**（包内写 `to: self.<port>`） |
| 任意层下都成立的规则（如"用户一提退款就回主流程"） | **G0 闸门**（优先级最高）或**边界事件**       |
| 异常 / 超时 / 挂断               | **边界事件**                        |
| 回退重来                       | **执行环** + `max_rounds`          |
| 同级多条边的先后                   | `edge_order`（列表位置即优先级）          |
| 按时间 / 轮次 / 字段值的条件          | 边上的条件表达式（确定性），或 `llm` 叶子作布尔值    |

> 这张表的意义：**"特殊"不是靠放开一条边来支持的，而是靠"给它一个正确的位置"。** 放开裸跨层只会让特殊性扩散到整张图——到那时没人能回答"这通电话为什么会走到这一步"。

### 3.5 为什么裸跨层仍然禁

即便有了端口，仍要禁最裸的那种。三条理由：

1. **"收起"失去隔离语义**——端口可见、内部不可见，收起才有意义。
2. **`reads`/`writes` 声明失义**——有边绕过了端口，第 7 条的包含关系不再成立。
3. **路径断言不可算**——端口到内部节点的映射是固定的，裸边是任意的，评测无法断言"走到了哪一步"。

代价也说清：某些"想从 A 直接跳到 B 内部某步"的写法，**要多声明一个入口端口**。这是**故意付的代价**，而它换回来的正是"可验收"。

### 3.6 组合环与执行环

- **组合环**（A⊃B⊃A）是抽象失败：两者都无法单独校验、单独版本化、单独测。**禁。**
- **执行环**是业务常态：用户改主意、反复确认、补材料。禁掉它等于逼作者造 goto。**允**，但三条硬要求：
  1. 回到先前节点的边必须带 `max_rounds` 与 `exit`（达到上限后去哪）；
  2. 重复进入同一单元必须**写计数器字段**（进 `writes`）；
  3. 达到上限必须走兜底，**不得无声明地继续**。

区别一句话：**组合环在"定义"上，执行环在"运行"上。定义必须是 DAG，运行可以回到过去。**

### 3.7 嵌套深度与"一层一屏"

深度本身不设硬上限，但有一条可读性判据：**任何一层展开后，人必须能在一屏内读完它的节点与出边**（工程化取值：≤12 节点、单节点扇出 ≤5）。

默认只展开 3 层（任务 → 动作 → 策略）。要画到第 4 层，我们把它当**信号**而不是罪状：说明中间那一层的命名没承载住语义，强制评审一次"是不是该合并/该重命名"。

## 4. 路由：三层，且"闭集"是关键

```
输入
 │
 ├─▶ ① 闸门 G0（确定性，模型外）
 │      硬规则 / 权限 / 授权范围 / 停止退订 / 人工锁定
 │      命中 → 直接定去向或阻断（不交给模型）
 │
 ├─▶ ② 路由 G1（LLM，优先用模型能力）
 │      输入：本层路由表摘要 + 当前事项 + 最近 N 轮
 │      输出：unit_id + 各候选分数 + 依据 + 未匹配声明
 │      ★ 只能从 exits 给出的闭集里选，不能发明
 │
 └─▶ ③ 兜底 G2（工程）
        低 margin / 无匹配 / 越权 → 澄清单元 / 默认单元 / 转人工
```

### 4.0 本层先声明路由方式（`routing.mode`）

**逐层（每张图）必填、不可推断**。因为「端口 / 闭集变大」到底危险不危险，取决于谁在选：

| `routing.mode` | 谁在选 | 闭集变大意味着 | 提示阈值（闭集大小） |
|---|---|---|---|
| `deterministic` | 表达式 + `edge_order` | 准确性几乎不受影响，但**条件要人工保证互斥 / 穷尽**，越加越死板 | > 8 |
| `llm` | 模型在闭集里选 | **选择准确率随闭集增大而下降**（主要风险） | > 5 提示 · > 8 强提示 |
| `hybrid`（默认） | 先确定性筛，再模型选 | 取决于筛完剩几个 | 筛后 > 5 |

**告警量的是「闭集大小」，不是「端口个数」**：闭集 = 本层所有出口边指向的目标去重后的数量。一个单元 3 个出口端口、各指向 2 个单元，闭集是 6——只量端口会漏报这种情况。

告警**只提示、不阻断**（保存与发布都不挡），分两级；必须同时给出替代：合并入口 / 拆包 / 改成本层确定性路由 / 两段式（先分大类再细分）。忽略要留痕并进评审摘要。

### 4.1 为什么"闭集"是整个方案的关键

ElevenLabs 的做法是在**同一条规则**里混确定与概率（`{"type":"llm"}` 作为 AST 叶子）。我们更进一步：

> **概率只用在"选"，确定性用在哪"些"和"能不能"。**

模型可以自由判断"用户现在要退款还是查物流"，但**它不能发明一个不存在的单元**，也不能自己决定"退款可以跳过身份核验"。三个后果：

- **错也只错在"选错路"，不会错在"编出一条路"**——这是可评测的错。
- 模型变强时，收益直接体现在"选得更准"，而**不需要改契约**。
- 选项集由工程产出（受权限、授权范围、当前事项状态过滤），因此"选对"与"有权去"是同一个集合。

### 4.2 置信口径：不用绝对置信，用 margin + 可校验依据（RG-3 定）

模型自评的绝对置信校准差，且"自信地错"是常态——直接拿它做阈值，"低置信→澄清"这条兜底形同虚设。改为两个可验的信号：

| 信号         | 怎么来                                            | 怎么用                                         |
| ---------- | ---------------------------------------------- | ------------------------------------------- |
| **margin** | 要求模型给闭集内**每个候选**打分（或至少首选 + 次选），取 `top1 − top2` | 低于阈值 → 澄清；**分数本身不进契约**，只作路由提示               |
| **依据**     | 模型必须指明"依据哪个已声明字段 / 用户哪句话"                      | 工程校验该字段存在且已赋值、该句确实在最近 N 轮里；**校验不过 = 视同无依据** |

| 情形                     | 处置                       |
| ---------------------- | ------------------------ |
| 高 margin + 依据可校验 + 在闭集 | 进入该单元                    |
| 低 margin               | 走**澄清单元**（一句追问，而不是猜）     |
| 依据缺失或不可校验              | 视同低 margin               |
| 无匹配                    | 走 `fallback`（默认单元 / 转人工） |
| 想去的单元不在闭集（越权/未授权）      | **按无匹配处理**，并留证（坏例候选）     |

> 最后一行是硬要求：**模型说"我要去 U-退款"，但当前授权范围内没有这个单元**，系统不能"就近找一个"，必须当成"没有这个选项"，并记成一次越界尝试。否则闭集就白设了。

### 4.3 与 ElevenLabs AST 混合的差别（一句话）

它是"**一条规则可以由确定与概率拼成**"；我们是"**一次选择由模型做，但候选项由工程定**"。前者让概率进入规则内部，后者让概率停在**选择**这个动作上——而选择恰好是模型最擅长、也最容易评的东西。

## 5. Unit 的完整定义

```yaml
unit_id: U-退款-02
version: 3                       # 独立版本，随 AgentVersion 冻结引用
goal: 判断订单是否符合退款条件并完成受理        # 进提示，一句话

entry_ports:                     # 每个入口 = 一条"可以被怎么进来"
  - port: from_start             # 默认入口，走完整流程
    requires: []                 # 端口只声明「进入前必须就绪的字段」
  - port: from_verified          # 外部可跳过核验，直接进"确认订单"
    requires: [user.verified]    # 跳步的前提：字段必须已就绪
    goto: n2

reads:  [order.status, order.paid_at, user.verified]
writes: [refund.case_id, refund.result]        # 保存前校验"确实会被赋值"

# ---- 内容层：二选一 ----
body:
  kind: graph                    # graph | tool | judge | speak | say
  nodes:                         # 只在本层内可见
    - unit_ref: U-核验身份-v2
    - unit_ref: U-确认订单-v1
    - unit_ref: U-发起退款-v3
  edges:
    - from: n1  to: n2  condition: verified == true
    - from: n1  to: self.need_human  condition: verified == false   # 提前离开，走自己的出口
    - from: n3  to: n1  condition: 用户改主意      # 执行环
      max_rounds: 2
      exit: self.need_human
    - from: n3  to: self.done

prompt_fragments:               # 引用，不内联；按 L1 加载
  - P-退款-政策-v2
  - P-语气-共情-通用-v1
tool_scope:                     # 权限与批准包络，不是"工具清单"
  - T-order-lookup      (auto)
  - T-refund-create     (需批准：金额 > 500)
knowledge_view:
  - 标准回复: 退款时效
  - 业务知识: 退款政策（RAG）

exit_ports:                     # 一个出口 = 一个完成条件
  - port: done                  # 正常完成
    completion:
      deterministic: refund.case_id != null
      llm: 用户确认已知晓到账时间
      on_unknown: 保持本单元，最多追问 2 次
    exits: [U-退款-已受理, U-结束]
  - port: need_human            # 提前离开
    completion: { deterministic: 已说明转人工原因 }
    exits: [U-转人工]

on_event:                       # 边界事件：scope = self | subtree | global（global 只能在专家版本层，且不得穿进包里）
  - { event: user_hangup,         goto: U-留资,  scope: self }
  - { event: side_effect_unknown, goto: U-对账,  scope: self }   # 副作用未知 → 事项 reconciling
  - { event: timeout,             goto: U-等待提示, scope: self }

waits:                          # 可选：等外部
  - 等审批回执 / 等物流 / 等人工
    超时: 120s → 走 U-等待提示
```

## 6. 九条保存前校验（全部确定性，离线可算）

| # | 约束 | 层次 | 补的是哪条缺点 |
|---|---|---|---|
| 1 | `writes` 里每个字段，必须在某条路径上被真实赋值 | 单元 | 无状态一等公民 |
| 2 | `reads` 里每个字段，必须已被上游声明写过、由系统注入、或由本单元自己先写 | 单元 + 图 | 同上 |
| 3 | **每个入口端口有 `requires`（字段前提），每个出口端口有 `completion`**；出口端口至少有一条入边；无出口端口不允许发布 | 单元 | 只有进入条件 |
| 4 | `exits` 必须覆盖所有分支或显式声明兜底（穷尽性） | 单元 | 校验只到结构 |
| 5 | **组合关系必须是 DAG**（禁组合环）；**执行环必须带 `max_rounds` 与 `exit`** | 组合 / 图 | 默认不防环 |
| 6 | 引用的提示片段 / 工具 / 知识 / 子单元必须存在且**版本已冻结** | 单元 | 引用失配 |
| 7 | **接口诚实性**：body 实际读的字段 ⊆ `reads`，实际写的 ⊆ `writes`；每个 `entry_port.requires` ⊆ `reads`；每个 `exit_port.completion` 引用的字段 ⊆ `writes` ∪ 系统字段 | 单元 | 新增（分形结构的唯一真实风险） |
| 8 | **连接合法性**：边只能指向本层单元、本单元的端口、或 `self.<出口端口>`；事件 `goto` 不得跳出声明层的子树；**不存在裸跨层边** | 图 / 组合 | 新增（跨层走端口而非通道） |
| 9 | **条件深度 ≤ 2 层**：`all_of` / `any_of` / `none_of` 的嵌套层数；**`llm` 叶不计层**；硬规则 `when` 与边 `condition` **同一上限** | 单元 / 图 | 复杂度转嫁模型 |

> **另有第 10 条，但它是「提交前」而非「保存前」**：**孤立单元**（无任何边指向、也非入口、且 `load_mode = routed`）——保存**允许**（草稿中间态），**提交阻断**，单元清单标「未接入」。与「保存允许有错、提交禁用」同一条逻辑（RG-F12）。
>
> 第 9 条同样按"保存允许、提交阻断"处理：草稿可以有中间态，但超过 2 层不是一个可提交的形状（[硬规则模型](HARD-RULE-MODEL.md) §3.1）。

### 6.1 为什么第 7 条是这个结构的命门

前六条都建立在"声明是可信的"这个前提上。而分形结构允许 body 里藏一整张图——**一旦包说谎，上层所有校验都是假的**：上层以为只依赖 `order.status`，实际下层读了 `user.id_card`。

第 7 条的做法是反向检查：不看声明，看 body 的真实读写集合，与声明做包含关系。全部离线可算（读 AST / 读子图节点的 `reads`/`writes` 并集）。

### 6.2 逐层局部校验：包让校验更便宜，不是更贵

| 校验对象 | 检查什么 | 何时做 |
|---|---|---|
| **每个单元** | 第 1、2、3、6、7 条；第 8、9 条（限 body 内部边与 body 内条件） | 保存单元时 |
| **每张图** | 第 2 条（跨节点覆盖）、第 4 条（穷尽）、第 5 条（执行环上限）、规模上限 | 保存图时 |
| **整棵组合树** | 第 5 条的前半（组合 DAG，只在组包时新增一跳，增量可查） | 组包时 |

关键收益：**同一个包只验一次，被 N 处复用**。拍平成一整张图反而要验 N 遍。所以"允许嵌套"这件事在校验上是**省钱的**——代价只是必须保证接口诚实（第 7 条）。

### 6.3 单元的可复用性怎么体现

- 一个单元被 N 个节点指向，**改一次生效 N 处**；
- 单元的编辑页必须列出 **`Used by`（被哪些节点/图/专家引用）**，改之前看得见影响面；
- 单元升级版本时，**引用方不自动跟随**——要显式升级引用，否则不同版本号下行为不可比。

## 7. 渐进式加载：与分形结构天然对齐

既有 L0–L2 的定义（`AGENT-INTEGRATION-PLAN` §1.2）是对的，但**缺一层**：模型要路由，就必须在 L0 就知道"本层有哪些单元、各自何时用"。现在 L0 是"事项摘要 + 少量能力描述"，没有**路由表**。

**关键性质**：加载是**逐层下钻**的，不是一次性铺开。这正好是分形结构的红利——展开一层才加载一层，深度不增加上下文成本。

| 层 | 新增内容 | 原有的不变量 |
|---|---|---|
| **L0** | **本层路由表摘要**：每个候选单元一行（`unit_id` + 一句话"何时用" + `goal`），以及**当前闭集**（受权限/状态过滤） | 不加载提示全文、不加载工具 Schema、不加载知识内容 |
| **L1** | 命中单元的**契约层 + 提示片段 + 工具精确 Schema + 知识视图指针 + 完成条件** | 命中不等于授权；生产动作仍单独确认 |
| **L2** | 按需展开：话术样例、历史案例、详细资料、证据 | 分页/摘要/裁剪留证 |

> 下钻的边界：进入单元的 body 后，**重新按 L0 处理下一层**（拿到下一层的路由表，而不是把下一层的全文塞进来）。这是"分形"在加载上的必然做法，也解释了为什么深嵌套不会撑爆上下文。

### 7.1 虾宝五类知识 → 三个加载档位的天然映射

| 虾宝知识类型 | 加载档 | 理由 |
|---|---|---|
| **标准回复** | **L1（命中即加载，逐字）** | 高权重固定答案，不能改字；对应 `say` 原子与 ElevenLabs 的 `Say` 步骤 |
| **参考任务**（TOP 教师的策略描述） | **L1** | 就是"这一步该怎么做"，属于单元的提示片段 |
| **业务知识** | L1 给指针 + L2 检索 | 不定内容，只定"可查这个范围" |
| **参考话术** | **L2** | 风格样例，按需取两三句即可，全塞进去会淹没指令 |
| **标准物料** | **L2** | 图片/视频/文档按需，L0/L1 只留引用 |

> 这张映射表解决了一个具体问题：**虾宝的五类知识本来就是按"该不该逐字"分的**，正好对应加载档位。不需要新造分类。

### 7.2 为什么这套能让"模型越强越吃得到红利"

| 如果把流程写死 | 本方案 |
|---|---|
| 模型只负责填槽位 | 模型负责**选路 + 组织表达** |
| 模型升级，行为不变 | 模型升级，路由更准、表达更好，**契约不动** |
| 每加一个场景要画一段流程 | 加一个**单元**即可，图只多一条边 |

一句话：**契约稳定，行为可变。** 契约是单元的九字段与九条校验；行为是提示片段里的表达。

## 8. 版本与评测（RG-4 定：三类测试，粒度不对称）

| 测试类型 | 输入 | 断言 | 覆盖范围 |
|---|---|---|---|
| **整通** | 完整场景（从会话开始到终态） | 终态 + 验收判据 + 关键副作用 | 场景全集；**`blind` 只在这一层存在** |
| **路由** | 用户话术序列 / 起始字段集 | 命中的 `unit_id` 与路径顺序 | 单层图的边与兜底 |
| **单元** | 已进入该单元的上下文 | 单元内行为：工具调用、话术、完成条件 | 单单元 |
| **召回** | 用户话术 + 当前所处单元 | 是否应召回某个 `concurrent` 单元（以及是否误召回） | 只覆盖 `load_mode = concurrent`（RG-F11） |

**划分原则（不对称）**：

- `golden` **下沉到单元**可用——改一个单元只跑引用它的案例，评测范围变小。
- `blind` **保持场景整通，不得切碎**。切到单元级会丢两样东西：一是"**怎么进来的**"这个最关键变量被前置条件去掉了；二是样本碎掉，失去统计意义。且 `blind` 不得由搭建者编写这条规则，在分形结构下更容易被绕过——所以粒度必须钉死在整通。
- **路由测试是补"无路径断言"的正确位置**，不是单元级测试。ElevenLabs 的 `Node entered` 只是观测过滤器；我们要求它是判据。

**门禁归属**（沿用两栏，不合并）：

| 落哪一栏 | 内容 |
|---|---|
| **不退步** | 整通 `golden` 通过率不降 · 整通 `blind` 通过率不降 · **路由路径断言不降**（结构性强，进硬栏） |
| **有改善** | 单元级测试改善（可单测但**不单独构成通过**——它证明不了路由对不对） |
| **诊断（暂不进两栏）** | 召回测试（`concurrent` 单元）——召回是概率行为，样本稳定后再评估是否升为门禁 |

**硬软分离计分**：硬规则命中 = 阻断/转人工，**不进人评**；软判据 = 进人评、三值、可 `unknown`。避免把"规则拦住了"算成"模型做错了"。

三者挂在同一个 `AgentVersion` 上：图 / 单元 / 规则三份引用**同一版本冻结**，任何一份升级都产生新版本，可回滚。

## 9. 逐条对照：它八条缺点，本方案怎么答

| ElevenLabs 的缺点（卷二 §12） | 本方案的回应 | 强度 |
|---|---|---|
| ① 无状态一等公民 | 每个单元声明 `reads`/`writes`；第 1、2、7 条保证"声明即会被赋值、且不会多读多写"；写入必须过 `ExecutionService` | **结构解** |
| ② 只有进入条件 | 每个出口端口各带一个 `completion`（**一个出口 = 一个完成条件**），且 `completion` 确定性优先；它整图只有一次 `end.outcome` | **结构解** |
| ③ 无"等外部"原语 | `waits` 是一等字段，带超时分支，落进事项的 `reconciling` 语义 | **结构解** |
| ④ 工具失败只有两态 | 失败是**事件**不是边：`side_effect_unknown` → 事项 `reconciling`，不是重试/挂断二选一 | **结构解** |
| ⑤ 校验只到结构合法 | 九条校验 = 可赋值 + 可达 + 穷尽 + 组合 DAG + 执行环有上限 + 引用已冻结 + **接口诚实** + **连接合法** + **条件深度 ≤2** | **结构解** |
| ⑥ 复杂度转嫁模型 | 模型只做闭集选择；候选集、闸门、完成条件都在工程侧 | **结构解** |
| ⑦ 编辑回路断裂 | 收起/展开是同一对象的两个投影，任一处改都写同一草稿；单元页有 `Used by` | 部分解（仍取决于 S2 页面组织） |
| ⑧ 无节点级版本 / 路径断言 | 单元独立版本 + 路由测试断言路径 | **结构解** |
| ⑨（它没有这一条）**扁平**：节点只能是"一次接管"，装不下"动作内还有策略" | 分形单元：任意层都可展开为图，收起后与上层节点同构 | **结构解** |

**只有第 ⑦ 条是"部分解"**——它不是数据模型问题，是交互问题：能不能让"看图"和"改单元"在同一个界面里闭环，取决于 S2 的页面组织。

## 10. 不做什么（边界比功能重要）

| 不做 | 原因 |
|---|---|
| **不做对话脚本**（不在图上编排"说哪句"） | 一旦在图上写台词，就退化成 ElevenLabs 的节点。原子级 `say` 是唯一例外，且必须声明 `verbatim_reason` |
| **不让单元内联提示** | 内联＝不可复用＋不可单测＋无独立版本 |
| **不做通用编排 DSL / 不做"图即上线"** | 图只服务路由；上线仍走 `ChangeProposal` → 评测 → 审批 |
| **不追求节点类型多** | 只有一种节点（单元）+ 一种终点；原子四型是唯一枚举，且每项须有存在理由 |
| **不允许裸跨层边** | 跨层只经端口或事件（§3.1）；包边界必须是唯一通信面 |
| **不允许无上限的执行环** | 默认防环；开环必须声明 `max_rounds` 与 `exit` |
| **不替换单 Agent 为主的形态** | 见 §11 的准确表述：**默认是单 Agent 在一个单元里说话；图只用来表达"必须换权限或换资料边界"的分叉** |

## 11. 已定事项（RG-1…RG-7，2026-10-22 确认）

### 11.1 RG-6 的判据为什么不是数字

数字只能拦住"太大"，拦不住"不必要"。真正决定"该不该有这张图"的是：**这些分支是否需要不同的工具授权、不同的资料可见范围、或不同的合规处置**。

- 全都相同 → 这张图只是分层，**用提示 + 单元选择更省**（也是"单 Agent 为主"的本意）；
- 有一项不同 → 必须用图，因为**权限与资料边界不能靠提示实现**。

### 11.2 RG-5 落地时的一个检查点

虾宝的 SOP 里若含"等待 N 天再触达"，翻译时不是边，而是 `waits`（一等字段）。**判据：时间是最长的那一段就说明它是等待，不是步骤。**

### 11.3 v0.3 修订：跨层不是"通道"，是"端口"或"事件"

v0.2 把"跨层跳边"整条禁掉，是把三种不同的东西混为一谈：

| 真实需求 | v0.2 的处置 | 错在哪 | v0.3 的处置 |
|---|---|---|---|
| 同层跳过中间节点 | 允许 | — | 不变 |
| 进包内某一步、从包内提前离开 | **一律禁止** | 把"合法的部分进入"和"任意穿梭"当成一回事 | **入口/出口端口** |
| 任意层都要生效（挂断、超时、副作用未知、接管） | 没有原语 | 这类东西写不成边（要写 N 条） | **边界事件** |

三条由此产生的结构性变化：

1. **完成条件下沉到出口级**：`completion` 不再是单元的一个字段，而是每个 `exit_port` 各带一个。**一个出口 = 一个完成条件**——比 EL 的单一 `end.outcome` 精确。
2. **失败处理从"边"变成"事件"**：`on_failure` 取消，改为 `on_event.side_effect_unknown`。理由：失败可能发生在任意节点，写成边要写 N 条；写成事件只要一条。
3. **新增第 8 条校验（连接合法性）**：这条是"端口化"能成立的前提——它保证没有任何一条边绕过端口。

代价写清：**要多声明端口**。但换来的是"路径断言仍可算"（端口到内部节点的映射固定），以及"收起"仍然有隔离语义。**这是唯一一笔值得付的交易：牺牲一点书写便利，换"可验收"。**
