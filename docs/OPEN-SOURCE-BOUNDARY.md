# 开源与私有工作区边界 v0.1

状态：项目协作规范，2026-10-12（新增 §开源协议：协议开放程度排序、选型理由与**已确认的选择**）。

## 目标

Loomrise 的公开仓库用于沉淀可以独立理解、验证和协作的产品资产，而不是公开作者的全部思考过程。每条信息在进入公开仓库前，都应先判断它是**可发布的项目事实或决策**，还是**尚未确认的个人判断与讨论材料**。

`private/` 是本地工作区，已加入 `.gitignore`。Agent 和协作者不得使用 `git add --force` 等方式把该目录提交到公开历史。

## 两侧职责

### 公开仓库

公开内容应满足至少一项：

- 已实现且可复现的代码、配置或测试；
- 已有明确状态和边界的版本化决策；
- 可复现的评测方法、结果与已知限制；
- 对贡献者必要的问题、接口、路线和验收标准；
- 不依赖个人经历、雇主语境或内部关系即可理解的背景。

公开文档必须区分：

- **已确认**：已经形成项目决定，但仍可注明尚未实现；
- **待验证**：已有候选和验收门，不得写成事实；
- **待决策**：存在开放选项，不假装已经选定；
- **规划**：尚未实现的能力；
- **已实现 / 已验证**：只有在代码、测试或真实运行证据存在时使用。

### 私有工作区

`private/` 用于保存：

- 尚未收敛的产品判断、个人偏好和讨论过程；
- 个人品牌、职业展示、商业化、定价和预算假设；
- 敏感的用户研究、合作沟通和未公开计划；
- 原始研究、长清单、读书笔记和方案草稿；
- 可能因语境变化而失去意义的临时取舍。

建议结构：

```text
private/
├── README.md
├── research/       # 原始报告、资料摘录与外部研究
├── notes/          # 个人判断、待确认讨论与索引
├── decisions/      # 尚未公开的决策草稿与取舍记录
├── experiments/    # 不进入公开仓库的试验记录
└── archive/        # 被新结论替代但希望本地保留的材料
```

`private/` 只是减少误提交风险的工作区，不是密钥保险箱。API key、密码、token、客户隐私和受监管数据不得因“已忽略”而存入其中；这些内容应进入操作系统密钥链或受管密钥服务。

## 从私有到公开的晋升流程

1. **分类**：确认该材料属于项目事实、已确认决策、待验证假设还是个人意见。
2. **脱敏**：移除雇主、客户、合作方、个人信息、预算、职业策略和无关背景。
3. **重构**：从个人叙事改写为可独立理解的背景、决定、理由、边界和验收方式。
4. **证据化**：补充来源、版本、运行环境、测试结果或明确标记“待验证”。
5. **定位公开文件**：产品结论进入 `docs/PRODUCT.md`，架构进入 `docs/ARCHITECTURE.md`，路线进入 `docs/ROADMAP.md`，选型进入 `docs/REFERENCE-PROJECTS.md`。
6. **交叉检查**：更新 README 入口和受影响文档，避免公开文档互相矛盾。
7. **提交前审查**：确认没有私有路径、密钥、真实客户数据、个人敏感信息或被误加入暂存区的文件。

公开文档不得依赖 `private/` 中的链接才能理解，也不得出现指向本地私有文件的 Markdown 链接，因为公开访客无法访问这些目标。

## 公开红线

以下内容不得进入公开仓库、公开 Demo、截图、Issue 或评测报告：

- 雇主或第三方私有代码、Prompt、流程、系统设计和内部术语；
- 真实客户数据、个人信息、通话录音、聊天日志和未授权业务资料；
- API key、访问 token、Cookie、内网地址、账号凭据和真实线路信息；
- 未经确认的合作关系、商业化承诺、合同和价格；
- 把私人研究中的观点冒充已验证事实、行业结论或用户需求。

公开样例默认使用原创或明确授权的材料，并标注“虚构”或“模拟”。截图、日志和评测集需要独立的分享确认，不能因内容已脱敏就自动视为可发布。

## 开源协议

### 开放程度排序（从最开放到最受限）

「开放程度」的判据是**对使用者的限制多少**，尤其两点：能否闭源商用、修改后是否必须开源。

| 档 | 协议 | 可闭源商用 | 主要义务 | OSI 认证开源 |
|---|---|---|---|---|
| 1 · 弃权型 | `MIT-0` · `Unlicense` · `CC0` | 可 | 几乎无（`MIT-0` 连署名都不要求） | 是 |
| 2 · 宽松型 | `MIT` · `BSD-2-Clause` · `BSD-3-Clause` · `ISC` | 可 | 保留版权与许可声明（`BSD-3` 多一条「不得用作者名背书」） | 是 |
| 3 · 宽松型＋专利条款 | **`Apache-2.0`** | 可 | 保留声明 ＋ `NOTICE` 文件 ＋ 标注修改过的文件；**显式授予专利许可**，且对使用者发起专利诉讼即终止授权 | 是 |
| 4 · 弱 copyleft | `MPL-2.0` · `EPL-2.0` · `LGPL-3.0` | 可（限于链接层面） | **被修改的那部分文件**必须开源；仍可与闭源代码组合 | 是 |
| 5 · 强 copyleft | `GPL-2.0` · `GPL-3.0` | 不可 | 衍生作品**整体**必须以同一协议开源 | 是 |
| 6 · 网络 copyleft | `AGPL-3.0` | 不可 | 同 GPL，且**通过网络提供服务也算分发**——SaaS 形态使用同样必须开源 | 是 |
| 7 · 源码可见但非开源 | `BSL-1.1` · `SSPL` · `Elastic License 2.0` · `PolyForm` | 不可 | 带使用与商用限制、期限转换等条款 | **否** |

两处常见误解：

1. **`Apache-2.0` 排在 `MIT` 之后，不是因为它"更不自由"**，而是它**多给了**专利保护、**也多要了**义务（`NOTICE`、标注修改）。对采用方整体是更"重"的协议。
2. **第 7 档不能称作开源。** 采用 `BSL` / `SSPL` 一类，就不能在定位里写"开源"——而本项目已确认「开源」是承诺（见[产品定义 §定位](PRODUCT.md)）。

### 本项目的选择：`Apache-2.0`（2026-10-12 已确认）

理由按已确认的事实推导：

1. **企业要二次开发，且不打算公开自己的改动。** 定位已确认"产研做二次开发后台，增加定制化 / 个性化功能"（[产品定义 §定位 §使用者分层](PRODUCT.md)）。**第 5、6 档会直接把这条路堵死**——`AGPL-3.0` 更进一步，连以 SaaS 形态使用都要求开源。
2. **显式专利授权，对企业内嵌很关键。** 这是 `Apache-2.0` 相对 `MIT` 的主要优势：企业把它嵌进内部系统时，专利风险有明确答案（`MIT` / `BSD` 只有隐含授权）。
3. **与已选依赖一致，无兼容性障碍。** 上游 AgentScope 为 `Apache-2.0`、Pipecat 为 `BSD-2-Clause`，同属宽松型，不存在 copyleft 传染；许可证清单风格也统一（见 `VERSION-PINS.md`）。
4. **保留品牌与商标空间。** `Apache-2.0` 不授予商标权，"Loomrise"这个名称与标识仍归作者控制。
5. **与「是真的开源」一致。** 第 1–3 档都是 OSI 认证的真开源，可以理直气壮地使用"开源"一词。

**什么情况下该改选 `MIT`**：若目标是让采用摩擦**最低**、不在意专利条款与 `NOTICE` 义务。两者都满足本项目需求，差别只在「专利保护 vs 更简洁」。

**开源与商业双轨（已确认）**：核心按 `Apache-2.0` 开源；**保留未来创建需商业化的独立模块的机会**——该模块**另建仓库**、按其自有许可发布。**不要**给现有开源核心改用 `BSL` / `SSPL`——那会让定位里的"开源"变成不成立的表述。

### 落地情况

仓库根目录已建：

- **`LICENSE`**——Apache License 2.0 完整原文（逐字采用官方文本，与上游同款，未做修改）。
- **`NOTICE`**——署名与许可声明（`Copyright 2026 The Loomrise Authors`）。

`NOTICE` 中的版权持有者暂用 **"The Loomrise Authors"**（开源项目常规写法，便于后续加入贡献者或成立主体时无需改动）。若要改为个人姓名或主体名称，改 `NOTICE` 一行即可。

第三方组件的版本与许可证记在 `VERSION-PINS.md`，**不 vendor 进本仓库**。注意 `VERSION-PINS.md` 中的 `Apache-2.0` / `BSD-2-Clause` 分属 **AgentScope / Pipecat**，不是 Loomrise 自己的许可证——Loomrise 自己的许可以本仓库根目录的 `LICENSE` 为准。

## 误提交处理

如果私有内容已经进入 Git 暂存区，先取消暂存并修正规则；如果已经提交到远端，删除文件不足以从历史中移除内容。对于密钥应立即撤销并轮换，对于隐私或雇主材料应先评估影响，再决定是否重写历史、通知相关方或使仓库失效。

不要在公开 Issue 中粘贴待脱敏原文。需要讨论时，应先构造最小且安全的公开问题。

## Agent 提交前检查

- [ ] `private/` 未进入暂存区或公开历史；
- [ ] 文档中的“已实现、已验证、生产级、企业级”等措辞有对应证据；
- [ ] 计划、候选和待验证内容没有被写成事实；
- [ ] 未出现密钥、真实个人数据、雇主内部信息或未授权材料；
- [ ] 公开文档没有依赖本地私有链接；
- [ ] README、PRODUCT、ARCHITECTURE、ROADMAP 和 REFERENCE 的定位一致。
