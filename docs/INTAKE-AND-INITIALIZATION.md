## 1. 议题

两个问题：

1. Loomrise 是否按「数字员工」来对外定位和描述？
2. 一个 Agent（即一个数字员工）的初始化，靠用户在平台上传资料，还是提供 CLI / MCP 让 Agent 直接读本地知识库并在平台创建？

## 2. 定位：谨慎使用「数字员工」这个词

Loomrise 交付的不是「一个像人的员工」，而是**岗位定义 + 培训材料 + 质检 + 上岗审批**这条链路：最终产物是一个可发布、可回滚、可验收的 `AgentVersion`。

| | 数字员工（常见理解） | Loomrise 实际交付 |
|---|---|---|
| 卖点 | 像人、能自主干活 | 说得清、验得过、退得回 |
| 交付物 | 有人设的聊天角色 | 冻结的 `AgentVersion` + 评测证据 + 回滚路径 |
| 验收方式 | 主观体验 | 固定案例回放 + 硬规则裁决 + 人工审批 |

两者不冲突，但首屏只能押一个。若对外用「数字员工」，用户预期会变成「它能不能自己干活」，而当前产品回答的是「它干完的活我能不能验收」。**待决策**：是否把「数字员工」作为对外主说法，或仅作为面向业务方的通俗类比，产品文档内仍用 `ScenarioPack` / `AgentVersion` 等对象名。

## 3. 一个数字员工当前是如何被创建的

以 `scenarios/course_consult_v1/pack.json` 为证据（S1 已落地）：

| 组成 | 现状 |
|---|---|
| `agent_version` | 模型及版本、合同版本、`skill_ids`(2)、`tool_ids`(2)、`rule_ids`(4)、`context_budget_tokens` |
| `routing` | 两条业务请求路由（课程咨询预约 / 退款），每条 3–6 步 |
| `skills` / `tools` / `rules` | 2 个 Skill、2 个工具（含一个模拟写入）、4 条模型外硬规则 |
| `fragments` | 8 个可引用知识片段 |
| `cases/` | 11 个人工审定真值（成功、资料缺失、拒绝、工具报错、重复写入、取消、预算截断等） |

创建链路即[六层配置合同](CONFIGURATION-LAYERS.md)的填充与冻结：

```text
获授权资料 → 六层配置（上下文/路由/Skill/硬规则/工具策略/业务结果）
          → 试用（文字/语音）→ 坏例 → 回放 → 人工审批 → 发布可回滚版本
```

S1 中这一步是手写 `pack.json` + `python -m loomrise.cli replay`（干净环境 11/11 确定性案例通过）；S2 才把它变成工作台向导。**初始化通道要解决的，正是第一步「获授权资料 → 六层配置」怎么走。**

## 4. 网页与本地摄入分工（方向已确认，未实现）

| 通道 | 目标用途 | 边界与状态 |
|---|---|---|
| 网页 FAQ / URL / File | 非开发者初始化客服知识、维护资料；查看解析和索引状态 | S2-a 产品范围。声明来源、授权、有效期与撤销入口；FAQ 编辑或资料替换产生新版本，不覆盖已发布知识 |
| 可选 CLI | 本地目录和已有知识库的批量导入、脚本化处理与可复现产物 | 共用来源与草稿合同；具体命令尚是草案，不要求用户先装 CLI 才能创建客服 |
| MCP + 配套 Skills | 第三方 Agent 读取授权资产、创建受限草稿、提交候选和执行沙盒检查 | S2-a P0 方向已确认。仅暴露获授权资源与候选工具；不开放生产业务写入或直接发布，不提供未消费 blind 或凭据；原生 Skills 与本地技能包兼容分别验证 |

两种摄入方式都需要处理资料进入服务端、模型或检索供应商的实际数据路径。本地扫描不等于有权使用，也不能据此承诺数据始终留在本地。

## 5. 已确认方向与待定实现

1. S2-a 提供网页 FAQ、URL、File 摄入和解析/索引/失败状态。上传承担初始化与持续维护，旧“只作协作入口、不承担初始化”的建议不再适用。
2. CLI 保留为可选批量通道，与网页使用同一来源、版本与授权合同。具体 CLI 与 MCP 接口尚未实现。
3. 摄入与发布分开。解析或索引成功只证明资料可供检索；生成的 Agent 配置进入草稿，引用变更使受影响的验收证据待重验。
4. MCP 受限草稿／候选写入已纳入 S2-a P0，具体字段、工具名和认证待合同登记；与网页共用 revision、来源、幂等和权限。外部 Agent 可创建草稿与提交建议，人工锁定项和候选采用权仍由工作台管理；发布不开放给普通创作 Agent。

工具声明导入与知识摄入是不同接入合同。MCP/OpenAPI 工具声明仍须映射为 ToolManifest 并通过沙盒验证，不能借知识上传授予执行权限。

本节对外 MCP 让第三方 Agent 使用 Loomrise 的配置与候选能力；Loomrise 连接第三方 MCP 工具则属于上述工具声明接入。两个方向分别授权，外部创建权限不自动变成客服执行权限。

### 5.1 可选初始化助手与完整手动路径

2026-10-14 已确认体验原则，未实现：用户可完整手动创建，也可请初始化助手整理授权资料并提出候选；助手不是必经流程。手动方式不依赖生成会话或助手连接，两种方式共用草稿、来源、校验与发布门禁。关闭或失败后仍能继续手动编辑，不丢已采用内容，也不静默覆盖人工修改。

先以用户自己的有效授权资料完成客服答疑试用，再接真实业务工具；无写工具不阻断纯 FAQ 创建。缺有效模型连接时可保存草稿或明确使用脚本模拟，模拟不冒充基于自有资料的真实 AI 答疑。品牌、完整 SOP 与工具映射按需补齐；来源授权、有效期、真实数据去向和风险确认仍必须可见。详细配置保留完整查看与获准手动编辑入口。具体布局、候选处理与需求分期见[配置后台体验优化](CONFIGURATION-UX-OPTIMIZATION.md)。

## 6. 三条硬约束（先钉死，再谈实现）

1. **本地 ≠ 有权。** 摄入时必须强制写入 `source_ref`、权利范围、有效期和撤销入口。没有来源标记，就无法定位「资料撤销后哪些已验证结论必须失效」——这是[产品形态与开放接入规范](PRODUCT-FORM-AND-INTEGRATION.md)中已经写死的规则。
2. **各摄入通道生成的配置一律是草稿或 `candidate`，不是 `published`。** 一旦本地命令能直接造出已发布员工，S2 的审批与回滚链路即被绕过。留一个 `propose` 动作送审即可。
3. **摄入产物复用既有对象，不新增概念。** 切分结果进 `fragments`（`ContextSnapshot` 的可引用事实），生成结果进 `AgentSpec` 草稿；知识库是可审阅事实，会话记忆是带来源与有效期的上下文，两者不互相自动升级（见[产品定义](PRODUCT.md)）。

## 7. 可选本地接口草案（命名待定、未实现）

```bash
loomrise init --from-local <dir> --scope <授权范围>   # 只扫描、出 source manifest，未确认不摄入
loomrise ingest <manifest> --confirm-rights           # 切分 → fragments（带 source_ref/版本/有效期）
loomrise spec draft --pack <id>                       # 生成六层配置草稿，candidate 态
loomrise propose --version <id>                       # 提交审批，不发布
# 发布仍由人工在工作台或显式命令完成，绑定审批人与 EvalSet 版本
```

MCP 侧（原只读草案保留，新增受限创建方向已确认；下列名称待合同登记，未实现）：

| 类型 | 名称 | 说明 |
|---|---|---|
| resource | 场景包 / `AgentVersion` / `EvalSet` | 只读暴露，含版本与状态 |
| tool | `replay` | 固定案例回放，返回结果与差异 |
| tool | `audit` | 回答加载了什么、跳过了什么、为什么、是否预算截断 |
| tool | `diff` | 旧版与候选版的结构化差异 |
| tool | 创建草稿 / 提交候选 / 校验 / 沙盒试用 | S2-a P0；统一授权、revision、幂等与证据，不直接采用人工锁定项或发布 |
| skill | 创建客服草稿 / 诊断失败 / 生成并验证改动候选 | 分别在 S2-a、S2-b、S2-c 建设；外部使用指导与内部 `SkillManifest` 分开管理 |

## 8. 待决策项

1. 「数字员工」是否作为对外主说法（§2）。
2. 网页摄入的字段、大小/数量上限、解析任务与索引状态合同；具体阈值待登记，不照搬其他平台限制。
3. MCP 草稿／候选写入已定 S2-a；具体身份、授权粒度、字段和原生 Skills 支持矩阵待验证。S2-c 发布继续由独立评测与人工审批，不开放给普通创作 Agent。
4. `init` 阶段的授权声明形式：命令参数、manifest 文件，还是交互式确认。
5. 本地知识库的范围边界：只读扫描还是允许 Loomrise 写回（当前建议只读）。
