## 0. 结论

**前端信息架构与交互已明显领先于正式配置服务；当前下一步是先把现有配置面接入 R1 共用服务，再按 R2 → R3 → R4 → R5 逐段解锁能力。** 不再把“界面上能点”当成“对应版本能力已交付”。

1. 本地原型已落地并验证两平面导航：工作区是专家列表及物料库、模型连接、部署维护三个资源直达入口；专家内是 7 个工作面 + 专家设置，并有返回工作区、折叠侧栏、窄屏抽屉和历史导航。最新导航批次记录 `212/212` 单测通过，桌面与手机交互验证见报告；这不是候选稿中的平台设置聚合，也不是服务端功能。
2. 配置仍由本地 `localStorage` 驱动；知识摄入、流程图、测试、上线等视图中的可变状态仍是原型状态机，没有配置读写 API 或服务端版本权威。
3. 后端已验证的是 R1 的部分底座：WP1 完成，WP2 与 WP7 部分完成；事件接纳新增测试只是这些工作包的子集。配置版本/差异、流程清单与规则、入向 MCP、CLI 同合同、后台共享服务联调尚未完成，不能据此称 R1 或 WP9 完成。
4. [S2-SIDEBAR-SPEC](S2-SIDEBAR-SPEC.md) 是候选稿。本文将其 S2-a/b/c、S3/S4 映射到 RELEASE-PLAN 的 R1/R2/R3/R4/R5a/R5b 作为排期讨论，不把两套编号视为天然等价；冲突处列在 §6。

## 2. 导航候选如何进入后续计划

当前可作为已验证原型基线的是**两平面关系与现有入口**，不是终态候选树整体。后续新增菜单必须等相应产品范围和服务能力进入计划后再做。

| 候选阶段 | 侧栏稿提出的界面变化 | 当前状态与规划边界 |
|---|---|---|
| S2-a | 专家列表；专家内 7 个工作面与专家设置；设置中的工具/连接、模型/语音聚合为工作区平台设置；变更仍放在单专家上线页 | 两平面与专家内 7+设置已部分实现；物料、模型连接、部署维护目前仍独立直达。平台设置聚合是候选，不与当前资源入口等同 |
| S2-b | 搜索与新建、完整摄入、流程画布、测试中的判据/人工评分 tab；不增加专家平面菜单数 | 当前部分 UI 已存在本地形态；搜索、正式摄入/索引、R3 画布与判据能力需按服务 Gate 验收。S2-b 与 R2 摄入的分期差异见 §6 |
| S2-c | 任务与主动服务菜单；真实办理、发布 Gate 与回滚留痕 | 本地配置/模拟不能替代 R4 业务执行、配对评测、审批与回滚 |
| S3 | 工作区级变更、完整平台设置、成员权限、系统诊断与首云 | 侧栏候选；按 R5a 范围和另行确认的导航决策实施 |

`S2-a/b/c` 描述产品与导航候选阶段；`R1/R2/R3/R4` 是有 Gate 的交付版本。只有 RELEASE-PLAN 与 Gate 矩阵可以确定正式版本顺序和退出条件。

## 3. 后续迭代计划

计划按依赖顺序推进。每批可做对应的前端连接与必要的交互修正，但不得为了让原型“看起来完整”而提前实现后续版本的可执行语义。

### I0 · 范围对齐与原型边界

**目的：** 在 R1 页面联调前，确定哪些本地页面是服务客户端、哪些仍是独立演示，并消解 §6 的文档差异。

| 工作 | 出口判据 |
|---|---|
| 按当前两平面路由、页面、状态和写入动作建立“页面/动作 → 应用服务用例或本地演示”映射；不预设每个 `dispatch` 都能一对一变成 API | 映射表覆盖配置保存、校验、冻结候选、知识/物料、测试、上线等现有写入动作；未映射项明确标本地演示或后续版本 |
| 对照 D3 字段目录、六层合同、R1-WP4 清单边界，标出不可映射字段 | 未确认/不可映射的数据只读保留，不静默丢弃或转换；`routeGraph` 不进入 R1 可执行配置 |
| 与权威计划协调 WP9 页面范围、侧栏候选的阶段划分和导航行为 | 确认前不修改 RELEASE-PLAN/ROADMAP，不将平台设置聚合、S2-b 全量行为或 S3 入口当成已批准范围 |
| 给本地模拟的批准、发布、回滚、运行结果加清楚的演示边界；布局/键盘/无障碍修复可继续 | 原型可验证 UI，但任何本地状态变化均不被描述为服务端批准、发布或运行成功 |

### I1 · R1：能配，完成配置主链

**主依据：** [RELEASE-PLAN §R1](RELEASE-PLAN.md) 及 `R1-WP1…WP9`。本轮先补服务端权威和跨入口一致性，不做画布或正式发布。

| 顺序/责任面 | 迭代内容 |
|---|---|
| 服务端与合同 | 在已完成/部分完成的 WP1/WP2/WP7 基础上，完成 WP3 版本与字段级 diff、WP4 单元清单/判定规则及字段路径校验；按 R1 完成 WP5 Task 蓝图所需范围。字段与 Schema 服从 D3、六层合同和相应权威设计，不按原型字段随意扩列 |
| 共享入口 | 完成 WP6 入向 MCP 受限草稿/候选写入、WP8 最小 CLI 同合同；使用 AGI-01 和 RELEASE-PLAN 定义的统一应用服务及接口，不在本文预定未确认的端点、存储形状或供应商协议 |
| 配置前端 | WP9 将专家列表与配置页改为共享服务客户端：真实读取、草稿保存、字段路径校验、服务端 revision 冲突、字段级 diff、冻结候选、稳定历史只读；加载/保存/冲突/只读/服务错误要有明确状态 |
| 导航边界 | 保持现有两平面原型作为候选实现基线；未确认前不把三个工作区资源直达入口强行合并为平台设置。R1 页面不出现可执行审批/生产发布/回滚 |
| 出口 | 网页、CLI、MCP 读写同一服务端草稿/revision；两个入口基于同 revision 保存时旧写入被服务端拒绝并能在 UI 展示；服务重启后数据不变；非法字段在入口间返回同一字段路径；冻结候选后不改稳定版本 |

**依赖顺序：** 按 RELEASE-PLAN，WP1 → WP2；WP1 → WP3 → WP4；WP1 → WP5；WP3 → WP6 → WP8；WP1/WP6 → WP7；WP9 等 WP3/WP4/WP6/WP8 与共享服务就绪。WP5 按 RELEASE-PLAN 纳入 R1，不因侧栏“任务与主动服务”排在 S2-c 而误删或提前开放菜单。R1 退出仍逐行看 `M-A-01…04 / 06 / 16…18` 及 Gate 矩阵，不以 WP9 联调代替整个 R1。

### I2 · R2：能跑，配置进入最小运行闭环

**主依据：** [RELEASE-PLAN §R2](RELEASE-PLAN.md)。S2-a 后批，必须以前置 R1 完成为条件。

| 工作面 | 迭代内容 |
|---|---|
| 发布与运行 | 最小沙盒发布、指定版本入口绑定、发布前检查；草稿不生效。将现有本地上线控件接到服务状态，但不提供本地伪成功 |
| 知识摄入 | FAQ/URL/File 解析状态、失败/重试、撤回及索引/缓存失效、受影响版本待重验。浏览器解析可保留为预览，不作为正式导入结果权威 |
| 物料 | 上传/下载/恢复、资产/授权/版本/原件分离、人工发送前重验；现有工作区入口与候选平台设置聚合分开核算 |
| 客服入口 | 最小 Widget + Inbox 文本往返、人工接管和最小身份隔离；不做完整 Contact Page、Telegram/Email 或完整展示 |
| 出口 | 按 `M-A-01…18` 父 Gate 逐行签核；撤回能阻止后续检索；入口实际绑定指定 AgentVersion；运行态失败、未知、取消与结果 ID 可区分。仅本地 UI 回归不计 Gate 证据 |

### I3 · R3 / S2-b：扩展客服和组织图

R2 完成并满足 [RELEASE-PLAN §R3 画布开工合格标准](RELEASE-PLAN.md) 后实施。已有图形 UI 只作为交互原型，R1 仍不得保存或执行图语义。

- 完成图/清单/规则三投影、端口与边界事件、嵌套单元、`waits`、执行环与 `max_rounds`、`concurrent` 单元和闭集提示；图执行语义与校验按 R3 合同实现。
- 完成 R3 的完整网页客服、联系页、完整 Widget、授权沙盒渠道与运行叠加。
- 侧栏候选的全局搜索、测试判据/人工评分 tab 等若通过产品确认，落在既有入口内，不重复增加菜单。全量摄入在候选稿写作 S2-b、而 RELEASE-PLAN 已纳入 R2；实施排期以 §6 协调后的权威版本归属为准。
- 出口：R3 工作包与客服矩阵有对应工件；画布按任务测试与既定 Gate 验收，未达标准时保留清单投影，不以画布存在本身宣称体验通过。

### I4 · R4 / S2-c：真实办理与受控改进

- 真实工具沙盒与外部结果 ID、路径断言、配对评测、C6 不相交校验、候选改进/审批/发布/回滚及语音/自动发送，依 RELEASE-PLAN R4 WP1–WP6 实施。
- 专家平面增加“任务与主动服务”入口前，明确其承载 `TaskBlueprint`/`TaskItem` 的哪些配置和事实；不得与 `ServiceRequest`、上游 RuntimeTask 混为同一对象。
- 上线页的本地“批准/发布/回退”转换为真实状态前，须由服务端门禁裁决并留证；生产发布不由前端或模型自动批准。
- 出口：`M-C-01…10` 与 `M-S1-15/16` 按矩阵逐行通过；一条端到端坏例只作为必要、不充分证据。

### I5 · R5a/S3 与 R5b/S4：部署、身份和多云

- **R5a/S3：** 发行包、首云模板、生命周期与费用/护栏；另按已确认范围增加工作区“变更”、平台成员权限、系统诊断等入口。平台设置聚合和“变更”是否及何时上侧栏仍需范围对齐。
- **R5b/S4：** 在首云发行包验收后扩第二朵云与新渠道；工作区切换器/租户选择如获确认，不提前作为当前单租户原型必需项。
- 两个版本分别留独立 Gate 证据；首云不能代替多云验收，多租户和跨专家知识也不因侧栏有相应入口而自动成立。

## 5. 待决策与建议

以下建议均为提案，不在本文中视为已确认：

| 编号 | 决策 | 建议 | 未决影响 |
|---|---|---|---|
| D-1 | R1 WP9 前端范围是否以当前已验证的两平面页面为原型基线 | 建议以当前原型为实现起点，但按 D3、六层合同和 R1-WP4 重映射字段；正式替代 RELEASE-PLAN 旧 IA 描述前需产品确认 | 不确认就可能出现 WP9 按旧四组/三深度验收，而代码沿当前两平面推进 |
| D-2 | 新 UI 功能与服务接入的先后 | 建议暂停没有后端对应的“可执行成功”模拟；继续缺陷修复、无障碍/响应式走查和与 R1 状态联调有关的 UI 工作，不冻结所有前端工作到 R2 | 若继续无 Gate 的新模拟能力，页面状态和服务能力差距会继续扩大 |
| D-3 | `localStorage` 最终用途 | R1 服务模式中配置权威必须是共用服务，不能在服务失败时静默写回本地；本地演示和 UI 偏好（如侧栏折叠）可继续本地存储。离线快照是否只读及其长期保留策略另确认 | 避免同一配置同时有服务端与浏览器两个权威 |
| D-4 | 配置字段目录与旧原型字段映射 | 以权威 D3/六层合同为准；不可映射内容保留并只读，等待有明确迁移规则再写回 | 防止 WP9 静默丢字段或把图能力提前塞入 R1 |
| D-5 | 侧栏候选规范的采用范围 | 建议逐项采纳，不整体升为已确认：先批准菜单名/聚合/行为，再更新 IA、差距需求与 WP9 验收 | 不确认时保留当前已经验证的两平面和资源直达入口 |

## 7. 风险与不做

- 不在 R1 把 `routeGraph` 当可执行配置；R1-WP4 仍是单元清单与规则，`Unit.body` 仅按权威计划预留，图工作面按 R3。
- 不把 localStorage、本地浏览器解析、测试快照、批准按钮或本地发布状态机作为后端验收证据。
- 不因侧栏候选增加“任务”“变更”“平台设置”入口就新增领域对象、授权、跨专家共享知识或服务承诺。
- 不用 R1 页面联调代替 R1 父 Gate；不把 S2-alpha UI 完整度称为正式 S2 退出。
- 不在服务、数据作用域与授权合同尚未验证前接入真实外部写入、生产发布或多租户。

主要风险是把“本地原型能力”误判为“后端已实现”，或因侧栏候选更新而出现一套菜单、另一套 Gate 的双重路线图。缓解方式是每个 UI 页面同时标明当前数据源、对应 R/WP、对应 Gate 证据与未实现状态。
