## 1. 移植过来的那一句话

> 只要能把一件事量出来，就能把它变快；所以杠杆最高的事是**找到更多能数的东西**，并确认你数的就是用户感受到的。

在 Loomrise 落成三条配套，缺一条就变成"刷指标"：

1. **每个指标先自证**：至少两次改动里，该计数降了、用户体感时延也降了。证明不了就下线，不让 Agent 去爬一座错的山。
2. **棘轮锁战果**：赢下来的数字写进基线，之后只许降不许升；让它变差的改动不得合入。
3. **护栏与掌舵**：改动有审批、有回放、有开关；人负责野心、品味、方向。

## 2. 三条本地裁决（与既有纪律对齐）

这一节是本文档最需要先读的部分，因为直接搬方法会和项目已有纪律冲突。

### 2.1 棘轮上限 ≠ Gate 阈值

| | 棘轮上限 | Gate 阈值 |
|---|---|---|
| 来源 | **实测基线**导出（可以有样本量、有抖动） | **跑测前登记**（六项齐全，见验证计划 §0） |
| 回答 | 有没有比以前差 | 够不够格过门 |
| 变化 | 只许降；变快就自动下调 | 一轮一登记，不倒填 |
| 失败含义 | 有改动退步，需说明或回退 | 本阶段不能退出 |

**过了棘轮不等于达标**，达标仍看 Gate；**Gate 阈值也不能从棘轮值反推**，那正是"根据结果倒填"。
两者共用同一批埋点，但裁决口径分开写、分开存。

### 2.2 可数 ≠ 该数

语音里最容易数错的是"服务端发了多少包"。它确定、好压、看着像进步，但用户听不见。
判据沿用 [D-03](VOICE-ARCHITECTURE-DECISIONS.md)：**服务端生成完成 ≠ 已送达，以客户端 `playback.started` 为准**。
所以任何以"首包已发出"为主语的指标，必须同时登记客户端回执段；没有回执的会话不得计入结论。

### 2.3 快 ≠ 对

延迟优化在语音里会直接换成体验取舍：首响更快常意味着更早插话，判定窗更短常意味着更多误停，按句合成更早出声但韵律更差。
这些不是 benchmark 能裁决的，必须由人拍板，并按 [D-02](VOICE-ARCHITECTURE-DECISIONS.md) 的配对逻辑**成对登记**——只压一边，另一边必然顶上来。

## 3. 三档指标口径

真实耗时噪音大，适合当结论，不适合当每一步的闸门；确定性计数稳定，适合当闸门，但不能单独当结论。

| 档 | 网页 | 语音通话 | 用途 | 进棘轮 |
|---|---|---|---|---|
| **墙钟** | 打开到能打字的 p75（冷缓存、限速、交替配对） | 用户说完到听见第一个可懂音节的 p75（真实设备与网络） | 结论 | 可以，但要求同条件配对测 |
| **确定性计数** | 关键路径请求数、阻塞脚本数、首屏字节、外域来源数 | 串行档数、首包字节、字符数、丢弃字节、回退次数 | 每一步的闸门 | 优先 |
| **线上真实用户** | 真实访客 p75 | 真实通话 p75 | 最终判据 | 需真实流量；当前缺 |

项目现状：语音的墙钟只在**服务端链路**上有样本（[基线](reports/PERF-BASELINE-2026-10-30.md) §3），浏览器整链只有 1 个回执样本；网页墙钟尚未测，只有结构计数。**这三档不能互相顶替**。

## 4. 语音通话：把"延迟"拆成能数的段

### 4.1 先定义终点

对标文章里的"打开到能用"，语音的终点是：**用户听到第一个能听懂的音节**，不是"服务端开始合成"，也不是"浏览器收到第一块 PCM"。
骨架屏式的骗法在语音里对应"我先播个提示音或占位语气词"，这类改动必须显式标注为**体验设计**，不得计入首响指标。

### 4.2 分段与两个测量缺口

一轮对话切六段，全部落在会话时钟内（`web.py:voice_ws` 的 `t_ms`）：

```text
[用户说完]→(A)→[最终文本]→(B)→[轮次结束]→(C)→[发起合成]→(D)→[首个音频包]→(E)→[客户端可听]→(F)→[整句播完]
```

| 段 | 含义 | 现状 |
|---|---|---|
| A final→closed | 客户端何时宣布"说完了" | 可测；受客户端 `asr.stop` 时机支配，属交互设计 |
| B closed→tts.request | 业务链路（路由/模型/工具/确认） | 可测；当前走脚本模型，**接真实模型后才是真数字** |
| C tts.request→tts.first_audio | TTS 首包 | 可测；目前最大的一段 |
| D first_audio→playback | 客户端调度到可听 | 可测，但只有 1 个样本 |
| E first_audio→done | 整句播完 | 可测 |
| — 说完→最终文本 | 识别侧时延 | **不可测**，见缺口一 |

**缺口一：识别流时钟与会话时钟不同源。**
`asr.final.end_ms` 属于识别流内部时钟，`t_ms` 属于 WebSocket 会话时钟。用 `asr.open` 当原点做了个近似，结果出现 **负值**——直接证明该假设不成立（[基线](reports/PERF-BASELINE-2026-10-30.md) §4）。修法很小：在 `asr.final` 上带一个 `stream_started_t_ms`，或在服务端记录首帧音频的会话时刻。**这是当前最高杠杆的一件事**——因为全链最大的一段现在完全在黑箱里，而它可能比 C 段大一个量级。

**缺口二：客户端回执覆盖不足。**
9 个 trace 里只有 1 个带 `client.playback.first_audio`。没有回执就没有"可听"这条线，D 段永远只有一个点。

### 4.3 语音侧的确定性计数（新增，与统计指标并列）

| 计数 | 为什么数它 | 当前值（重算） |
|---|---|---|
| 业务链路**串行档数**（closed→request 之间的标记数） | 每多一个串行阶段就多一条 p95 尾巴；这个数不随机器抖动 | 上限 1 |
| 首包字节 / 首帧大小 | 首帧越小出声越早；可验证地挂钩首包时延 | 上限 11744 B |
| 合成字符数 | 判断是否真的按句切分（长文本首包更晚） | 上限 53 字 |
| 背压丢弃字节 | 已在 D-05 定为显式计数上报 | 历史会话合计 50880 B |
| 热路径上的账本提交次数 | 首响路径上若有同步落盘，先数它再谈优化 | 未统计（缺口） |

这些计数**不替代** p75，只做闸门：先看计数有没有降，再看墙钟有没有跟着降，两次都对才保留。

### 4.4 首批候选线程（估计值，全部未验证）

按"先补测量、再动代码"排序。**收益一列是假设，不是结论**；每条都要先写假设、再测。

| # | 线程 | 假设 | 影响段 | 风险 |
|---|---|---|---|---|
| V-1 | 补识别侧时钟字段 | 拿到"说完→最终文本"的真实数字，判断它是否才是主因 | A 之前 | 协议小改，需同步 `web.py` 注释与测试 |
| V-2 | 客户端回执常态化 | 让 D 段有足够样本，避免用服务端数冒充可听 | D | 无 |
| V-3 | 合成连接预热 | closed 后立刻建连、不等文本，压 B+C 的固定开销 | C 前半 | 失败时占资源；需超时与回收 |
| V-4 | 首句短合成 | 先出短确认语再出正文，改善感知首响 | C | **话术变更，属品味，必须人拍板**；且不得计入首响指标 |
| V-5 | 客户端播放调度 | AudioContext 预激活、首帧提前调度 | D | 需真实设备，本地回环数字无效 |
| V-6 | 判定窗与首响的取舍 | 缩短"停—判—续"判定窗换取更快恢复 | 打断恢复 | 误停上升；按 D-03 §3.2 三项成对登记 |

**V-3 之前的硬前置**：V-1/V-2 没做之前，任何"首响降低了 X%"都不能作为结论——因为你不知道总时延里有多大一块根本没测到。

### 4.5 语音延迟招式库（含与既有决策的冲突）

按分段挑，不要照单全抓。**"冲突"一列是这张表的主要价值**：不少通用提速招式会直接撞上 D-05 已经踩过的坑。

| 招式 | 影响段 | 前提与风险 | 与既有决策的关系 |
|---|---|---|---|
| 边生成边合成（按句切分，出一句合一句） | C | 句切得碎，韵律变差 | 与 D-05 第 3 条"一句一个 TTS 实例"**一致**，是它的正向用法 |
| 首句切短（第一句单独短切） | C | 首句可能语义不完整，听起来断 | 需话术配合，属品味 |
| TTS 连接预热（建连、鉴权前移，每句仍是新实例） | C 固定开销 | 空闲连接要回收；不能变成跨句长连接 | **不是**"D-05 禁止的长连接跨句合成"，但要在实现里写清边界，否则一次"优化"就把打断能力弄丢 |
| 收到 partial 只做**预热**，不提交 | B | 提交过早会截断用户的话 | D-05 第 1 条：`final` 只是句尾，轮次结束由 `asr.closed` 决定；**任何"收到 final 就提交"的写法都是回归** |
| 首响路径上的账本写盘改为批量/异步 | B | 丢事件的代价远大于省下的毫秒；必须有落盘保证 | 事件账本是权威，不能用性能换掉；先数提交次数再谈 |
| 重检索/工具调用挪到后台委派 | B | 需要"先说一句"填空 | 与 [D-04](VOICE-ARCHITECTURE-DECISIONS.md) 同一时序；插入时机受播报窗口约束 |
| 客户端 AudioContext 常驻 + 首帧预调度 | D | 浏览器自动播放策略、切后台被挂起 | 本机回环测不出真实效果，必须真机 |
| 缩短"停—判—续"判定窗 | 打断恢复 | 误停上升、复读风险 | D-03 §3.3 已把判定窗列为待验项并随版本冻结，改它要重跑配对指标 |

**不许做的三个"提速"**：跨句长连接合成（毁掉按句打断）、收到 `final` 就提交（截断用户）、浏览器回退合成冒充服务端（D-05 第 4 条：凭据缺失必须显式失败）。

### 4.6 语音特有的"品味"清单（不许由 score 自动决定）

- 按句合成 vs 整段合成：早出声 vs 韵律自然
- 首响优化 vs 打断灵敏度：快 vs 稳
- 短确认语：像人 vs 像话术
- 后台委派的等待话术（[D-04](VOICE-ARCHITECTURE-DECISIONS.md)）：先说一句 vs 静默等待
- 误停后的续播方式：断点续 vs 重组

每一条都要有配对指标同时看，否则优化一头必然顶起另一头。

## 6. Agent 持续做工程优化的运行协议

这是文章里最值得抄的部分：不是"让 Agent 优化一次"，而是把优化变成**可以并行、可以停、可以验收的常规工序**。

**一条线程 = 一个指标 + 一个具名的人。**

1. **开工简报**（一次）：哪几条路径最重要、每条路径"能用/能听"的定义、哪些不能动（视觉、话术、Gate 阈值、硬规则）、谁批准上线。
2. **取基线**：`voice_latency_report.py` / `web_perf_probe.py` → `runs/perf/`。没有基线不动手。
3. **先棘轮，后改代码**：棘轮没建起来就开改，等于让战果在后续改动里悄悄流失。
4. **指标自证**：每个新计数至少配两次改动，证明它降了、墙钟也降了。证不出来就下线。
5. **爬山**：一次一个假设、一个最小改动、一个 commit。没变快就回退，不留"可能有用"的改动。
6. **记账**：`runs/perf/<thread>/log.md` 记假设、改动、计数、前后 p75、保留或回退。**这是唯一的事实来源**，聊天记录不算。
7. **三件事归人**：野心（目标不是终点，达标后继续问"下一个是什么"）、品味（§4.6）、方向（几百行换几毫秒的，主动提议不做；边际收益递减的线程主动关掉）。
8. **收口**：配对测量 + 人批准 + 写明回滚办法。

**并发纪律**：先有护栏再扩线程。护栏指——棘轮在跑、固定回放 11/11 绿、后端回归全绿、改动可回退。护栏不全时同时开多条线程，只会得到一堆互相踩脚的假数字（文章的 8 个 agent 烧光额度是同一类代价）。

## 8. 别这样（本地化版）

- 用"服务端已发首包"当"用户已听见"——语音版的骨架屏骗子。
- 用合成音频 5 倍实时推流冒充真实语速（`scripts/voice_latency_sample.py` 开头自己写着不是真实语速）。
- 跨模型、跨网络、跨设备混算一个 p75；换模型后拿旧基线比。
- 只跑一轮、报平均数、不报 n。
- 没棘轮就开改；棘轮红了却"顺手"把上限调高。
- 为几毫秒引入难维护的复杂度（原文里 900 行只换 2ms，一句话就毙掉）。
- 改了用户能感知的行为（话术、打断灵敏度、复读）没告诉人。
- 没批准就上线、改 Gate 阈值、把候选判据写成已确认。
