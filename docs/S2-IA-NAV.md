# Loomrise 平台信息架构与主菜单定义 v0.12

状态：**设计草案，待确认**。2026-09-30。

本文定义 S2 工作台的信息架构与导航——**主菜单的一级域、二级页、专家详情与版本详情的 tab，以及每个页面的核心功能与优先级**。它取代 [S2 工作台界面设计](S2-UI-DESIGN.md) v0.2 的 §2「信息架构」（该节按「旅程分区」组织，已确认为结构性问题）。

本文只定义**信息架构与导航**，不改动 S2-UI-DESIGN 中已确认的界面约束（两栏证据分离、比例只读、七态常驻等）。对象权威见 [架构与对象权威](ARCHITECTURE.md)，六层职责见 [六层配置合同](CONFIGURATION-LAYERS.md)，范围边界见 [S2 范围讨论记录](S2-SCOPE-DECISIONS.md)。

> 本文件只保留**现行结论**，不记录逐版修订过程。改动历史见 git。

**计数**：一级域 **6** · 二级页 **16** · 专家详情 tab **3** + 版本详情 tab **3**（+ 页头模型状态条 1）· §4.7 面数 **22**。

**前置依赖**：S1 退出 Gate 未闭合（真实音频链路、真实模型端到端留档待补）。S2 工作台依赖执行内核，但信息架构、页面清单与优先级可以现在定稿。

## 0. 结论速览

**总判据：一级菜单回答「管哪一类东西」，二级归属回答「这东西归谁管」。** 参考项目的配置化平台一律用「对象域」做一级轴线，不是「流程阶段」。

四条结论：

1. **一级菜单为 6 个对象域**：**专家** / 运行 / 验收 / 变更 / 知识 / 设置。旅程（建 → 试 → 看 → 改 → 验 → 批 → 滚）不进菜单，改由**顶部流程指示条 + 专家概览的「待办」**承载。
2. **专家详情是三层，配置挂在「版本」上。** 专家列表 → **专家详情**（概览 / **版本** / 流量）→ **版本详情**（人设 / 流程 / 边界）。**选中专家后第一屏是版本列表，不是配置**——配置的宿主是「某个专家的某个版本」（§1.2-4），所以点进某个版本，才是那一版的配置。稳定版本**只读**，要改先"从稳定版本新建草稿"。**两层之间给一条直通车**：专家列表与版本列表上的**「稳定版本 / 最新版本」两枚指针**可一键直达版本详情，不必逐层点进（§4.3.3）。
3. **补齐 5 个此前没有落点的权威对象**：工具注册表（`ToolManifest` + 连接引用）、技能与流程（`SkillManifest`）、审批档位（`PolicyProfile`）、依据追溯、数据看板。
4. **合并单页分区**：试用并入运行域（主入口在**版本详情**，独立页保留作通用入口）；**「交付」不是页面**——导出降为**版本上的动作**、恢复校验归系统诊断、交付包归第三条体验（§4.2 ① 注）；专家概览由「首页」降为「专家详情的一个 tab」。

**目标菜单树**（改动处标 `←新` / `←迁移` / `←改名`；完整表格见 §4.6，页面核心功能见 §4.7）：

```text
交付与验证
  专家   `experts`        专家列表(P0) · 新建专家(P0)
                          └ 专家详情（3 tab，不占菜单）
                             概览(P0) · 版本(P0) · 流量(P1)
                          └ 版本详情（3 tab + 页头状态条，不占菜单）
                             人设(P0) · 流程(P0) · 边界(P0)
                             〔页头〕模型状态条：gpt-6-sol（跟随平台默认）→ 可覆盖
                          ※ 快捷指针（不占菜单）：稳定版本 / 最新版本 → 一键直达版本详情
  运行   `runs`           数据看板(P0) · 试用台(P0) · 依据追溯(P1，S2-a 不进菜单)
  验收   `acceptance`     案例集(P0) · 回放验证(P0) · 案例标注(P0)

治理
  变更   `changes`        待我审批(P0) · 版本与发布(P0) · 审批档位(P1)

平台                       ← 被所有专家共用、与版本无关；改一次影响全局
  知识   `knowledge`      业务知识(P1) · 文件与物料(P2)
  设置   `settings`       工具与连接(P1) · 模型(P1) · 系统诊断(P2)

（开发者模式 = 全局开关，不占菜单）
```

**界面文字与领域合同名是两套东西。** 合同名（`ScenarioPack`、`AgentSpec`、`ChangeProposal`）只在文档与代码里出现；界面只用用户一眼能懂的业务词——`ScenarioPack` 的界面名是**「专家」**。映射与理由见 §4.5。

**两条跨文档的口径**：

- **分组顺序 = 「按天看的在前、偶尔改的在后」**：交付与验证每天用，治理有审批就来，平台极少动。
- **详情页是三层，不是重复**：二级页（列表 / 向导）**不选具体专家也能打开**；专家详情 tab **选中专家才存在**；版本详情 tab **选中某个版本才存在**。全部 tab 用前缀匹配回指同一个菜单 key（§1.3）。

## 1. 参考项目的组织规律（实测）

依据：本地浅克隆的三个开源项目源码（2026-09-26 索引）＋ 一份真实在跑的企业 Agent 中台后台（2026-09-28 实测）。

### 1.1 六条组织规律

| # | 规律 | 证据 |
|---|---|---|
| 1 | **一级导航 = 对象域，不是流程阶段。** | Octop：Chat / Experts / Tasks / Token Usage；Dify：Home / Studio / Agents / Datasets / Skills / Integrations / Marketplace；生产后台 9 个一级全是对象域。无一家把「配置 → 测试 → 发布」做成一级菜单。 |
| 2 | **流程靠详情页内 tab 或阶段条承载。** | Octop 的 Agent 生命周期（配置 / 渠道 / 定时任务）全在资源详情里。 |
| 3 | **详情页不占主菜单。** 列表 → 详情，菜单高亮停在列表项上。 | 深度页面（Flow 画布、数据集文档）走全屏或独立侧栏。 |
| 4 | **单页不设一级**（无责任 / 权限归属需求时）。 | 三家开源项目都没有「只有 1 个页面」的一级菜单。 |
| 5 | **全局域与业务域在视觉上分组隔离。** | Octop 用 Settings / Control / Admin 三个分组头把配置、控制、管理区与 Chat / Experts 分开。 |
| 6 | **菜单是路由表的派生物，不是手写清单。** | Octop 的 `routeConfigs` 与 `sidebarNav.tsx` 从同一份配置派生菜单与权限；**菜单与路由写两遍必然漂移。** |

### 1.2 生产后台样本的结论

该后台 9 个一级 / 32 个二级，是 10 个月里演进出来的（不是设计出来的），比开源项目更有说服力。

**可借鉴：**

1. **验收独立成域，且「案例标注」挂在验收下**（测试集管理 / 标注任务 / 回放任务）。标注的**产出物**直接进测试集，是闭环任务。→ 本文把「案例标注」放验收域。
2. **回放分两级粒度：单节点回放 / 全流程回放。** 原因诊断用单节点（快、便宜），发布 Gate 用全流程（慢、可信）。→ 待确认项 13。
3. **工具拆两层，且「版本对比 / 草稿合并」只挂在下面那层**：**智能体工具**（从属某个智能体）有版本对比 / 草稿合并；**工具管理**（平台级注册表）只有添加 / 修改 / 删除。结论：**版本 / diff 能力要挂在会频繁变动的对象上，不挂在稳定的注册表上。**
4. **对象生命周期**：智能体列表 → 版本管理（草稿版本可反复编辑 / 线上版本）→ 流量配置。三条结构事实：
   - 配置的宿主是「某个智能体的某个版本」，不是全局配置库；
   - **草稿版本是一等、可反复编辑的容器——保存 ≠ 提交**（攒够一版再送审，不是改一处提一次）；
   - 流量配置与版本管理平级，是对象上的**常驻旋钮**（发布是**动作**，流量是**状态**）。
   → **本文的专家详情三层结构（专家 → 版本 → 配置）与之完全对齐。**
5. **配置本体**（一个真实在跑的销售 Agent：3 子 Agent / 11 动作 / 74 条规则）：
   - 三级规则作用域（全局 / 子 Agent / 动作）与 Loomrise 的定义**完全对应**；
   - **工具授权挂在动作上，不是场景上** → `ToolPolicy` 粒度到 Skill / 步骤；
   - 规则复用靠**内容指纹**（`ruleId` + `hash`），同一规则只有一份定义、多对象引用（"对象被引用而非拥有"）；
   - 决策函数强制输出依据（「定班依据」列为必填）→ **决策产出必须可审计**；
   - 反面证据：74 条规则里约 12 条在讲「别重复」——**规则数量是状态建模缺失的补丁**，说明上下文账本不是可选装饰。
6. **一级菜单同时承担"找谁"的职能**（每个菜单项登记了负责人，9 个一级分属 5 人）。**一级是责任边界，不只是导航**——这解释了它为什么允许「单页一级」。

**不能照搬：**

1. **它是单实例企业内台，没有「交付」这个动作。** Loomrise 的核心动作恰是"换台干净机器还能跑"，所以必须有**导出与恢复校验能力**——但这是**能力**（导出动作 + 恢复校验），不是**页面**。
2. **它没有「发布与回滚」一级**（版本审批是对象下的权限项）。Loomrise 把它提为独立域（`changes`），因为「验收证据 → 审批 → 灰度 → 回滚」是一条带 Gate 的完整链路，且改动可能**跨对象**。**学它的地方**：批准动作的入口仍挂在被改动的对象上，跨对象聚合页**只做收件箱**。
3. **同一对象挂两个菜单项、且权限不一致**（同名页两个入口，其中一个点进去没权限）是它的病。Loomrise 明确避开——**菜单项唯一，视图与权限随角色变**，不是同一对象挂两个菜单项。

### 1.3 Octop 的结构做法（Loomrise 直接采用）

Octop 的菜单清晰来自四条做法：

1. **一个对象的能力收在 1 个菜单项里，用多个 tab 分**（`/personalization/{skills,subagents,tools,…}` 全部映射回同一个菜单 key）。它选的是「1 + 7」，不是「7」。
2. **页面自己声明作用域**（`PageShell agentScoped`），未选中对象时渲染「先选一个」，**不渲染空表**。Loomrise 用 `expertScoped`。
3. **tab 不占菜单位**，靠路径前缀匹配回指菜单 key（`resolveSelectedKey`）。
4. **配置编辑用抽屉 / 行内**，不占菜单。

> **Octop 没有 Agent 版本概念**（编辑原地覆盖 `PATCH`，没有草稿 / 对比 / 回滚）。**它清晰在「结构」，不在「功能」。结构抄 Octop，迭代抄生产系统（§1.2-4）。**

### 1.4 对 Loomrise 的采用边界

可以直接抄的：一级按对象域（规律 1）、详情不占菜单（规律 3）、菜单由路由表派生（规律 6）、全局域分组（规律 5）。

**不能直接抄的**：三家开源项目都是「配好就能用」的平台，主导航终点是**运行**（Octop 首页是 Chat）。Loomrise 的终点是**验收与发布**——「说得清、验得过、退得回」。所以 Loomrise 必须比它们多两个域：**验收**与**变更**。这是产品定位决定的结构增量，不是抄来的。

## 2. 设计原则（8 条）

> **动机**：S2 早期的信息架构按「旅程阶段」组织（建 / 试 / 看 / 标 / 验 / 改 / 批 / 发 / 滚 做成 7 个分区）。两条轴线（对象域 vs 流程阶段）混在同一层，粒度不可比（内容库下挂 5 个库、交付下只有 1 页，菜单上却同级）；同时工具、Skill、审批档位等一等对象没有维护面。下面 8 条是按对象域重排后的判据——**新增对象时照此判断落点，不必重开讨论**。

1. **一级 = 对象域。** 判断一个候选一级是否合格：它能不能用「这里管的是哪一类东西」一句话说清。回答不了就不是一级。
2. **单页不设域**（**有前提**）。只有 1 个二级页面的候选一级，一律并入相邻域。**例外**：当一级菜单同时承担责任 / 权限归属边界时（企业内台的常态，见 §1.2-可借鉴 6——样本中 9 个一级分属 5 人），单页一级是合理取舍。Loomrise S2-a 无此需求，仍按本条执行。
3. **旅程由流程条承载，不进菜单。** 页面顶部常驻 `建 → 试 → 看 → 改 → 验 → 批 → 滚` 指示条，标出当前位置与下一步入口。
4. **列表 → 详情，详情不占菜单。** 判断标准：**这个页面能否在不选任何具体对象时被打开？** 不能，就不是二级页面。（详情页的 tab 与抽屉清单见 §4.3。）
5. **对象必须有落点。** 每个权威对象至少能在一个页面被看到、并在最多一次跳转内被操作。对账表见 §4.4。
6. **界面文字用业务词，不用工程名。** 一个对象只准有一个用户可见的名字；分层数（六层）、数据形态（账本）、发布手段（灰度）这些是实现细节，不是菜单位。对照表见 §4.5。
7. **归属决定位置。** 每个对象先问两句，再决定它住哪：
   - **作用域**：平台（所有专家共用、与版本无关）还是专家级（某一次交付的行为规定、跟版本走）？**专家级的对象一律住版本详情 tab，不住全局菜单。**
   - **性质**：行为规定（配置）还是外部事实（知识）？

   两句合成 2×2：平台×规定 = **设置 · 工具与连接**；平台×事实 = 知识域；专家×规定 = **版本详情 tab**；专家×事实 = 专家对全局知识的**引用**（不复制）。
8. **承载面容量上限。** **一个承载面装的内容块 > 5，必须拆 tab 或加页内二级导航（左侧 anchor rail）。** 三层规则各有分工：**域**层看原则 2；**tab** 层看"内容成体系才开 tab"；**舱内**看本条。**数"内容块"要按形态数**（有列表 + 增删改才算一块），不按行数——否则「模型」这种单值项会被误算成一块。

## 3. 分层模型与视觉分组

### 3.1 平台实现的分层模型（总）

一级菜单不是拍出来的，是下面这张表的直接投影——**每个域恰好对应一层**。

| 层 | 域（一级菜单） | 这一层回答的问题 | 权威对象 | 作用域 | 可写性 |
|---|---|---|---|---|---|
| 交付物层 | **专家** | 交付的是哪一包东西？ | `ScenarioPack`、`AgentVersion`（含**草稿版本**）、`Release`、导出包 | 专家 | 建 / 导 / 交付 |
| 执行层 | 运行 | 它实际干了什么、花了多少？ | `ServiceRequest`、`RunEvent`、`Outcome` | 专家 | 只读 |
| 配置层 | **版本详情「人设 / 流程 / 边界」三个 tab**（专家）+ **设置 · 工具与连接**（平台） | 它被要求怎么做、不许怎么做？ | **平台**：`ToolManifest`、连接引用<br>**专家**：`AgentSpec` 六层、`SkillManifest`（含**应答能力**）、`ExampleSnippet`、`HardRule`、变量与字段、`RequestRouting`、`ToolPolicy`、**知识引用**、**触达频控**、**模型覆盖档**（版本详情页头状态条） | **两段** | 候选化编辑 |
| 事实层 | 知识 | 它能引用哪些事实和物料？ | 业务知识、物料（`ContextSnapshot` 来源） | 平台（专家引用） | 上传 / 版本 / 撤回 |
| 证据层 | 验收 | 新旧版本比，退步了没有？ | `Case`、`EvalSet`、`EvalResult`、`CaseNomination` | 专家 | 审定 / 归档 / 标注 |
| 决策层 | **变更** | 改不改、发不发、退不退？ | `ChangeProposal`、`Release`、`Rollout`、`PolicyProfile` | 跨专家 | 审批 / 发布 / 回滚 |
| 系统层 | 设置 | 平台自己怎么配、连了哪些工具？ | **模型默认档**、凭据引用、**工具与连接（`ToolManifest`）**、诊断信息 | 平台 | 设置 |

**用法**：新增对象时，先问它属于哪一层、哪种作用域，就知道它该住哪个菜单。注意**配置层是唯一横跨两处的层**——平台级注册表与专家级规定本来就不是一类东西。

**模型是唯一"三层都沾"的对象**（不遵守"一个对象一个域"的规整形态）：

| 层 | 落点 | 谁能改 | 是否写进配置 |
|---|---|---|---|
| **① 平台默认档** | 设置 ·「模型」 | 平台管理员 | 是（平台级，不随版本走） |
| **② 版本覆盖档** | **版本详情页头状态条** | 这个版本的编辑者 | **是**（专家级，**随版本冻结**——`AgentSpec` 本就含"模型"字段） |
| **③ 试用临时档** | 试用台 / 版本详情试用时 | 试用者本人 | **否**，只影响这一次运行 |

**判据**：一个新对象若**同一个值在多层级都有意义**，允许它横跨；若只是"被多处引用"，那就仍是单点定义 + 各处引用（如知识）。模型属于前者——**同名不同层，不是重复**。

### 3.2 菜单的视觉分组（3 组）

分组解决的是导航歧义：**用户要改一个 Skill，是去「专家」还是去「设置」？** 答案是**去「专家」**——他要改的 Skill 属于某一个专家的某一版，不属于所有专家。

| 分组 | 域 | 组内对象的关系 | 用户在第一屏该获得的判断 |
|---|---|---|---|
| **交付与验证** | 专家 / 运行 / 验收 | 一个专家 × 它的运行事实 × 它的验收证据 | 「我手上有几个专家、它们跑得怎么样」 |
| **治理** | 变更 | 跨专家的决策动作 | 「有东西等我批、等我发」 |
| **平台** | 知识 / 设置 | 平台级定义，**与版本无关**，专家只是引用 | 「这里改一下，会影响所有专家」——所以这里**很少改** |

分组只把 §3.1 的层级关系显性化，不改变域与层的对应。

### 4.2 二级页面明细

#### ① 专家 `experts`　【交付与验证】

**命名理由**：参考项目 Octop 的 Agent 列表页 UI 就叫**「专家」**（`nav.experts` / `/experts` / `ExpertCard`，发布叫"发布到专家市场"）；Dify 叫「工作室 Studio」；Langfuse 不管 Agent 定义。取 Octop 用法——① 已有先例，不是新造；② 「专家」是**人的隐喻**，与"业务岗位"命名（课程咨询顾问 / 二手车预约专员）天然接得上；③ 业务 PM / 运营一眼懂，不必先学"智能体 / 代理"。

**配套规则（必须守）**：一级菜单文字用「专家」，**列表里每一条用业务岗位名**（如「课程咨询顾问」「二手车预约专员」），**不得再用"专家 / 专员"这类职级词**——否则会出现"专家列表里装着专员"的层级矛盾。`ScenarioPack` 仍是合同名，只在文档与代码里出现。

> **专家详情是三层**：**专家列表 → 专家详情（概览 / 版本 / 流量）→ 版本详情（人设 / 流程 / 边界）**。选中专家后**第一屏是版本列表**——配置属于某个版本，点进版本才是那一版的配置。理由：配置的宿主是「某个专家的某个版本」（§1.2-4）；把配置挂在专家上、用一个隐式草稿承接编辑，只做了一半——用户看不见"我在改哪一版"，历史版本也无法回看。**稳定版本只读**，要改先"从稳定版本新建草稿"（不允许原地覆盖稳定版本）。
>
> **代价与缓解**：日常"改一条规则"比两层时多一次点击（进专家 → 点版本 → 改）。**缓解手段就是 §4.3.3 的「快捷指针」**——`稳定版本` / `最新版本` 各一枚，从专家列表行**一键直达版本详情**，跳过中间这层。

| 二级页面 | 承载对象 / 回答的问题 | 优先级 | 版本 | 依据 |
|---|---|---|---|---|
| 专家列表 | `ScenarioPack` 列表：**岗位名**、**稳定版本 / 最新版本**（两枚可点指针）、审批档位、流量比例、待处理数；行操作 = 新建 / 导入 / 停用 / **导出**（弹窗选版本） | P0 | S2-a | 多专家与第二专家（二手车预约）复用的唯一入口。列表必须露出**最新版本是否为草稿**——"有未提交草稿"是这里最该被看见的信号；做法是把这两个字段**升级成可点指针**（零新增元素）。导出须弹窗选版本：列表上同时有稳定版本与草稿，指代不能含糊 |
| 新建专家 | 分步生成可审阅的 `AgentSpec` **草稿版本**：业务目标 → 资料来源与授权 → 预约字段 → 示例结果 → 汇总 diff | P0 | S2-a | UI-DESIGN §3.2；S2 Gate 的「建」。产出物是 `draft` 状态的 `AgentVersion`，**不直接产出提案、不直接生效** |

> **「导出与交付」不是页面，能力拆三处归位。**
>
> | 原设想承载 | 落点 | 理由 |
> |---|---|---|
> | 导出动作（导出包 + 依赖清单） | **「专家列表」行操作** + **版本详情**的"导出这一版" | 它是**版本上的动作**，不是常驻页面（原则 4） |
> | 干净实例恢复校验（`--offline` 安装 + 回放复现） | **「设置 · 系统诊断」**（**S2-b 起**，作为发布前**检查项**被引用） | 它验证的是**平台环境与依赖完整性**，与某个具体专家无关。**不属 S2 alpha Gate 依赖** |
> | 交付包内容清单（部署清单 / 就绪检查 / 成本假设） | 归**第三条体验**（终端业务应用与交付包），S2 不建 | S2 不做终端应用，没有接收方 |
>
> **保留不动**：「`ScenarioPack` 是可带走的交付单元」这条定义不变，"配置可导出到新实例"仍是成功指标。删的是**页面**，不是概念。

#### ② 运行 `runs`　【交付与验证】

本域回答"它跑起来之后发生了什么"。三页按**问题**切，不按数据表切。

| 二级页面 | 承载对象 / 回答的问题 | 优先级 | 版本 | 依据 |
|---|---|---|---|---|
| **数据看板** | 顶部常驻指标卡（今日运行量 / 成功率 / 平均首响 / 平均成本）+ 两个视角 tab：**过程与结果**（运行流水：状态 / 时延 / 结果 / 渠道 / 版本，可展开到单次详情）｜**成本与用量**（按版本 / 档位 / 渠道 / 工具 / 模型拆；顶部**配额与上限**） | P0（成本部分 P1） | S2-a（过程与结果）· S2-b（成本） | UI-DESIGN §3.4 + §3.1。**合并的理由是"同源"**——两者读同一份 `RunEvent`，只是聚合粒度不同；分两页会让用户在它们之间对不上号 |
| **试用台** | 通用试用入口：左对话区 + 右证据四段（依据 / 动作 / 结果 / 代价），七态常驻，人工确认卡片 | P0 | S2-a | UI-DESIGN §3.3；S1 `web.py` + `web.html` 已有雏形。**这是双入口里的"通用入口"**，主入口在**版本详情** |
| **依据追溯** | 它当时凭什么这么答：`load_status` / `activation_reason` / `source_version` / `token_estimate`；召回命中与兜底 | P1 | **S2-a 不进菜单**（只做运行详情内 tab）· **S2-b 升为二级页** | UI-DESIGN §7 第 6 条；S1 上下文事件已在 `RunEvent` 中。按原则 4——它**必须先选一次运行**才能看，不具二级页资格，故 S2-a 只做运行详情内的一个 tab |

> **两条结构判断**：
> 1. **「运行记录」+「成本与用量」合成「数据看板」**——一个页面、两个 tab。**风险**：成本异常会藏在 tab 里 → 要求 tab 上带**徽标**（超预算时可见），否则等于埋掉。
> 2. **试用双入口。** 主入口：**版本详情的"试用这一版"**（草稿版再加"试用当前草稿"），带版本上下文；通用入口：本域「试用台」，进去先选专家 + 版本。**两个入口进的是同一个试用视图，只预置版本不同——禁止做成两套 UI。**
>
> **⚠️ 本页作用域是混的，「§6.4 讨论项 32」正在评估。** 一个页面同时装**专家级**数据（指标卡 / 过程与结果 / 成本拆分的主体）与**平台级**数据（配额）。**备选方案**：配额在成本 tab 顶部只做**只读引用条**（"当前配额 X（平台级设置 →）"，编辑回平台域）——作用域不混，体验诉求也能满足。**若坚持现方案**，须在原则 7 下正式登记为"体验例外"。**定案前按现文本执行。**

> **为什么不叫「运行日志」**：① 字面与「数据看板 · 过程与结果」撞车；② 中文后台的"日志"默认指**系统级排障文本**（面向开发），而本页是给业务 PM 的"凭什么这么答"；③ 违反 §4.5「不用数据形态做名字」。
>
> **本域定义（定稿）**：本域只含**只读事实**，以及**产生事实的入口**（试用台）——不含任何写入业务判断的动作。试用台会发消息、会落确认卡片，它产生事实。

#### ③ 验收 `acceptance`　【交付与验证】

**本域坚持三页独立，不合并。** 三者**性质不同**：案例集是**资产**（长期，只增不改）、回放验证是**动作**（一次一批，有输入有报告）、案例标注是**任务**（积压待办，有人要做完）。合成一页会让"待标注积压"这类**要盯的信号**被埋进 tab 里。参考项目同源：Langfuse 把「人工标注」独立成一项。

| 二级页面 | 承载对象 / 回答的问题 | 优先级 | 版本 | 依据 |
|---|---|---|---|---|
| 案例集 | `Case` / `EvalSet`：**待审案例 / 基准案例 / 盲测案例** 三 tab（三池构成一条链：待审 → 基准 → 盲测）；真值审定记录、归档状态、`usage`、`batch_id`；盲测按批次显示待 Gate / consumed | P0 | S2-a | UI-DESIGN §3.5；范围记录第 25 条 |
| 回放验证 | 一次回放 = 一个批次：案例集版本、批次号、审批档位版本、阈值快照；关键回归与 Gate 报告分开呈现 | P0 | S2-a | UI-DESIGN §3.5。**待补维度**：生产样本分「单节点 / 全流程」两级粒度（待确认项 13） |
| 案例标注 | `CaseNomination` 提名池 + 业务真值标注（期望状态 / 必须做 / 禁止做） | **人工标注 P0 / 系统提名 P1** | 标注 S2-a · 提名 S2-b | 归**验收域**：它的产出物直接进案例集，是闭环任务（§1.2-1）；它是 P0 且 B3 批次依赖它 |

**案例集三池的中文名**：

| 原词 | 中文名 | 含义 | 谁在动它 |
|---|---|---|---|
| `pending` | **待审案例** | 提名进来了、真值还没定 | 业务标注人（积压了要盯） |
| `golden` | **基准案例** | 已定真值，每次回归对比用；通过率是 Gate 依据 | 系统回放读取 |
| `blind` | **盲测案例** | 真值封存、对优化器不可见；按批次消费，consumed 后不可再用 | 人工补新批次 |

> 三池不是并列的三个抽屉，而是**一条链**：新案例先进「待审」→ 定完真值进「基准」→ 从基准里**人工抽一部分封存**成「盲测」。三个 tab 的排列顺序就是这条链的顺序。

#### ④ 变更 `changes`　【治理】

**命名理由**：该域本质是「邮箱式审批流 + 版本管理」，「发布」只覆盖其中一段。采用 ITIL 变更管理口径：一次改动**从提出到上线到回退**的全程归口。「发布」只是其中一段，「审批」只是一个动作，「治理」太抽象。

| 二级页面 | 承载对象 / 回答的问题 | 优先级 | 版本 | 依据 |
|---|---|---|---|---|
| 待我审批 | **收件箱**：跨专家的待批列表（每条 = 专家 / 版本 diff 摘要 / 风险档 / 来源 / 等待时长）；点进去是**改动详情**（行级 diff + **两栏证据（不退步 / 有改善，不得合并）** + 硬性限制检查 + 成本变化 + 来源标记 + 放宽窗口横幅）；批准整个版本 / 逐项审批 | P0 | S2-a | UI-DESIGN §3.6；S2 Gate 的「批」 |
| 版本与发布 | **时间线**：跨专家的版本时间线（`draft → tested → approved → released → rolled_back`）、发布记录（操作人 / 档位 / 观察期结论）、红线命中、紧急回滚入口 | P0 | S2-a | UI-DESIGN §3.7；S2 Gate 的「滚」 |
| 审批档位 | `PolicyProfile`：风险分类 + 阈值 + 审批要求；创建 / 复制 / diff / 预设切换时间 / 到期回落 | P1 | 两档预设 S2-a · 完整 S2-b | 范围记录第 12 条 |

> **本域的角色是「收件箱 + 时间线」，动作仍在对象上。**
>
> | 动作 | 在哪做 | 为什么 |
> |---|---|---|
> | 看"有什么等我批" | 本域 · 待我审批（收件箱） | 跨专家聚合才有意义 |
> | 批准某次改动 | **改动详情**（从收件箱点进，或从**专家详情 · 版本列表**点进） | 审批要看完整上下文，脱离对象没有意义 |
> | 调某个专家的流量 | **专家详情 · 流量 tab** | 流量是专家的**状态**，常驻，不是发布流程的一步 |
> | 紧急停 / 退 | 两处都有：本域做跨专家总览，专家详情做单专家操作 | 应急动作要最短路径 |
>
> **为什么「审批档位」放这里而不是设置**：档位回答"什么风险由谁批、按什么阈值"，是**审批这件事的规则**。放在审批流旁边，用户改规则时看得见它会影响什么。

#### ⑤ 知识 `knowledge`　【平台】

| 二级页面 | 承载对象 / 回答的问题 | 优先级 | 版本 | 依据 |
|---|---|---|---|---|
| 业务知识 | 全局库 + 专家引用：来源、授权、有效期、版本；上传 / 替换 / 撤回；引用计数与重复提示；**撤回时列出受影响的专家、已发布版本与待重验评测** | P1 | **S2-a 只读列表（摄入走 CLI）· S2-b 完整版** | 内容库第 2 行；[摄入通道](INTAKE-AND-INITIALIZATION.md) 仍为提案，α 期以 CLI 为主通道。S2-a 有**只读形态**（不占 B1–B6 的交付清单，见 §5.2） |
| 文件与物料 | 文件库：**可用范围**（哪些专家、哪个环节）、授权、有效期；上传 / 版本 / 撤回 | P2 | S2-b | 内容库第 3 行 |

> **两页明确拆开，不合并。** 理由不是"内容多少"，而是两者的**授权与生命周期模型不同**：业务知识是**事实**（被召回引用、算引用计数、撤回要列影响面并触发重验），文件与物料是**素材**（按专家 / 环节授权、有有效期、不进召回）。合并会让两种不同的授权语义挤进同一张表。
>
> **知识与工具的分界**：知识域管「外部事实」，工具与连接管「能调用的能力」。前者只做上传 / 版本 / 撤回，**不编辑事实本身**。**改 Skill 去专家；加工具、配模型凭据去设置；换知识去知识。**

#### ⑥ 设置 `settings`　【平台】

设置域回答两件事：**平台连了什么能力**（工具与连接）和**平台自己怎么配**（模型 / 系统诊断）。三者共同属性：**平台级、与版本无关、改一次影响所有专家**。

| 二级页面 | 承载对象 / 回答的问题 | 优先级 | 版本 | 依据 |
|---|---|---|---|---|
| **工具与连接** | `ToolManifest` + 连接引用：平台上有哪些工具、连了哪个系统、授权范围与撤销；**粗粒度动作**（添加 / 修改 / 删除 / 停用）；**连接的凭据只存引用**；**渠道凭据（企微 / 外呼线路）**；调用沙盒（试调一次看返回）；被哪些专家引用 | P1 | S2-a | PRODUCT-FORM「连接 → 映射 → 沙盒 → 撤销 → 启用」。**不做版本对比**——粗粒度动作对稳定注册表足够（§1.2-3） |
| **模型** | **平台默认档**：默认模型 + 备选模型；模型参数默认值；**成本对照档**（同一任务在不同模型下花多少）；**模型密钥引用**（只存引用不存明文） | P1 | S2-a | `ARCHITECTURE` 权威对象表末行（`AgentSpec` 含"模型"字段，故需定义**平台默认值**）；S1 已有 `configure-model` 与 `--model` 的 UI 化 |
| **系统诊断** | 版本钉 / 依赖 / 许可证清单；运行环境自检；**干净实例恢复校验**；**凭据存放与轮换记录**；日志与导出；数据目录与备份 | P2 | S3 | VERSION-PINS / S1 自检脚本的 UI 化，非 Gate 依赖 |

> **「模型」这一页为什么薄、为什么仍值得独立。** 它 S2-a 真正要做的只有四件事：看当前默认档、切默认档、看两档成本对照（`gpt-6-sol` vs `gpt-6-luna`，S1-BUILD §4.3 已有实测数据）、填 / 换密钥引用。**不并入「工具与连接」的理由**：工具是"能调用的**能力**"，模型是"用哪个**大脑**"；工具的选择逻辑是 Schema / 幂等 / 副作用，模型的是成本 / 时延 / 稳定性。并成一页会装两种东西（原则 1）。
>
> **一条硬约束**：本页只设**默认档**，不改任何单个版本的**模型覆盖档**。**版本覆盖只能在版本详情里改**（页头状态条），**且必须走草稿 → 提交**——否则"某个版本用哪个模型"会绕过审批偷偷变，而这个字段直接影响成本与回答质量（§3.1 末表）。
>
> **工具注册表为什么放设置、而不是独立成域。** 工具是**平台级能力**。再拆一个单页一级会制造"只有一项的分区"（原则 2）。与 Octop 的差别是**取舍不同而非对错**：Octop 把 `/connectors` 与 `/knowledge-bases` 做成独立项，代价是首屏多两个入口；Loomrise 收进设置，代价是"加工具"要多点一层。**若工具数量长出独立视野的需求，再提升为一级**（待确认项 22）。

#### 4.3.1 专家详情的 3 个 tab（选中专家后）

**默认落点是「版本」**，不是概览。

|---|---|---|---|---|
| **概览** | `ServiceRequest` 统计、待办 | 这个专家健康吗、有什么事等我 | 跳到待办对象 | P0 |
| **版本** | `AgentVersion` 列表（`draft` / `released` / 历史）+ `ChangeProposal` | 这个专家有哪些版本、我在改哪一版、和线上差在哪 | 打开版本 · **指针直达稳定 / 最新** · 新建草稿 · 提交 · 丢弃 · 对比 · 导出 · 试用 | P0 |

**版本列表的构成**：**列表顶部钉着两枚指针行**（`稳定版本` / `最新版本`，见 §4.3.3，**不参与下面的排序**）＋ 完整版本序列。每行 = 版本号 · 状态（草稿 / 生效 / 已归档）· 创建人 / 时间 · 流量比例（仅生效版）· 与上一版的 diff 摘要。序列里**草稿置顶**；无草稿时首行即"**新建草稿（从稳定版本派生）**"。行操作 = 打开 · 对比 · 导出这一版 · 试用这一版 ·（草稿）提交 / 丢弃。

**新建专家直接落到一个草稿版本的版本详情**（向导产出 `draft`），一步进入可编辑状态，不必再"新建草稿"。

##### 概览 tab 的两块内容

**① 四指标**（每张卡带环比，对比上一版或上一周期）：

| # | 指标 | 回答什么问题 | 异常时往哪走 |
|---|---|---|---|
| 1 | 任务成功率 | 干得对不对 | 环比掉 → 看「回放对比结论」 |
| 2 | 平均首响 | 快不快（语音链路尤其关键） | 环比涨 → 看渠道与模型 |
| 3 | 单位任务成本 | 贵不贵（按当前稳定版本算） | 环比涨 → 看数据看板 · 成本与用量 |
| 4 | **回放对比结论** | 稳不稳（对上一版：不退步 / 有改善 / 有退步） | 出现"有退步" → 最高优先级 |

**② 待办列表**（每条锚定一个**具体对象**、可点击直达；**不做成通知流**）：

| 待办 | 指向 | 点进去 |

| 待我批 | 这个专家有 N 个改动等我批 | 改动详情（批准 / 逐项 / 拒绝） |

| 草稿未提交 | 有 1 个草稿版本放了 N 天没提交 | 专家详情 · 版本列表 |
| 已自动停流 | 某版本命中红线，已自动停止暴露，等人工决定 | 专家详情 · 流量 tab |

#### 4.3.2 版本详情的 3 个 tab + 页头状态条（选中某个版本后）

| tab | 承载对象 | 回答什么问题 | 主操作 | 优先级 |
|---|---|---|---|---|
| **人设** | `AgentSpec` 的身份与输出约定 + 变量与字段 | 它是谁、按什么身份和风格说话、要拿到什么信息 | **编辑 → 写入本版本草稿**（历史版本**只读**） | P0 |
| **流程** | `RequestRouting`、`SkillManifest`（主流程 + 应答能力）、`ExampleSnippet` | 它怎么把一件事办完；用户插问时怎么答 | 同上 | P0 |
| **边界** | 知识引用、`ToolPolicy`、`HardRule`、触达频控 | 它能引用什么、调用什么、绝不能做什么、什么时候不许打扰 | 同上 | P0 |
| 〔页头〕**模型状态条** | `AgentSpec` 的"模型"字段（覆盖档） | 这个版本用哪个档跑 | 点击覆盖 / 改回默认（**进草稿**） | P0 |
| 〔版本级动作〕 | — | 这一版能不能发、要不要留 | 提交审批 · 丢弃草稿 · 版本对比 · 导出这一版 · 试用这一版 | P0 |

**读 / 写随版本状态变**：草稿 → 可编辑；生效 / 已归档 → **只读**，但可"对比""导出""从这一版新建草稿"。

**为什么配置 tab 挂在版本、不挂在专家**：因为**配置的宿主就是某个版本**（§1.2-4）。挂在专家上会让"我在改哪一版"变成隐式状态（那个草稿），历史版本也无法回看。挂在版本上后，`AgentSpec` 的"模型"字段、三张配置表、提交与导出**全都归属同一个版本容器**，层级自洽。

**为什么仍按「模型能否绕过」分三个 tab**：**人设 / 流程**是模型内的策略，改错了靠回放能发现；**边界**的四块全部落在 `CONFIGURATION-LAYERS` §7.4 的**不可自动修改清单**里，改错不是效果变差而是**出事**，审阅标准（确定性检查）也不同。**把"事故面"和"效果面"放在同一个 tab，等于让审批者用同一副眼光看两类风险。**

**拆的是呈现，不是提交单位。** 三个 tab 的改动进**同一个草稿**，`ChangeProposal` 仍只有一个 diff、回放**只跑一次**。绝不能做成"人设一个版本、流程一个版本"（审批碎片化 + 回放跑三次）。**连带**：版本对比的 diff 必须**按这三组分段**呈现。

##### ① 人设 —— 它是谁、怎么说话、要拿到什么信息

| 配置项 | 配什么 | 形态 |
|---|---|---|
| **人设与使命** | 身份（业务岗位角色）、目标、职责边界（不管什么）、服务对象、称呼与语言 | 富文本 + 结构化字段 |
| **输出合同与语气** | 回复结构（要不要给选项）、语气、禁用表达、长度上限、追问方式 | 开关组 + 短表单 |
| **变量与字段** | 要问出 / 确认 / 回填的业务字段（学员姓名 / 年级 / 科目 / 可试听时间 / 家长手机号 / 来源渠道）：类型、必填、校验、**允许来源**（用户口述 / 从 CRM 带入 / 系统推断）、**回填目标**、敏感级别 | 字段表 |

**约束**：

1. 人设只写"**是什么、要什么**"，**不写"不许做什么"**——后者属「边界」。
2. **「输出合同」与「硬性限制」的分界是"管表达 vs 管能不能做"**：前者管"怎么说"，后者管"能不能做"。
3. **变量与字段：定义只在一处编辑，流程 / 边界里只做只读引用。** 字段被路由条件或工具入参引用时，保存要提示"**被 N 处引用**"。
4. **升级条件**：字段数 **> 15 且被多处引用** → 升为独立 tab。

##### ② 流程 —— 它怎么把一件事办完

| 配置项 | 配什么 | 形态 |
|---|---|---|
| **路由规则** | 一轮输入进来判什么主请求、下一步做什么、何时澄清；按优先级排序 | 有序列表 |
| **主流程** | 有顺序、由路由逐步推进的 Skill（接待 → 问需求 → 推荐 → 约试听） | 有序卡片列表 |
| **应答能力** | 用户随时可能问、可与主流程某步**同时加载**的 Skill（退费政策 / 师资 / 上课方式 / 网络问题）＋**加载范围**＋**并发加载上限** | 卡片列表 + 组级设置 |
| └ **示例片段** | 挂在各自 Skill 下的好例 / 坏例 | 子视图，**不写进主 Prompt** |

**约束**：

1. 路由必须**可解释**（每次判定落 `activation_reason`）。
2. **路由的"下一步"只指主流程**；应答能力**不参与下一步决策**。
3. Skill 不允许只写正向路径，**退出 / 转人工条件必填**。
4. **主流程与应答能力共用同一个 Skill 卡片编辑器**——字段完全一样（适用条件 / 目标 / 步骤 / 退出条件 / 引用的知识与工具），差别只有：主流程**有顺序**，应答能力没有。

##### 应答能力与主流程：同轮并发加载

**模型**：应答能力**不是**"从主流程切走 → 答完再回来"，而是**与主流程当前步被同一轮同时加载**，由模型自行决定输出的组织方式——这样能**平衡问题响应与流程推进**，两个目标在同一轮里同时可见。

**必须立住的一个区分**：**"加载多个 Skill" ≠ "推进多个主请求"**。

- `RequestRouting.next_step` **仍唯一**，仍指向主流程下一步；
- 应答能力**只参与本轮输出内容的构成**，不参与路由结果。

合同依据（读原文核实）：

| 出处 | 原文 | 含义 |
|---|---|---|
| `CONFIGURATION-LAYERS` §2 `RequestRouting`「不负责」列 | 不同时推进多个互斥**主请求** | 限定词是**主请求**，不是 Skill。合同禁的是"两个主请求并存"，**没禁"多个 Skill 并存"** |
| §2 `Skill/SOP` 权威内容 | 适用条件、目标、步骤、退出 / 转人工条件、引用的知识和工具 | **无互斥性** |
| §1 渐进式上下文加载 | 决定当前轮次把哪些事实、**Skill 片段**、规则摘要和工具结果提供给模型 | **Skill 片段是复数** |

举例：用户在主流程第 3 步问"退费怎么算"，路由的输出仍是"推进到约试听"，同时加载了「退费政策」片段；模型决定把退费答在前、推进跟在后面。**主请求没变、下一步没变，变的只是这一轮的输出。**

**「Agent 自决」的边界**：

| | 谁决定 |
|---|---|
| **表达层**（先说退费还是先推进、要不要合并成一段、语气怎么衔接） | **模型自决** |
| **权限层**（能不能给出退费承诺、能不能调用查询工具、金额算错谁负责） | **仍走 `HardRule` / `ToolPolicy` 模型外裁决**，与是否加载了应答能力无关 |

**加载范围（默认 A + 单条可选收窄）**：

| 档 | 做法 | 采纳 |
|---|---|---|
| A | 全进"可召回池"、不配范围，路由 + 模型每轮自行召回 | — |
| **B** | **默认 A；单条应答能力可选填"限定范围"**（仅第 N 步之后可加载 / 排除某些步） | ✅ **采用** |
| C | 每条必须声明绑定的主流程步 | — |

**理由**：默认零配置负担，与"Agent 自己决策"一致；只有"明显不该早期出现"的能力（如催单话术不该在第一次接待就被召回）才需要收窄。

**并发加载上限（组级设置）**：同时加载多个 Skill 会推高 token。合同 §5 已有现成机制承接（`token_estimate`、`load_status = budget_capped`）——本节需要一个组级上限（每轮最多同时加载 N 条应答能力 / token 预算），**不设则预算与召回都不可控**。

##### ③ 边界 —— 它能引用什么、调用什么、绝不能做什么、什么时候不许打扰

**本 tab 的四块全部在 `CONFIGURATION-LAYERS` §7.4 的「不可自动修改边界」清单内**——自进化流程不得静默修改它们，只能形成待审提案。这是它独立成 tab 的**首要理由**。

| 配置项 | 配什么 | 形态 |
|---|---|---|
| **知识引用** | 哪个环节可引用哪些知识 / 物料；**引用不是复制**；显示被引用条目的授权与有效期 | 引用列表 |
| **工具授权**（`ToolPolicy`） | 步骤 × 工具 × 确认方式 × 副作用等级 × 幂等键 × 预算 / 超时 | 绑定矩阵 |
| **硬性限制**（`HardRule`） | 禁止 / 必须 / 停止 / 去重 四类，按 **类别 × 作用域** 分组 | 规则列表 |
| **触达频控** | 时间窗、静默时段、单位时间次数上限、按渠道分设（**S2 只做专家级**，全局默认后议） | 规则表 |

**约束**：

1. **工具授权步进给，不给"全开"**——按 Skill / 步骤逐条授权。
2. **硬性限制必须在模型外执行**，且按 类别 × 作用域 分组、**禁平表**（生产样本单 Agent 74 条规则，平表必然重演作用域错配）。
3. **频控的覆盖只能更严不能更松**——专家覆盖是收窄，不是放宽。
4. **知识引用是引用不是复制**：条目本身在「知识」域维护，本页只声明"这个环节可以引用它"；撤回知识要能反查出受影响的专家与已发布版本。
5. **为什么触达频控不属于「硬性限制」**：后者是确定性的"绝不能做"，频控是"什么时段、多久一次"的**节奏参数**，两者裁决方式不同。

##### 〔页头〕模型状态条

`gpt-6-sol（跟随平台默认）` — 可点开切换 → **改动进草稿**。

| 取值 | 界面行为 |
|---|---|
| 未设置 | 显示"**跟随平台默认（当前：`gpt-6-sol`）**"——默认值必须显示出来，不能让用户去别处找 |
| 已覆盖 | 显示所覆盖的档 + 一个"改回默认"的入口，并标 **「草稿」**（若该覆盖尚未提交） |

**显示的是草稿的取值，不是生效态的**——否则用户改完发现页头没变，会以为没保存。

**为什么不做成 tab**：① 判据（形态）——一行选择 + 少量参数，不够格；② 判据（层级）——它**高于**人设 / 流程 / 边界三者（影响这三者的执行），塞进任一个都会把覆盖关系画错。

**为什么必须走草稿 + 审批**：这个字段直接决定成本与回答质量，绕过审批改它等于绕过审批改成本。

两条实现约束（抄 Octop）：

1. **`expertScoped` 声明**：专家详情与版本详情的所有 tab 必须声明"我在某个专家（某个版本）里"，由全局**专家切换器**定位；未选中专家时渲染"先选一个专家"，**不渲染空表**。
2. **tab 不占菜单位**：路由 `/experts/:id/{overview,versions,traffic}` 与 `/experts/:id/versions/:vid/{persona,flow,guardrails}` 全部用前缀匹配回指菜单 key `experts`。**指针路由** `/experts/:id/{stable,latest}` 是**别名**——解析到具体版本后**重定向**到 `/experts/:id/versions/:vid/...`，自身不渲染页面、不留独立 URL 语义（§4.3.3-4）。

**两层 tab 的分工与顺序**：专家层 **概览 → 版本 → 流量**（这个专家健康吗 → 它有哪些版本 → 怎么分流）；版本层 **人设 → 流程 → 边界**（这一版是什么样）。合起来就是「它是什么样 → 攒成一版 → 分多少流量」的因果链。

| | 版本详情的 人设 / 流程 / 边界 | 专家详情的 版本列表 |
|---|---|---|
| 回答 | 这一版**是什么** | 它有哪些版本、**和线上差在哪、能不能发** |
| 读写 | 直接编辑（写进本版本草稿） | 打开 / 对比 / 提交 / 丢弃 / 导出 / 试用 |

#### 4.3.3 快捷指针：稳定版本 / 最新版本（两层详情之间的直通车）

三层结构（§4.3.1）不可避免带来"多点一次"的代价。**两枚指针就是这条代价的解**——它们不新增页面、不占菜单，只是把**已经存在于列表里的两个字段升级成可点入口**。

| 指针 | 指向 | 判定口径 |
|---|---|---|
| **稳定版本** `stable` | 当前正在对外服务的 `released` 版本（状态为「生效」的那一版） | 恒为**一个**。灰度期间指**灰度前的基线版本**，不是灰度中的候选版 |
| **最新版本** `latest` | 版本序列里**创建时间最晚**的一版 | 恒为**一个**。有草稿时就是那版草稿；无草稿时是最近创建的一版（可能已发布，也可能停在「已测试」） |

**三个落位**（按路径从短到长）：

| 落位 | 形态 | 路径 |
|---|---|---|
| **专家列表行**（最短） | 每行岗位名右侧两枚 chip：`稳定 v3` · `最新 v4 草稿` | 专家列表 → **版本详情**（跳过专家详情，1 跳） |
| **版本列表顶部** | 两枚指针行钉在列表最上方，不参与列表排序 | 专家详情 · 版本 → **版本详情**（1 跳） |
| 专家切换器（全局） | 展开项右侧同样两枚 chip | S2-b 再评估，**S2-a 不做** |

**与列表原有列的关系**：专家列表本来就有「稳定版本 / 最新版本」两个字段。本次是**把这两个字段变成可点**——**零新增元素**，不加重列表负载。

**指针型 URL**（"短路径"的真正兑现）：`/experts/:id/stable` 与 `/experts/:id/latest` 解析后落到对应的版本详情（默认「人设」tab）。可书签、可分享、可被其他系统直链。

**五条必须守的约束**：

1. **落点必须是版本详情，不是版本列表。** 否则"最短路径"没兑现，只是换个地方再点一次。
2. **落点页头必须明示"你在看哪一类"**——`v3 · 稳定版本（生效中 · 只读）` / `v4 · 最新版本（草稿 · 可编辑）`。这是本功能最大的风险：用户一键进来会以为在改线上。**稳定版本只读**，要改必须显式"从这一版新建草稿"。
3. **两枚重合时只显示一枚。** 无草稿时"最新"就是"稳定"（同一版），只渲染 `稳定版本 v3`，**不得并列显示两个同版本号的指针**——否则用户会以为有两版。
4. **指针是动态解析的，不是快照。** `/latest` 永远指向**当下**最新的一版；今天存的指针书签，明天草稿提交后指向的可能是另一版。所以**要分享确定的某一版，必须用具体版本 URL**（`/experts/:id/versions/:vid/...`），不能用指针 URL——指针 chip 上的"复制链接"也走具体版本 URL。
5. **无稳定版本时的降级**：专家从未发布过（只有草稿）→ 稳定版本指针**置灰并标注"尚未发布"**；只有一版且无草稿 → 两枚合并为一枚。**不得渲染空 chip 或错误版本。**

> **不进菜单的判据**：它**不能在不选专家时被打开**（要先有专家，"稳定"才有所指），所以它是**入口而非页面**——与原则 4 同向。**计数不变**：一级域 6 · 二级页 16 · 面 22。

### 4.7 每个页面的核心功能

§4.6 回答「菜单长什么样」，本节回答「**每个页面进去干什么**」。写法：一句话职能 + 主操作 + 一条**会咬人的约束**（实现时最容易做错的那条）。**共 16 个二级页 + 3 个专家 tab + 3 个版本 tab = 22 个面**（页头模型状态条另见 §4.3.2，不按面计）。

#### 七个"别再搞混"

1. **专家详情 ≠ 版本详情**：专家详情第一屏是**版本列表**（它有哪些版本、哪个在跑）；点进某个版本才是**那一版的配置**（人设 / 流程 / 边界）。判据：**选版本在专家层，改内容在版本层。**
2. **「流量」tab ≠ 「版本与发布」页**：前者是**这个专家的状态**（常驻），后者是**跨专家的决策**（一次性）。判据：**看分流去专家，决定发退去变更。**
3. **「待我审批」页 ≠ 批准的落点**：它是收件箱。判据：**收件箱用来发现，改动详情用来决定。**
4. **「试用台」页 ≠ 试用的唯一入口**：主入口在**版本详情**的"试用这一版"，试用台是**通用入口**。判据：**但只有一套试用 UI。**
5. **「设置 · 模型」≠「版本详情页头 · 模型状态条」**：前者是**平台默认档**（改一次影响所有专家，不走审批）；后者是**这个版本的覆盖档**（随版本冻结，**必须走草稿 + 审批**）。判据：**改全局默认去设置，改某个版本的档在版本自己的页头。**
6. **「主流程」≠「应答能力」**：两者是**同一个 `Skill` 对象的两类触发方式**；**主流程有顺序，应答能力没有**。判据：**要按固定顺序推进的去主流程，用户随时可能问的去应答能力。** 两者**可以同一轮被同时加载**，但**路由的"下一步"仍只指主流程**。
7. **「稳定版本」指针 ≠ 「最新版本」指针**：前者是**现在正在服务的那一版**（恒为生效版，**只读**），后者是**时间上最新的那一版**（**可能是草稿，可编辑**）。判据：**要看线上现状去稳定，要接着改去最新。** 两者**指同一版时只显示一枚**。用指针 URL 分享出去的是"当下"，**要分享确定的某一版必须用具体版本 URL**（§4.3.3-4）。

**alpha 未交付（B7 / B8）**：**业务知识**（完整版；S2-a 期间只有 **CLI 摄入 + 只读列表**）· **文件与物料** · **系统诊断** · **数据看板 · 成本与用量 tab（含配额与上限）** · **依据追溯**（独立页）。**B1–B6 完成后**，非开发者可在不打开开发者模式的前提下走完「建 → 试 → 看 → 改 → 验 → 批 → 滚」；但**成本只看得见单位任务成本指标，看不到拆分视图与配额**。

### 5.3 每个批次的统一验收口径

1. 该批次页面之间的跳转不超过一次点击，且不出现死链到未实现页面（未实现的入口一律置灰并标注目标版本）。
2. 页面顶部流程指示条能正确反映当前所处阶段，并给出下一步入口。
3. 离开列表进入详情后再返回，筛选与选中状态不丢。
4. **指针落点与逐层点进落到同一个页面实例**——`/experts/:id/latest` 与「专家详情 · 版本 → 点该版本」解析后**URL 一致**，**不得做成两套视图**（同「试用双入口」的判据）。
