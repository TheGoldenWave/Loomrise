## 1. 一句话

它的治理栈是**按 git/GitHub 的隐喻逐层补齐的**：版本＝commit、分支＝branch、合并＝merge、提案＝PR、评审＝review、实验＝按流量分流。补齐度很高，**唯独把"测试必须过"这一条明确标成"未来几周"**——所以这套栈的最后一环是**人**，不是**判据**。

## 2. 版本与分支（机制层）

| 项 | 事实 |
|---|---|
| 粒度 | `agtvrsn_*` 版本；`agtbrch_*` 分支 |
| 不可变 | 版本创建后**不可修改**；保存改动即自动创建新版本 |
| 启用 | **opt-in**；一旦启用**不可关闭**（永久变更） |
| 主分支 | 每个启用版本化的 agent 有一条 `Main`，不可删除/归档 |
| 建分支 | 可从**任意分支的任意版本**拉，不必从 main |
| 分支名 | 允许字母数字与 `() [] {} - / .`，≤140 字符 |
| 流量 | 按百分比分配，**必须精确合计 100%**；**按 conversation ID 确定性路由**（同一用户稳定落同一分支） |
| 归档 | 只有 0% 流量的分支可归档 |
| 合并 | 任意非归档分支 → 任意非归档分支；`archive_source` 默认 `true`；自动把源分支流量转到目标 |
| 冲突 | 默认**取较晚更新的一方**；`force=true` 则一律取源分支 |
| 合并失败态 | `no_new_changes_to_merge` / `branch_already_merged` |
| 变基 | **仅非 main → main**；冲突时**保留分支自己的值**；失败态 `branch_already_up_to_date`；对 main 变基报 `cannot_rebase_main` |
| 预演 | `preview_merge` / `preview_rebase` 返回 `overridden_fields` 与 `conflicts` |
| 复制 agent | 复制**全部未归档分支**，每分支只带一个版本（**不复制历史**）、不复制草稿与流量 |

### 2.1 分支保护

`protection_status` 枚举：`writer_perms_required`（默认，需写权限）/ `admin_perms_required`（需工作区管理员）。

> **只在 API 参考里定义，叙述文档没有对应章节**。这意味着"保护分支"是个存在但未在产品文档里讲清的能力——我们的调研不能据此说"它没有保护"，只能说"它有字段、无说明"。

## 3. 合并提案：PR 隐喻，但门是软的

### 3.1 状态机

| 层 | 取值 |
|---|---|
| 提案状态 | `Open` / `Merged` / `Closed` |
| 评审裁决 | `Approved` / `Changes requested`（**同一人最新一次覆盖之前**） |
| 关闭原因 | `withdrawn`（作者自己关）/ `rejected`（他人关）/ `branch_archived`（源分支归档自动关） |

### 3.2 可以合并的三个条件（官方原句）

1. 合并者对**源与目标分支都有写权限**；在受保护分支上意味着**必须是工作区管理员**。
2. **没有任何评审人的最新裁决是 `changes requested`**。
3. **至少 1 个非作者批准**；**工作区管理员可绕过这一条**。

### 3.3 门禁的真相

官方两句话必须并读：

> `agent-testing`：测试可集成到开发流水线，"automated testing on every code change / prevention of regressions before deployment"。
> `merge-proposals`：**"Merging does not require tests to pass. Reviewers decide based on what the tab shows."**
> `merge-proposals`（Availability 段）：**"Planned additions over the coming weeks include: Required tests that must pass before a proposal can be merged."**

→ **测试通过不是合并的前置条件**；提案页会把源分支的**通过率与运行历史**摆在评审人面前，但**是否合并由人决定**。"测试必须过"是**官方自己列出的未来能力**。

### 3.4 提案页里放了什么

| 页签/区块 | 内容 |
|---|---|
| 描述 | Architect 写的固定三段：**Summary**（每处改动及原因）/ **Testing**（跑了哪些、结果如何，**或明确写"没跑"**）/ **How to review**（重点看什么、建议跑哪个测试） |
| 测试 | 源分支的通过率与运行历史；可切到目标分支对比；可 `Run tests` 重跑 |
| 会话 | 源分支最近的会话 |
| 元信息 | 源/目标分支、能否合并、落后/领先多少 |

> "**没跑测试也要显式写出来**"这一条比"要求必须跑"更现实：它把"没验证"变成一个可见状态，而不是留空让人误读成"验证过了"。我们 `S2-EVAL-GATE-PROPOSAL` 若做提案页，这条值得照抄。

### 3.5 已知粗糙处

- 提案是 **alpha**。
- 一个提案只覆盖**一对**源→目标分支（要比两个方案就开两条分支、两个提案）。
- 合并一个提案会**自动关闭同一源分支的其他提案**。
- "指定评审人""按区域设 owner""必须过测试"三项**都还没做**。

## 4. 实验：A/B 是分支的副产物

| 项 | 事实 |
|---|---|
| 前置 | **必须先启用版本化** |
| 变体 | 一条分支即可；提示 / 流程 / 音色 / 工具 / 知识库 / LLM / 判据 / 语言**任何一项**都可不同 |
| 分流 | 百分比，合计 100%，按 conversation ID 确定性 |
| 队列路由 | 用 API 发起会话时，可**指定 cohort 走指定分支** |
| 可测指标（官方举例） | CSAT、**containment rate**、conversion、平均处理时长、响应延迟中位数、**每次解决成本** |
| 建议节奏 | 从 5–10% 起；10% → 25% → 50% → 100% |
| 收尾 | 提流量或合并成默认；保留完整版本历史以便回滚 |

> 它列的六个指标里，**"每次解决成本"（cost per agent resolution）** 是最容易被忽略但最该有的一个：它把"质量"与"成本"放在同一个分母上（每解决一个）。我们的评测域目前只有质量与预算，没有"每次解决成本"这个复合口径。

## 5. Architect：能开提案，不能批提案

| 能力 | 有 |
|---|---|
| 从失败会话 / 失败测试 / Spotlight 发现 / 工单 出发改配置 | ✅ |
| 在分支上改，**自己写测试并跑**（同一测试最多重复 **50 次**报通过率） | ✅ |
| 开 merge proposal，描述由**真实 commit 与测试运行**生成 | ✅ |
| 建议评审人 | ✅ |
| 提议先分一小部分真实流量给该分支 | ✅（**需你批准**） |
| **评审 / 批准 / 合并 / 关闭提案** | ❌ **永远由人做** |
| 替代人接受条款、代表组织做决定 | ❌ |

身份事实：**Architect 以"你"的身份行动**，所以它开的提案**作者是你**。

另有一处产品限制（`architect/how-it-works`）：它生成的**看板只存在浏览器标签页内存里**，刷新/换标签/建太多就丢，页面会提示"请让它重建"；看板是**只读快照，无筛选、不实时**。工具返回数据过大时，完整响应只留在浏览器内存里，**从不保存或上传**。

> "AI 能开提案、不能批提案"这条界线，与我们的"模型只提交候选、不得裁决"是**同一条线**，而且它是在一个**商业闭源产品**里划的——这是很强的外部佐证：**即使不追求可审计，产品也必须这么划，因为责任归属不能给模型**。

## 6. 工单（Triage）：四个来源，四个状态

| 来源 | 说明 |
|---|---|
| `flag_issue_for_review` | **live agent 在会话中主动打标** |
| 人工建 | 一次性修复或 todo |
| 会话复核 | 看记录时开单 |
| Architect 复核 | **coming soon**：跨会话发现重复模式后自动开单 |

状态：`Open` / `In progress` / `Resolved` / **`Merged`**（与另一张同根因的票合并）。

边界（官方明写）：**Triage 票讲的是 agent 自己的表现，与 agent 在会话中替终端用户开的支持工单是两回事。**

> `Merged` 这个状态值得记：它承认"多张票同一个根因"，并允许**合并成一件事修一次**。我们 `CaseNomination` 若不支持合并，会出现"同一坏例被提十次、修十次"。

## 7. 隐私：三个开关 + 一条企业级能力

### 7.1 留存

| 项 | 事实 |
|---|---|
| 默认 | **2 年** |
| 可设 | 任意天数（30 / 90 / 365…）· `-1` **无限** · `0` **到期即删** |
| 作用域 | **转写与会话音频分开设** |
| 追溯 | 可选择**应用到已有数据**（⚠️ 缩短会**立即删除**超出新期限的数据） |
| 合规建议 | GDPR 按处理目的对齐；**HIPAA 建议 ≥6 年** |

### 7.2 音频保存

独立开关（`audio-saving`），决定是否留存通话音频。官方给了三档推荐配置：**最大隐私**（关音频 + 留存 0 天）/ **平衡**（关键交互留音频 + 中等留存）/ **合规导向**（留音频 + 按法规设留存）。

### 7.3 会话历史脱敏

自动识别并**移除**敏感实体后再落库：转写里替换为占位符，音频里替换为**哔声**。**仅企业客户可用。**

### 7.4 零留存模式（ZRM）

| 项 | 事实 |
|---|---|
| 作用域 | 可按 agent 开；工作区全局开启时**强制所有 agent 开启且不可单关** |
| 效果 | **不存录音**；会话后**不记录含 PII 的转写与元数据**；推理摘要可生成并外送但**不写入转写** |
| 后果 | 要拿会话信息**必须靠 post-call webhook** |
| 模型限制 | 仅 **Eleven Realtime v1 Max** 可用，且**仅美区与欧区** |
| 代价 | 可能影响它自己排查问题（可用数据极少） |

> ZRM 这条对我们有个直接提醒：**"零留存"会连带剥夺"事后评测"的数据源**。若客户要求零留存，评测只能靠**实时外送的 webhook 落库到客户侧**——这意味着评测数据的所有权与存放位置要跟着变。我们的 `S2-EVAL-GATE-PROPOSAL` 目前默认"平台侧有记录"。

## 8. 法律：三条它写进文档的义务

| 主题 | 要点 |
|---|---|
| **披露（disclosure）** | 与 AI 对话时**必须告知对方**这不是真人；各司法辖区要求不同 |
| **HIPAA** | 涉及受保护健康信息时的额外义务（BAA 等） |
| **TCPA** | 美国外呼/短信的**事先同意**与呼叫时段等要求 |

> `legal/disclosure` 与产品页"自然到听不出是 AI"的宣传**存在张力**：一个要求告知，一个以"像真人"为卖点。我们引用它的"拟真度高"时必须同时记住这条义务——**拟真与披露不是二选一，是必须同时满足**。

## 9. 鉴权与入口

| 项 | 事实 |
|---|---|
| `auth` | 属于**实例级设置**（不随版本），含鉴权设置与**白名单** |
| Widget | **必须公开 agent 且关闭鉴权**；可用签名 URL + 域名 allowlist 加固 |
| API | `xi-api-key`；另有短期 token 机制 |
| MCP | 有独立的安全页（`tools/mcp/security`），要点是 server 凭证与工具级覆盖的边界 |
| 工作区级设置 | 告警阈值、ZRM 全局开关等**仅管理员可改** |
