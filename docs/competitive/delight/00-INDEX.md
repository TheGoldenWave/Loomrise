## 3. 三句话结论

1. **它不是「配置项更多的客服后台」，而是把 SOP 变成一等可版本化资产（Actionbook），并围绕它做了可读、可导航、可被 AI 提议修改的三件套。** 这一层是它真正领先我们的地方。
2. **它用可读性换确定性**：退款阈值、升级判定这类硬规则写在自然语言 actionbook 里，由模型解释执行；safeguard 也只是概率分类器。这与我们 `HardRule`「模型外确定性裁决」是根本分歧，不可调和，只能各守一边。
3. **它的门禁装置齐全但门是软的**：有版本、diff、staging、灰度、A/B、审批 gate，却公开资料中未见「测试不通过不得发布」的强制；ZTI L3 甚至允许无人自动上线。这不能用来证明「门禁可以放松」，反而证明「装置齐全 ≠ 可验收」。

## 4. 与 ElevenLabs 卷的关系

两家的产品形状不同，但**治理叙事的同构度很高**（都是 See it / Steer it / Let it learn 三段式，都宣称可观测、可发布、可自改进）。差异在落点：

| 维度 | ElevenLabs | Delight |
|---|---|---|
| 主战场 | 语音 Agent 基础设施 | 企业客服/销售全渠道（语音是其中一条） |
| 编排默认形态 | 自然语言 Procedures，确定性表达式为可选第二形态 | 自然语言 Actionbook，无确定性形态 |
| 版本粒度 | Agent 整包快照（`AgentVersion` 不可变） | **资产级**版本（actionbook / profile 各自版本号）+ 选择性部署 |
| 自改进自治 | 无（本轮语料未见） | 有，且明确给出 L0–L3 四级阶梯 |
| 发布门禁 | 合并不要求测试通过 | 未见强制；L3 无人 |

结论：**ElevenLabs 与 Delight 在「门禁该在哪」上犯了同一类错，但 Delight 走得更远**。我们 S2 的独立评测 + 人工批准不能因为「头部厂商都这么做」而松动。
