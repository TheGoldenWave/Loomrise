## 1. 定位

S2 把「人长期充当配置搬运工与清洁工」换成「人提供业务真值、风险边界与发布判断，系统负责发现问题、生成候选、验证与整理证据」。三条边界不因运行频次而松动：**经验不因出现次数多就自动生效；事实不自动升级为知识；能力更新不立刻全量。**

S2 覆盖能力演进路线中的两级——经验技能化与评测驱动的自进化。任务内适应由 S1 部分覆盖；长程连续运行属后续服务端能力；跨会话记忆维持「带来源、有效期和删除入口的上下文，不与知识库互相自动升级」；多 Agent 集体进化不是本项目的目标。

## 2. 对象模型

### 2.1 新增对象

| 对象 | 用途 | 关键字段 | 生命周期 |
|---|---|---|---|
| `PolicyProfile` | 策略档位：一整套「风险分类 + 阈值 + 审批要求」的命名组合，可复制、可 diff、受版本管理 | `id/version/name`、`risk_tier_overrides`、`thresholds`、`approval_requirement`、`valid_until`、`baseline_snapshot`（生效版本、阈值、资料与工具版本） | `draft → approved → active → expired → retired` |
| `CaseNomination` | 系统提名：把可疑运行标为线索，不构成真值 | `id`、信号类型（确定性 / 行为异常）、证据引用（`run_id`、轮次、命中规则、加载或跳过、成本）、`status`、确认人 | `nominated → confirmed → promoted_to_case` 或 `nominated → false_positive` |
| `Rollout` | 灰度发布的状态，挂在 `Release` 上 | `mode`（`full` / `canary`）、`percent`、`unit`（会话或用户）、`status` | `canary_running → canary_stopped` / `→ full` / `→ rolled_back` |
| `ExampleSnippet` | 话术 / 表达范本，可检索召回，不独立成库 | `id/version`、触发条件标签（环节、意图、字段齐备度）、归属 `Skill`、共享标记与引用方、来源证据（人工编写 / 提炼自哪个已发布案例） | 随所属 Skill 版本演进；改动属表达层，走候选门禁 |

`EvalSet` 增加 `tier` 维度，分为三层：**`golden`**（人工审定真值，稳定、可复现、受版本管理，只用于一票否决项与关键回归）、**`pending`**（待确认池，人确认真值后才升级）、**`blind`**（从运行中抽样，多数只做确定性裁决，仅业务语义部分抽检人工真值）。

#### 样本的两个去向（已确认，范围记录第 25 条）

三层之上再增加一个**用途维度 `usage`**，把样本分成两个互不相通的池子：

| 池子 | 由谁组成 | 使用方式 | 回答的问题 |
|---|---|---|---|
| **回归池** | `golden` + `pending`（`usage=diagnosable`） | 每次候选必跑，可反复用 | 有没有退步 |
| **Gate Reserve** | `blind` 的一个批次（`usage=gate_only`） | 只在最终发布 Gate 跑一次，用过即归档 | 改善是不是真的 |

由此确立一条结论边界：

> **`golden` 上的通过率只作为「不退步」的证据，不得作为「改善」的证据。** 审批页上这两栏必须分开显示，改善只能由 Reserve 支撑。

Reserve 取 `blind` 批次而非从 `golden` 切割：`golden` 只有 50+ 例且每例人工审定，是最稀缺的资源，切走一部分会削弱哨兵、且补新案例的速度会卡住发布节奏；`blind` 便宜、可持续补、天然新鲜，测的正是泛化。Reserve 判定较弱（多数只做确定性裁决）这一弱点由两点承担：blind 的业务语义抽检比例（不低于 20%，可按需上调）提供业务信号；改善的最终判断权仍在人工审批。

具体规则：

1. **`blind` 按批次消费**：每批只服务一次发布 Gate，用过即标记 `consumed` 并归档，下一批重新抽样。诊断、归因、候选生成、迭代回放一律不得引用未消费的当前批次。
2. **`golden` 不做批次消费，保留全部 50+ 例做关键回归**，其结论只判不退步。
3. **Reserve 表现差不构成修改案例的理由**：不得因候选在 Reserve 上失败而回填真值、把案例移出 Reserve 或降级为 `pending`。真值修正仍只允许源于业务判断变化或当初标注错误（范围记录第 16 条）。
4. **批次消耗后强制补新**：Gate 用掉一批就抽一批新的补齐；抽样由系统做，涉及人工真值的部分由人承担。
5. **降级路径**：某场景 blind 供给不足时，允许临时从 `golden` 划一次 `gate_only` 切片，但必须显式记录理由与回补计划，不得成为常态。

### 2.2 扩展的现有对象

- `ChangeProposal` 增加：`origin`（`system_generated` / `human_edit`）、`risk_tier`（低风险 / 高风险）、`merged_source_cases`（按共同原因归并的来源案例，保留逐例追溯）、`policy_profile_ref`、`canary_plan`。
- `EvalResult` 增加：`case_set_version`、`policy_profile_version`、`threshold_snapshot`。**回放报告必须写明所用的案例集版本与档位版本**，否则历史结论不可比。
- `SkillManifest`：新建 / 拆分 / 合并时，适用条件、退出条件与转人工条件成为**必填字段**并做 Schema 校验。
- `Case` 增加：真值审定记录（谁、何时、依据）、归档状态（归档后保留历史判定，不再参与门禁），以及 `usage`（`diagnosable` / `gate_only`）与 `batch_id`（所属批次，用于批次消费与 `consumed` 标记）。
- `EvalResult` 增加：本次评估所用批次的 `batch_id` 与是否属于 Gate（区分「关键回归」与「最终 Gate」两类结论）。

### 2.3 不受自进化影响的边界

`HardRule`、`ToolPolicy` 的授权范围与副作用等级、确认要求、幂等策略、`Outcome` 语义、发布审批权与数据保留策略，只能形成待审提案，不进入自动候选范围。Skill 不授予权限，新建 Skill 不获得任何新权限。

## 3. 关键流程

### 流程 A：坏例进入

```text
运行信号（确定性：硬规则命中/工具失败/超时/未确认写入/结果缺失/重复写入）
行为异常（多轮自我纠正/澄清轮次异常/加载异常或预算截断/成本突增/输出偏离）
        │
        ▼
   CaseNomination（必须附可观察证据：哪一轮、命中哪条规则、加载或跳过了什么、成本多少）
        │
        ▼
   人确认业务真值（期望业务状态 + 必须做/禁止做的动作；原因可选）
        │
        ├──► 确认为坏例 → 进入 golden 或 pending
        └──► 判定误报 → 记为提名器负样本，用于后续调整提名信号
```

**多轮自我纠正只说明某处不一致，不等于限制不足。** 归因由系统分析、人确认；系统归因不替代人工审定的真值。提名器本身有版本、阈值与治理，其调整走与候选版本相同的审批。

### 流程 B：归并 → 候选生成

```text
已确认坏例（按共同原因归并）
        │
        ▼
  生成一处尽可能小的候选修改（允许删除、合并重复内容，而非只追加）
        │
        ▼
  ChangeProposal：origin + risk_tier + 来源案例追溯 + 父版本 + 结构化 diff
        │
        ▼
  提交校验：确定性冲突（硬规则冲突/越权/缺证据）阻断；
            模型识别的重复或语义冲突只给建议，不阻断
```

### 流程 C：评测门禁

```text
冻结环境与资料/工具模拟版本 → 读取已登记阈值（不得运行中为通过而放宽）
        │
        ├── 一票否决项（不进打分）：硬规则违规 / 关键退步 / 缺证据
        ├── 确定性裁决：越权、重复写入、未确认写入、结果缺失
        ├── 软质量机评：只补充，必须由人工校准
        └── 成本与延迟对比
        │
        ▼
  旧版与候选版配对批量回放，分两类结论，互不混用：
    · 关键回归（回归池：golden + pending，可反复跑）→ 只判「不退步」
    · 最终 Gate（Gate Reserve：当前 blind 批次，只跑一次）→ 判「改善为真」
        │
        ▼
  Gate 跑完：该批次标记 consumed 并归档，抽新批次补齐
        │
        ▼
  产出 EvalResult（含案例集版本、批次号、档位版本、阈值快照）
```

诊断、归因与候选迭代过程中**不得引用当前未消费的 `gate_only` 批次**；Reserve 只在最终 Gate 出现一次。

阈值由人登记初始值，作为受版本管理的配置；系统可提出调整建议并附证据（机评与人工校准一致率、误报率、成本漂移），但必须走与候选版本相同的审批。

### 流程 D：审批与发布

```text
候选版本进入审批页
  展示：改动摘要 / 关联案例 / 旧版与候选版配对回放对比 / 硬规则检查结果 / 成本变化
  回放对比分两栏且不得合并：不退步（golden + pending 关键回归）｜ 有改善（Gate Reserve）
  版本差异用类 VS Code 的 diff 视图；详细轨迹按需展开
  标记：来源是人还是系统归纳；是否处于临时放宽窗口
        │
        ├── 低风险：人一次审阅批准整个版本
        └── 高风险：逐项审批（硬规则、工具权限与副作用、价格或业务承诺、业务结果语义）
        │
        ▼
  发布 → Rollout（full 或 canary）
        │
        ▼
  观察期：确定性红线命中 → 见流程 E
```

编辑者与审批者分别记录；单人项目允许自审，多人团队可启用强制复核；确定性安全门禁始终有效，不因自审或豁免绕过。

### 流程 E：观察、止损与回滚

```text
全量生效版本命中确定性红线 → 自动回滚到上一个已发布版本并告警（留证，人可推翻，推翻需审批）
        │
灰度期命中确定性红线 → 自动把灰度比例降到 0（停止新流量进入，不切版本，不打断在途请求）
        │              回滚 / 恢复灰度 / 扩量 全部由人决定
        ▼
软质量下降或成本漂移 → 系统告警并呈现证据，由人决定是否回滚
        │
        ▼
策略档位的切换（含收紧方向）只由人发起；可预设切换时间，到点直接生效，
但需先校验基线快照；若生效版本、阈值、资料或工具版本已变化，则转为待审批项。
切档后进入强制观察期。
```

回滚只回退到上一个已发布版本，不做跨版本搜索或自动修补。

## 4. 权限矩阵

| 动作 | 系统 | 编辑者（人） | 审批者（人） |
|---|---|---|---|
| 提名可疑案例 | 可（须附证据） | 可标记 | — |
| 确认业务真值 | 不可 | 可 | 可 |
| 提出表达与执行策略候选 | 可 | 可 | — |
| 提出新建 / 拆分 / 合并 Skill | 可 | 可 | 审批 |
| 提出硬规则、权限、承诺、结果语义的修改 | 只可形成待审建议 | 可 | 逐项审批 |
| 修改阈值 | 只可提议 | 可 | 审批（与候选版本同流程） |
| 切换策略档位 | 只可提议，不可执行 | 可发起 | 审批 |
| 批准低风险版本 | 不可 | 可（多人团队需他人复核） | 可 |
| 启动灰度 / 调整比例 / 扩量 | 不可 | 可发起 | 审批 |
| 停止灰度（红线命中） | 自动（比例归零） | 可 | 可 |
| 回滚已发布版本 | 自动（确定性红线） | 可发起 | 可（推翻自动回滚需审批） |

原则：**安全方向可以自动，放宽方向必须人工。** 系统永远不能自行扩大自己改动的影响面，也不能自己决定及格线。

## 5. 验收清单

对应 ROADMAP 中「非开发者不改代码完成建 → 试 → 看 → 改 → 回滚」：

1. 非开发者可在工作台完成：建场景 → 试运行 → 看证据 → 改策略 → 验收 → 审批发布 → 回滚，全程不改代码。
2. 场景包向导生成可审阅的 `AgentSpec` 草稿，并冻结版本。
3. `Case` 真值描述业务状态、必须 / 禁止动作与预期持久副作用，而非唯一标准话术。
4. 样本分 `golden` / `pending` / `blind` 三层，并按 `usage` 分为回归池与 Gate Reserve；回放报告标注案例集版本、批次号与档位版本。
5. 黄金集受控演进：新增、真值修正、归档三类变更均审批留证；**不存在因候选输出不同而回填真值**的记录。
6. 系统可提名可疑案例并附可观察证据；提名器有版本与治理。
7. 候选按共同原因归并，允许删除与合并；每个来源案例可追溯。
8. 确定性冲突阻断提交；模型识别的语义冲突只作建议。
9. 审批页展示改动摘要、关联案例、配对回放对比、硬规则检查结果、成本变化与类 diff 视图；标记来源（人 / 系统）与放宽窗口状态。
10. 阈值在跑候选前登记，运行中不放宽；调整走同一审批。
11. 发布支持灰度；灰度数据不进黄金集。
12. 确定性红线命中：全量版自动回滚、灰度版自动停止暴露；两者均留证且可被人推翻。
13. 策略档位可创建、复制、diff、切换、带有效期回落；切换全程留证。
14. 人工编辑产生的候选与系统候选走同一门禁。
15. 配置可导出到干净实例重新运行并复现回放结论。
16. 示例片段的召回路径被评测覆盖：改示例或调召回参数后，回放能验证「该命中时仍命中、不该命中时被过滤」；盲测集中存在专门覆盖召回路径的案例。
17. **Reserve 不回流，且 `golden` 不充当改善证据**：诊断、归因与候选迭代过程中不出现当前未消费的 `gate_only` 批次；Gate 用后标记 `consumed` 并强制补抽新批次；不存在因 Reserve 表现差而修改或移出案例的记录；审批页把「不退步（golden）」与「有改善（Reserve）」分两栏显示，`golden` 通过率不得作为改善证据。

## 6. 待定项与默认建议

以下仍是待定，此处给出默认建议，确认后即写入正式设计：

| 待定项 | 默认建议 |
|---|---|
| 内置高风险清单是否增减 | 维持四类：硬规则、工具权限与副作用、价格或业务承诺、业务结果语义；建议**增加「身份与授权范围」与「外部写入」** |
| 临时授权与档位有效期上限、是否可续期 | 默认限期 7 天，允许续期一次，续期需重新审批 |
| 观察期时长、判定信号与超期处理 | 默认 24 小时或前 100 个请求（先到为准）；超期未复核则告警但不自动变更版本 |
| 多人团队强制复核的配置方式 | 默认按场景开关；开启后编辑者与审批者不得为同一人 |
| 提名器的初始信号清单与误报反哺 | 先只启用确定性信号，行为异常信号作为第二批；误报率超过登记值即触发提名器调整提案 |
| 各场景阈值初始值与基线采集 | 用首个场景的首轮全量回放结果作为基线，人工确认后登记，不作为长期阈值 |
| 盲测集抽样方法、抽检比例与确定性裁决维度 | **抽样方法已定**：按批次消费，每批只服务一次发布 Gate，用过即归档并抽新批次补齐（见 §2.1）。仍待定：每批规模。业务语义类抽检不低于 20%，Reserve 判定偏弱时可按需上调；确定性裁决覆盖越权、重复写入、未确认写入、结果缺失 |
| 黄金集是否分「必跑 / 定期跑」两层 | 建议分：核心层每次候选必跑，扩展层关键发布或定期跑 |

## 7. 明确不做

见[范围讨论记录](S2-SCOPE-DECISIONS.md)中的 12 条边界，其中「在线灰度分流」已移出不做清单并纳入设计范围。要点包括：不默认开放生产外部写入；S2-b 可接 Telegram/Email 授权沙盒，S2-c 可做真实工具沙盒联调；部署认证在 S3 验收，多租户与其他渠道在 S4 独立验收；公开 Demo 承载仍待决定；不自动发布；系统不自动切换档位或校准阈值；不做多 Agent 编排、跨会话长期记忆优化、插件市场、在线训练与微调；不由模型独自裁定业务真值。
