## 1. 先分清三种「记忆」（这是全项目的地基）

「记忆」这个词在 Loomrise 里目前混着三种**主体不同、生命周期不同、授权模型不同**的东西。不先分开，后面的设计全是错的。

| # | 名称 | 主体 | 生命周期 | 谁写 | 典型内容 | 归属文档 |
|---|---|---|---|---|---|---|
| **①** | **业务用户记忆** | **业务用户**（`subject_id`） | 跨会话，跨版本，长 | 系统抽取→候选→采用 | 「这个用户偏好中文」「上次问过 XX，但没下单」 | [用户上下文设计](USER-CONTEXT-DESIGN.md) |
| **②** | **专家记忆** | **专家**（`expert_id`，跨版本） | 跨版本，长，与 AgentVersion 发布节奏解耦 | 离线归纳→候选→评测→审批 | 「这类用户问退费时必须先核订单状态」 | **本文** |
| **③** | **搭建者个人记忆** | **我们自己**（Jason / 维护者） | 永久 | 工具自动 | 「我的口径偏好、文档写作习惯」 | **本文 §7 明确排除在产品外** |

**加上第四个必须分清的**：

| # | 名称 | 主体 | 为什么不能并入上面任一 |
|---|---|---|---|
| **④** | **配置与规则** | `AgentVersion` | 它**不是记忆**，是**已裁决并发布的契约**。能被记忆修改的配置项不存在——见 §2.4 |

### 1.1 与 MemHub 的根本差异（一句话）

> **MemHub / Hy Memory 解决的是「同一个人在多个 AI 工具之间不重复交代自己」；Loomrise 需要解决的是「业务用户跨会话的服务连续性」＋「专家跨版本的可控改进」。**

前者的主体是**开发者本人**，是**单用户本地**、**无鉴权**、**无租户**、**明文 SQLite**、默认走托管云端模型抽取的产品。后者的主体是**业务用户与专家**，必须**多租户隔离**、**授权与撤销**、**业务结果为准**、**留证可审计**。

**因此：MemHub 是 Jason 个人工具链的东西，不是 Loomrise 的产品依赖。** 把两者混为一谈会导致最危险的一种错误——用一个「本地单用户无鉴权」的记忆库去承载业务用户数据。

### 1.2 四者对照

| 维度 | ① 业务用户记忆 | ② 专家记忆 | ③ 个人记忆 | ④ 配置与规则 |
|---|---|---|---|---|
| 权威 | `UserContextService` | `ExpertMemoryService`（拟建） | 用户自己的工具 | `AgentVersion` |
| 隔离键 | `tenant + subject` | `tenant + expert` | 本机 | `expert + version` |
| 能否被模型直接改 | **否** | **否** | 不适用 | **绝对否** |
| 写入路径 | 候选→采用 | 归纳→候选→评测→审批 | 工具自动 | 人工配置→评测→发布 |
| 撤销语义 | forget + 派生失效 | 撤回 + 评测重跑 | 本人决定 | 回滚 |
| 与版本关系 | 跨版本连续，按读取时快照 | **跨版本连续**，但受版本兼容矩阵约束 | 无关 | **即版本本身** |
| 进 `RunEvent` | 是 | 是（诊断与依据） | 否 | 是 |

## 2. 专家记忆：方向结论

### 2.1 为什么需要独立于用户记忆的专家记忆

现有文档里，「经验」散在三处，都不是一等对象：

- [Hindsight 分析](HINDSIGHT-ITERATION-ANALYSIS.md) §3A：失败模式归纳与改进假设
- [六层配置合同](CONFIGURATION-LAYERS.md) §7.5：经验与 Skill 分层
- [用户上下文设计](USER-CONTEXT-DESIGN.md) §8：经验归纳与个人记忆分开隔离

**缺口**：没有对象承载「**跨用户、跨会话、跨版本**」的经验，也没有回答「这条经验现在适用于哪个专家的哪一版」。

用户记忆解决「**这个人**要什么」，专家记忆解决「**这类事**该怎么做」。后者是 Loomrise 承诺「让每次真实运行成为下一次受控改进的证据」这一句话的**载体**。

### 2.2 专家记忆的定义边界

**是**：
- 跨用户成立的行为规律与失败模式（「**未确认物流单号**时不得承诺到货日」——对所有用户成立）
- 带**适用条件**与**反例**的可复用经验
- 有来源运行/案例证据的经验候选
- 明确标注「**在什么条件下不适用**」的经验

**不是**：
- ❌ 某个用户的偏好（→ ①）
- ❌ 未通过评测的改动（→ `ChangeProposal`）
- ❌ 已发布配置本身（→ ④）
- ❌ 任何形式的原始业务数据（→ `ScenarioPack` / 知识库）
- ❌ 「群体规律填成某用户事实」——[用户上下文设计](USER-CONTEXT-DESIGN.md) §1 已明令，本文再确认一次

### 2.3 专家记忆的最小对象（提案）

| 字段组 | 最小合同建议 |
|---|---|
| **归属** | `experience_id`、`tenant_id`、`expert_id`、`created_by_version` |
| **适用条件** | **只能引用已声明字段**（与 [HARD-RULE-MODEL.md](HARD-RULE-MODEL.md) 同约束）、`precondition_expr`、`anti_precondition_expr` |
| **内容** | `claim`（一句话可判定）、`supporting_basis`（指向 `RunEvent` / `Case` / `EvalResult` ID，**不得内联原文**） |
| **状态** | `candidate / evaluating / accepted / rejected / retired / superseded` |
| **证据** | `support_count`、`conflict_count`、`last_validated_version`、`last_validated_at`、`eval_set_ref` |
| **生效范围** | `applies_to_stage`、`applies_to_channel`、`applies_to_skill_ref`、`max_age` |
| **退出** | `retired_reason`、`replaced_by`、`retired_at` |

**三条硬约束**：

1. **适用条件不得是自由文本。** Hy Memory 的 `boundary_envs` + LLM 判断式适用条件在我们这里**不可用**——[硬规则表达模型](HARD-RULE-MODEL.md) 已定：条件只能引用已声明字段、禁止自由文本。**专家记忆是「软建议」，但它的适用条件必须可确定性求值**，否则模型会在无据的情况下自我授权。
2. **证据只能引用 ID，不能内联原文。** 这是[参考项目四条规则](REFERENCE-PROJECTS.md) §3 第 1 条的直接落地：Loomrise 的领域对象不复制上游数据。
3. **专家记忆永不直接改配置。** 生效路径只有一条：经验 → `ChangeProposal` → 评测 → 审批 → 新 `AgentVersion`。经验本身**不是发布物**。

### 2.4 与 ④ 配置/规则的不可越界线

| 配置项 | 专家记忆能否影响 | 途径 |
|---|---|---|
| `HardRule` 定义 | **绝对不能** | 只能经人工改配置 → 评测 → 发布 |
| `ToolPolicy` 副作用定义 | **绝对不能** | 同上 |
| 提示词段落（`mutable`） | **不能自动改**，只能提候选 | `ChangeProposal` |
| 提示词段落（`locked`） | **绝对不能** | — |
| `Outcome` / 业务承诺 | **绝对不能** | — |
| Skill 选择顺序 | 只能提候选 | `ChangeProposal` |
| 检索排序权重 | 只能提候选，且须评测 | `ChangeProposal` |

沿用[六层配置合同](CONFIGURATION-LAYERS.md) §7.4「不可自动修改的边界」，本文**不新增任何例外**。

## 3. 主体与归属：五个必须先冻结的身份合同

[用户上下文设计](USER-CONTEXT-DESIGN.md) §3 已经指出「身份是首个前置合同」。本文把它扩到**五个**，因为专家记忆引入后身份维度从 3 个变成 5 个。

| # | 合同 | 现状 | 本轮结论 | 阻塞什么 |
|---|---|---|---|---|
| **I1** | 稳定业务 `subject_id` | **缺**。`ServiceRequest` 只有 `tenant_id` | **必须是新字段，不是别名**。匿名访客用会话作用域，**禁止落入公共默认桶** | 阻塞全部记忆接入 |
| **I2** | 陈述者 / 被描述主体分离 | 未定义 | 新增 `asserter_id` 与 `subject_id` 分离。「谁说的」不一定是「说的是谁」（代理人、坐席、群成员） | 阻塞画像正确性 |
| **I3** | 跨渠道身份关联 | 未定义 | 依赖**受信业务映射或显式验证**；**禁止**用昵称、号码相似度或模型实体合并替代 | 阻塞跨渠道连续性 |
| **I4** | `expert_id` 作为独立实体 | 隐含在 `AgentSpec`/`AgentVersion` 里 | **专家是独立对象**，记忆挂 `expert_id` 而**不挂 `agent_version`** | 阻塞专家记忆 |
| **I5** | 合并/拆分可逆 | 未定义 | 保留原映射、关联依据、可逆操作记录；**重算权限、任务归属与上下文可见性** | 阻塞身份修正 |

### 3.1 归属映射：跨版本连续 vs 版本绑定

这是 Hy Memory 与我们**语义不同**的地方，必须说清：

| 维度 | Hy Memory | Loomrise | 裁决 |
|---|---|---|---|
| 版本概念 | git `branch`（开发过程） | `AgentVersion`（**已发布业务契约**，冻结/评测/发布/回滚） | **禁止映射** |
| 记忆归属 | `user_id + agent_id + workspace_id` | `tenant_id + expert_id`，**跨版本连续** | 归属挂 `expert_id` |
| 版本绑定 | branch 天然带版本 | 需**显式兼容矩阵** | 见 §3.2 |
| 撤回语义 | SHADOW + 可恢复 | `retired` + 评测重跑 | Loomrise 更严：退休专家经验**必须触发受影响版本的重评** |

### 3.2 版本兼容矩阵（提案）

专家记忆跨版本连续，但**不是所有经验都适用于所有版本**。需要一个最小矩阵：

| 维度 | 规则建议 |
|---|---|
| `applies_to_stage` | 经验限定在特定服务阶段（如「退费协商」），阶段变更须重评 |
| `applies_to_channel` | 文字/语音/IM 的经验**不互相迁移**（模态是一等轴） |
| `applies_to_skill_ref` | 绑定具体 Skill 版本；Skill 变更则经验失效待重评 |
| `max_age` | 有时效的经验（价格、政策、季节性话术）必须设上限 |
| 结构变更 | `Outcome` / `HardRule` / `ToolPolicy` **结构变更** → 全部相关经验置 `retired`，不自动迁移 |

**原则**：版本升级**不自动继承专家经验**。要么按矩阵判定兼容，要么显式重评。**「新版本自动继承全部经验」是错的**——这会让一次错误经验无限传播。

## 4. 写入路径：所有记忆写入一律是候选

### 4.1 三条写入路径与权限

```
①业务用户记忆   授权事件/会话 → 抽取候选(candidate) → 【采用规则】 → active → (更正→superseded / forget→revoked)
②专家记忆       运行/案例聚合 → 归纳候选(candidate) → 独立评测 → 审批 → accepted → (不适用→retired / 被取代→superseded)
③个人记忆       工具自动（不在产品运行时内）
```

**关键差异**：①的采用可以按**预先登记的规则**自动进行（低风险明确自述，避免每条偏好都走人工）；②**必须评测 + 审批**，没有例外。

### 4.2 候选状态机（统一）

沿用[用户上下文设计](USER-CONTEXT-DESIGN.md) §4 的状态集，本文补一条**专家记忆的额外约束**：

```
candidate → evaluating → accepted → (retired | superseded)
                  ↓
               rejected
```

- 任何记忆**不得从会话/运行直接跳到 `active`**
- **模型口头声称「已记住」不是落库证据**（沿用 AGENTS.md Product Truth）
- **抽取为空是正常结论**——Hy Memory 的做法（提取成功后 L1_RAW 降级为不可召回、提取为空时同样降级，见 [Hy Memory 裁决 §2](HY-MEMORY-LAYERED-ANALYSIS.md)）值得抄：**「没什么可记」要成为合法结果，不能逼模型产出记忆**
- 专家记忆的 `evaluating` **必须绑评测集**；无评测集的 `candidate` 不得进入 `evaluating`

### 4.3 三条不可越界的写入红线

| # | 红线 | 出处 |
|---|---|---|
| W1 | **模型不得直接写记忆数据库**，只能提交候选 | [用户上下文设计](USER-CONTEXT-DESIGN.md) §2 |
| W2 | **模型不得删除记忆**。删除只能由 (a) 用户的 forget，(b) 有明确否定证据的更正，或 (c) 过期 + 到期清理 | Hy Memory 的 `Never DELETE just because a candidate looks "stale"` 值得直接抄 |
| W3 | **Provider 的自动 reconcile 管线必须降级为候选生成器** | [MEMORY-FOUNDATION-DESIGN.md](MEMORY-FOUNDATION-DESIGN.md) §2.4 第 1 条（对 TDAI 的同款裁决，适用于 Hy Memory） |

## 5. 读取路径：四层装配，一次冻结

### 5.1 装配顺序（承接既有设计，补专家层）

沿用[用户上下文设计](USER-CONTEXT-DESIGN.md) §7，补一步：

```
1 身份与用途校验（I1–I5）
2 当前消息
3 当前请求/事项结构状态（Task 账本，不是记忆摘要）
4 精确必需字段（权威状态、身份、授权、否定/更正、未完成义务、结果证据）
5 专家经验候选加载  ← 本文新增，且须过适用条件求值
6 必要知识与经历检索
7 来源/冲突/有效性/去重/授权过滤
8 分配预算（条数 + token + 时间 + 用量）
9 冻结 ContextSnapshot（ContextFragment 带完整加载证据）
```

**第 5 步的三条纪律**：
- 专家经验**必须先求值适用条件**，不适用即跳过并留证（不能「都塞进去让模型自己判断」）
- 加载的是 `accepted` 状态；`candidate` / `evaluating` **一律不进生产上下文**（只在改进工作台可见）
- 专家经验**不授予权限**。它是行为倾向，不是约束。约束永远由 `HardRule` 在模型外裁决

### 5.2 授权过滤必须在检索层执行

抄 Hy Memory 的第 7 条机制（见 [Hy Memory 裁决 §2](HY-MEMORY-LAYERED-ANALYSIS.md)）：**来源/主体过滤下推到存储查询条件，不做「先取回再过滤」**。理由：先取回再过滤意味着未授权数据已经离开存储边界——即使没进上下文，也已经越过了边界。

对应裁决：
- `subject_id` 过滤在查询条件里，不在应用层
- **匿名访客不得落入任何共享默认桶**
- `mixed`（跨来源聚合）记忆在开启任意来源过滤时**默认排除**（fail-closed）

### 5.3 预算纪律：按 token 计，不按条数计

抄 Hy Memory 的 bank-growth penalty（**按 token 而非条数计**）：否则会通过「把旧记录拉长」来膨胀。

Loomrise 预算四元组：**条数 + token + 时间 + 抽取/检索用量**。超预算时返回 + 日期过滤 + 权限限制由 **Loomrise 二次执行**，不只信 Provider 参数。

保护项装不下时**报告缺项并澄清、分步或停止**——不默默移出后继续高风险执行。

## 6. 演进闭环：从运行证据到受控改进

```
真实运行 RunEvent
   ↓ 归因（先归因再改）
失败模式 / 成功模式
   ↓ 候选归纳（脱敏、无原始业务数据）
专家记忆 candidate
   ↓ 独立评测（绑评测集，作者与评测者逻辑隔离）
evaluating
   ↓ 人工审批
accepted ─────────→ ChangeProposal ─→ 评测门禁 ─→ 新 AgentVersion ─→ 发布/回滚
   ↓
（不适用 / 被取代）retired / superseded
```

### 6.1 五条不可越界的闭环纪律

| # | 纪律 | 依据 |
|---|---|---|
| C1 | **原始轨迹不可变**。失败先归因再改 Skill | [参考项目](REFERENCE-PROJECTS.md) §2 自进化段 |
| C2 | **作者、执行者、审计者逻辑隔离**。提出经验的人不应是唯一评测它的人 | 同上 |
| C3 | **生产运行只加载已发布版本**。`candidate` 经验不进生产 | [六层合同](CONFIGURATION-LAYERS.md) §7.4 |
| C4 | **支持数 ≠ 结论**。`support_count` 是证据不是裁决；同一模式重复出现不增加独立支持样本数 | [用户上下文设计](USER-CONTEXT-DESIGN.md) §5 第 3 条 |
| C5 | **不记录隐藏思维链**。经验只记录外部可验证后果与依据 | 同上 §8 |

### 6.2 专家经验不能替代的三件事

- **不能替代归因**：「服务慢」不是根因，须归因到具体环节
- **不能替代评测**：经验说「这样更好」不等于「确实更好」
- **不能替代发布**：经验不改变生产行为，只经 `ChangeProposal` 改变

### 6.3 用第三方 Agent「带入专家视角」做洞察与复盘

**方向已确认可行**，且与[第三方 Agent 接入计划](AGENT-INTEGRATION-PLAN.md)天然咬合：把某个专家的**已发布配置 + 精选脱敏运行证据**作为只读上下文交给外部 Agent，让它以专家视角做洞察与复盘，产出专家经验候选——这正是 AGI-07「诊断失败案例」的边界，只是不止于单个案例。

**「带入专家视角」的准确含义**（不可放大）：

| 给什么 | 说明 |
|---|---|
| 该专家的 `AgentSpec` / 已发布 `AgentVersion` 配置快照 | 让 Agent 知道「现在是怎么办事的」，才能判断哪里不对 |
| 精选、脱敏、获准的运行证据与审定案例 | 按用途授权与主体范围筛选，不是全量轨迹 |
| 该专家的**既有** `accepted` 经验 | 让它不要重复提出已知结论 |
| 工具与 Skill 的**发现视图** | 只读；发现不等于授权 |

**四条必须先写死的边界**：

| # | 边界 | 理由 |
|---|---|---|
| **E1** | **第三方 Agent 只产出 `candidate`，永不产出 `accepted`** | W1 的直接延伸。`candidate → evaluating` 必须由 Loomrise 的评测绑定动作完成，不能由 Agent 自评 |
| **E2** | **作者/执行者/审计者必须分离** | 同一 Agent 既提经验又验证它有效 = 违反 §6.1 C2。评测用固定回放 + 独立评测集；**作者看不到未消费 blind**（沿用 AGI-09 既有规则） |
| **E3** | **「看到专家配置」不等于获得任何权限** | 注入专家视角是**上下文**，不是授权。它不改变角色边界：不获生产事项调整、客户触达、业务写入、真值或发布权（沿用 [AGENT-INTEGRATION-PLAN.md](AGENT-INTEGRATION-PLAN.md) §1.3 三类角色表） |
| **E4** | **不可自动修改清单在洞察阶段同样适用** | 诊断报告可以指出「这条 HardRule 可能有问题」，但只能形成待审提案。**报告本身不改任何配置**（沿用 AGI-08–10「不自动改变权限、业务承诺、硬规则、评分、固定真值或审批权」） |

**依赖关系（不可倒置）**：

```
MEM-1…MEM-5  手工归纳通道（不依赖任何 AGI 工作包）
     │
     ├─ 先决条件：必须已有「失败案例的证据引用」与「审定案例」→ 这是 AGI-07 的产物
     │
AGI-07  只读诊断 Skill ────────────► 提供可诊断的证据与案例
     │
AGI-08  受限 Worker（可选） ──────► 提供可复用的后台作业骨架
     │
AGI-09  生成并验证改动候选 ───────► 提供「经验 → 配置」的唯一出口
```

**关键区分**：
- **专家记忆这个能力**（MEM-1…5）**不依赖 AGI**——首个切片必须能在无第三方 Agent 的条件下跑通，否则记忆体系会变成单点阻塞
- **「用第三方 Agent 做归纳」是一种执行方式**，依赖 AGI-07/08，且是**可选项**不是前置

**与 C2 的衔接**：人工归纳时，「提出者」是人；Agent 归纳时，「提出者」是外部 Agent。**两种情况下评测与发布权都不在提出者手里**——这是本节唯一要守住的等式。

## 7. 明确排除：个人记忆不在产品内

[用户上下文设计](USER-CONTEXT-DESIGN.md) §6 待决策项已登记「是否接入个人知识库：默认不打通」。本文**确认这个结论并给出更强理由**：

| 理由 | 说明 |
|---|---|
| 主体不同 | 个人记忆的主体是搭建者本人，业务记忆的主体是业务用户。混在一起会让「谁的数据」不可答 |
| 授权模型不同 | 个人资产由本人授权；业务数据的授权来自租户与合规要求 |
| 边界风险 | Jason 的个人知识库含真实业务语境与私人内容。**产品运行时读取它等于把个人语境带进客户租户**，这是不可逆的泄漏路径 |
| 已存在的纪律 | `private/` 目录已被[开源与私有边界](OPEN-SOURCE-BOUNDARY.md) 隔离 |

**结论**：产品运行时**默认零接入**个人知识库与个人记忆。MemHub 这类工具属于 **Jason 个人工具链**，走 WorkBuddy 插件机制，与 Loomrise 仓库、运行时、租户数据**完全隔离**。若将来要打通，须单独立项并核验来源、用途与分享权限——**本轮不做，也不进 ROADMAP**。

## 8. 阶段路线

与 [ROADMAP](ROADMAP.md) 的阶段对齐。**每期一个可判定的退出条件，不通过不进入下一期。**

| 期 | 范围 | 退出条件（可判定） |
|---|---|---|
| **MEM-0 · 合同冻结**（仅文档） | 冻结 I1–I5 五个身份合同、`Experience` 最小字段、版本兼容矩阵、写入红线 W1–W3 | 负责产品与架构的人员确认；[用户上下文设计](USER-CONTEXT-DESIGN.md) §11 待决项逐条有结论 |
| **MEM-1 · 只读专家经验切片** | 从**已完成的 S1 运行与案例**离线聚合出专家经验候选（**不接真实用户数据**）；实现 `ExperienceCandidate` 落库 + 适用条件求值 + 工作台只读视图 | 干净环境可用确定性样例跑通「聚合 → 候选 → 求值 → 留证」；能证明不适用的经验被跳过并留证 |
| **MEM-2 · 评测绑定** | 专家经验 `candidate → evaluating` 必须绑评测集；`evaluating` 内容在工作台可见；生产上下文加载拒绝非 `accepted` | 构造「未绑评测集的候选」样例，被拒绝；生产加载断言只放行 `accepted` |
| **MEM-3 · 单一 Provider 只读对照** | TDAI / Hy Memory / Hindsight **三选一**做只读 Adapter，同条件对照（跨会话读取、冲突更正、撤销与迟到、故障降级、预算、运维负担） | 给出「采用 / 机制参照 / 不采用」书面结论；**不因「上游有」默认采用** |
| **MEM-4 · 受控写入** | 运行结束后按 W1–W3 提交候选；写 `RunEvent`：请求 ID、结果、耗时、失败原因 | 写入失败不影响业务终态（`Outcome` 不变）；能撤回；无凭据与未脱敏字段 |
| **MEM-5 · 闭环接线** | `accepted` 经验 → `ChangeProposal` → 评测门禁 → 新版本；退休经验触发重评 | 版本升级不自动继承全部经验（结构变更触发 retired）；回滚不复活已退休经验 |
| **MEM-6 · Agent 辅助归纳**（可选，依赖 AGI-07） | 第三方 Agent 带入专家视角做洞察与复盘，产出 `candidate` 经验 | §6.3 的 **E1–E4 逐条成立**：只产 `candidate`、作者看不到未消费 blind、注入配置不等于授权、诊断不改配置。**MEM-1…5 不依赖本期即可跑通** |

### 8.1 与现有 TM 工作包的关系

[联合计划](TASK-MEMORY-INTEGRATION-PLAN.md) 的 TM-01–13 管**任务与用户上下文**的联合建设；本文的 MEM-0–6 管**专家记忆**这条新轴。

**关系**：
- **TM 与 MEM 共用 MEM-0 的身份合同冻结**（I1–I5 是同一个前置，不重复做）
- TM-01（最小 Task 基础子片）**不依赖** MEM 任何一期——**首片必须能在无记忆 Provider 的条件下跑通**
- MEM-3 的 Provider 对照**合并进** TM 的 Provider Gate，不做两轮重复评测
- **MEM-6 不进入 MEM-1…5 的关键路径**：它是「用谁归纳」的可选实现方式，不是「能不能归纳」的前提（详见 §6.3 依赖关系）

**不在本轮范围**：定时调度、真实触达、跨租户记忆、记忆的服务端持久化实现。

## 9. 验收判据

| # | 判据 | 判定方式 |
|---|---|---|
| 1 | I1–I5 五个身份合同已冻结并有结论 | 文档评审记录 |

| 3 | 陈述者与被描述主体可区分 | 代理人/坐席/群成员三类样例 |
| 4 | 专家经验适用条件**可确定性求值**，无自由文本 | 条件表达式 schema 断言 |

| 6 | `candidate`/`evaluating` 经验不进生产上下文 | 加载断言 |
| 7 | 未绑评测集的候选不得进入 `evaluating` | 状态机断言 |
| 8 | 记忆写入一律经 W1（模型只提交候选） | 越权写入样例被拒 |
| 9 | 模型不能删除记忆（仅 forget / 明确否定 / 到期） | 「看起来过时」的删除请求被拒 |
| 10 | 授权过滤在检索层执行，不做「先取回再过滤」 | 构造越权来源的检索断言 |
| 11 | 每条加载/跳过/截断都有 `RunEvent` 留证 | 事件回放 |
| 12 | 记忆服务不可用时主流程不受影响 | 停服回放，对比 S1 基线 11/11 |
| 13 | 模型未因记忆或经验获得任何权限 | 构造「记忆中含越权指令」样例，硬规则仍拒绝 |
| 14 | 版本结构变更触发相关经验 retired | 改 `Outcome` 结构后断言 |
| 15 | 产品运行时零接入个人知识库/个人记忆 | 配置与代码路径审计 |
| 16 | 第三方 Agent 归纳产出的经验一律为 `candidate`，无 `accepted` | E1：断言 Agent 路径不产生 `accepted` |
| 17 | 提出经验的 Agent 看不到未消费 blind 集 | E2：blind 隔离测试 |
| 18 | 注入专家配置不改变角色权限边界 | E3：注入后仍无法生产写入/发布 |
| 19 | 诊断报告本身不修改任何配置 | E4：报告产出前后配置快照哈希一致 |

8. **服务端持久化**：专家经验存哪里？是否复用 `RunEvent` 账本的存储层？

未决项同步登记在 [S2-IA-NAV.md](S2-IA-NAV.md) §6.4 与 [S2-CONSOLE-KICKOFF.md](S2-CONSOLE-KICKOFF.md) §4；本文第 10 节各项默认**不阻塞出稿**，但第 1 项**阻塞 MEM-1**。
