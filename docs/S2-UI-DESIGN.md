# S2 工作台界面设计 v0.1

状态：**设计草案，未实现**。2026-09-28。

本文是[S2 设计草案](S2-DESIGN.md)在界面层的展开，依据[S2 范围讨论记录](S2-SCOPE-DECISIONS.md) v0.6 的 24 条已确认方向。产品原则见[产品定义](PRODUCT.md)，六层职责见[六层配置合同](CONFIGURATION-LAYERS.md)，对象权威见[架构与对象权威](ARCHITECTURE.md)。本文不替代 S2 退出 Gate，也不代表任何界面已实现。

**前置依赖**：S1 退出 Gate 未全部闭合。界面设计可与 S1 收尾并行，依赖执行内核的构建以 S1 Gate 闭合为前提。

## 1. 设计原则

1. **工作台不是 Prompt 编辑器，而是「问题 → 证据 → 决定」的操作台。** 人进来要回答的是「有什么问题、要不要批、要不要回滚」，不是「这段提示词怎么写」。
2. **默认视图回答业务问题**：依据是什么、做了什么、为什么等待、实际结果是什么、代价是什么。技术 Trace 折叠，按需展开。
3. **状态永远可见**：等待输入、后台执行、等待确认、取消中、成功、失败、已取消七种状态在试用台常驻可辨。
4. **暴露不等于开放自由编辑。** 所有内容库都要在后台可见，但维护权限按风险分层，且改动一律回到同一条门禁。
5. **反堆积优先于好维护。** 每个可新增内容的地方都要有重复检测、引用计数和影响面提示，避免重演「越堆越多、无人复核」。

## 2. 信息架构

以场景为工作区，七个分区挂在场景之下：

| 分区 | 页面 | 旅程 |
|---|---|---|
| 场景 | 场景概览、场景包向导、接入与沙盒 | 建 |
| 试用 | 试用台（文字 / 语音） | 试 |
| 运行 | 运行记录、提名与坏例标注 | 看 / 标 |
| 验收 | 案例集（golden / pending / blind）、回放报告 | 验 |
| 改动与发布 | 候选与审批、发布与灰度、策略档位 | 改 / 批 / 发 / 滚 |
| 内容库 | 限制、业务知识、物料、变量、示例片段 | 支撑 |
| 交付 | 导出包与依赖清单 | 交付 |

**首页落点**：场景概览。有未处理事项时，概览页顶部出现「待我处理」区块（待确认提名、待审批候选、观察期状态）。S2 不做跨场景收件箱首页——单场景 alpha 下它是重复入口。

## 3. 核心页面

### 3.1 场景概览

顶部状态条：场景名、生效版本、当前策略档位、灰度状态。中部四个指标：待确认提名、待审批候选、黄金集通过数、单位任务成本。下部「待我处理」列表，每条锚定具体对象并显示来源（系统归纳 / 人工编辑）与时间压力（观察期剩余）。

### 3.2 场景包向导

分步生成可审阅的 `AgentSpec` 草稿：业务目标 → 资料来源与授权 → 预约字段 → 示例结果 → 确认生成。全程不出现六层配置术语。每步产出物可单独回退，最后一步给出可审阅的汇总 diff。

### 3.3 试用台

左对话区，右证据面板。证据面板分四段：依据（引用了哪些资料、哪个版本）、动作（调用了什么工具、是否需要确认）、结果（业务结果 ID 或明确失败）、代价（token、工具调用、耗时）。七种状态在顶部常驻显示。确认卡片由受约束组件生成，不执行模型生成的任意 HTML 或脚本。技术 Trace 默认折叠。

### 3.4 运行记录与提名坏例

运行列表按时间与状态筛选；提名池单列一栏，每条提名显示信号类型（确定性 / 行为异常）与可观察证据（哪一轮、命中哪条规则、加载或跳过了什么、成本多少）。

标注界面只要求填**业务真值**：期望业务状态、必须做的动作、禁止做的动作；原因可选填。系统归因显示在下方，明确标注为「建议」，不预填进真值字段。判定为误报时进入负样本记录。

**标注入口有两个**，数据进同一条流程：试用台内即时标注（上下文最完整，直接建 Case）；运行记录页批量处理（处理系统提名更高效）。

### 3.5 案例集与回放

三个 tab 对应 `golden` / `pending` / `blind`。每个案例显示真值审定记录（谁、何时、依据）与归档状态。回放报告必须标注案例集版本、档位版本与阈值快照。真值修正界面在提交前强制确认「本次修正是否因候选输出不同而回填」——该情形不允许。

### 3.6 候选与审批

```text
┌──────────────────────────────────────────────────────────┐
│ 候选 v13 ← v12   [来源：系统归纳] [低风险 · 可合批] [阈值：日常档 v3] │
├───────────────────────────────┬──────────────────────────┤
│ 版本差异（类 VS Code 行级 diff）│ 验证证据                  │
│ skill / clarifying_order      │ 黄金集配对回放 48/50→50/50 │
│   - 先询问预算，再询问时间      │ 盲测集         92%→93%   │
│   + 先询问时间，再确认预算区间   │ 硬规则检查      0 违规    │
│ sop / booking_flow   +2 −1    │ 越权/重复/未确认/缺结果 0  │
│ examples / price_answer +4 −5 │ 单位成本   ¥0.46→¥0.42   │
│                               │ 软质量机评  +0.3 · 待校准 │
│                               │ 关联案例 4（3 坏例+1 哨兵）│
├───────────────────────────────┴──────────────────────────┤
│ [批准整个版本] [逐项审批] [拒绝并说明]   详细轨迹按需展开    │
└──────────────────────────────────────────────────────────┘
```

要点：来源（人 / 系统归纳）必须可见；处于临时放宽窗口时顶部出现醒目横幅；高风险改动不可「批准整个版本」，只能逐项审批。

### 3.7 发布、灰度与回滚

版本时间线展示 `draft → tested → approved → released → rolled_back` 与每次发布的操作人、档位、观察期结论。灰度面板显示模式（full / canary）、比例、分流单位（会话或用户）、红线命中状态。比例与单位**只读**，停止灰度、恢复灰度、扩量是人工按钮并留证。确定性红线命中时系统自动把比例降到 0，面板明确显示「已自动停止暴露，等待人工决定」。

### 3.8 策略档位

当前档位卡片（名称、版本、有效期、来源基线快照）+ 切换历史。支持创建、复制、diff、切换、预设切换时间。切档动作需审批；预设切换到点直接生效前先校验基线快照，若生效版本、阈值、资料或工具版本已变化则转为待审批项。到期回落状态可见。

## 4. 内容库的管理方式

所有库都要在后台暴露——不暴露会让用户绕过工作台改数据库，版本化、审计、回放与导出复现全部失效。但暴露不等于开放自由编辑。

| 库 | 作用域 | 暴露 | 维护方式 | 风险档 | 硬约束 |
|---|---|---|---|---|---|
| 限制 | 场景级 | 必须 | 人可增删改，**逐项审批**；确定性冲突阻断提交 | 高 | 稳定 ID、作用域、来源证据；不把每个 badcase 变成新规则 |
| 业务知识 | **全局库 + 场景引用** | 必须 | 上传 / 替换 / 撤回，不编辑事实本身 | 中 | 来源、授权、有效期、版本齐全；引用记版本；撤回使关联评测与发布结论标记待重验 |
| 物料（文件） | **全局库 + 场景引用** | 必须 | 上传 / 版本 / 撤回 | 中 | 可用范围（场景、环节）、授权、有效期 |
| 变量 | 场景级 | 必须 | 作为字段 / 槽位管理 | 中 | 必须声明来源（用户提供 / 工具返回 / 检索）；不允许模型补造 |
| 示例片段 | Skill 归属 + 显式共享 | 必须 | 新建 / 修改 / 归档，走候选门禁 | 低（表达层） | 见第 5 节 |
| 运行事件 | — | **只读** | 不可人工编辑 | — | 是事实源，不是配置 |
| 触发 / 激活事件 | — | S2 仅只读视图 | 不配置 | — | 主动触达属 `OutreachPolicy`，S2 不实现 |

### 4.1 反堆积机制（三条必须一起做）

1. **每个条目显示「被引用次数 / 最近命中 / 与谁重复」**。零引用或长期未命中的**提示**归档，不自动删除——与黄金集同一条原则。
2. **新建先做重复检测**。命中相似条目时先问「修改已有还是确实新建」，不直接落库。
3. **改动任意条目都要回答「影响了谁」**：哪些场景、哪些已发布版本、哪些评测结论需要重验。

删除一律是**撤回 / 归档**，不是物理删除；已发布版本标记失效，历史判定保留。

## 5. 示例片段与召回

话术**不独立成库**。Skill 臃肿的根因是把「条件」与「表达」混在同一段文本里；分离后 Skill 只写「这个阶段做什么、按什么顺序、什么情况转人工」，可长期精简，表达下沉为可检索的 `ExampleSnippet`。

```text
当前阶段与用户意图 ──┐
                    ├─► 召回器 ─► 命中示例注入上下文（记录 load_status）
示例片段池 ─────────┘  标签过滤 →      │
（带触发条件标签 ·        语义排序 →      └─► 无命中 → Skill 默认表达（兜底）
  归属 Skill · 显式共享）  取前 N 条
```

设计要点：

1. **标签优先，语义兜底。** 先用确定性标签（环节、用户意图、字段齐备度、是否命中某规则）过滤，再语义排序，取前 N 条，N 有硬上限。话术召回错了比不召回更糟。
2. **归属 Skill，显式共享。** 默认只在本 Skill 内可召回；跨 Skill 复用必须显式发布为共享片段并记录引用方。不做「任何 Skill 都能召回的场景级公共池」。
3. **重复与冲突可计算。** 同一触发条件下多个示例 = 疑似重复；同标签下表述相反 = 冲突。两者都要能被检测并提示归并。
4. **可观测与兜底。** 每次召回写 `RunEvent`，记录 `load_status` 与 `activation_reason`；无命中时回退到 Skill 内的默认表达，不让模型自由发挥。

与已定机制的关系：这不引入新流程，只是把第 2 条中「示例」与「有限检索参数」落到具体对象上。示例片段改动属表达层、召回参数属有限检索参数，**两者都在低风险候选范围内**，改动走同一条审批门禁，召回事件进 `RunEvent`（`context_scope=evidence`），与 S1 的加载账本一致。

## 6. 开发者模式

提供一个开关，**默认关闭**。开启后显示六层配置原文、完整 Trace、上下文加载明细与召回命中详情。默认视图必须能独立支撑「建 → 试 → 看 → 改 → 验 → 批 → 滚」全流程——非开发者不应被要求打开它才能完成工作。

## 7. 界面层验收要点

1. 非开发者在不打开开发者模式的前提下，能独立完成完整旅程。
2. 审批页默认可见：改动摘要、关联案例、配对回放对比、硬规则检查结果、成本变化、来源标记、放宽窗口状态。
3. 标注界面不要求填写配置归因，只要求业务真值。
4. 内容库条目可见引用次数、最近命中与重复提示；新建触发重复检测。
5. 改动任意库条目后，界面能列出受影响场景、版本与待重验评测。
6. 召回事件在运行记录中可查：命中了哪条示例、命中原因、无命中时是否走了兜底。
7. 灰度面板中比例与单位只读，人工动作（停止 / 恢复 / 扩量）全部留证。

## 8. 待定

- 内容库页面是按库分 tab，还是按「场景用到的内容」聚合视图优先。默认建议：库 tab 为主，条目页内附「被哪些场景引用」。
- 示例片段的 N 上限与标签体系初值。默认建议：N 初值 3，标签体系先只做环节、意图、字段齐备度三维。
- 开发者模式是否对同一账号记忆开关状态。默认建议：按会话记忆，不持久。
