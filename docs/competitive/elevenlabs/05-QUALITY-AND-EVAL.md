## 1. 一句话

它有一套**完整但不设门禁**的质量装置：三类测试、可重复采样的通过率、三值的成功评估、四种护栏、六类告警。**唯独缺"过不了就不许上线"这一步**——官方把"测试通过才能合并"明确列为未来能力。所以它的质量体系是**观测装置**，不是**裁决装置**。

## 2. 测试：三类，各有明确分工

| 类型 | 验什么 | 输入 | 判法 |
|---|---|---|---|
| **Simulation（模拟）** | 整通对话是否达到既定结果 | 场景（自然语言）+ 成功条件 + 最大轮数 + 可选历史/变量/mock | 用"成功条件"评整段记录 |
| **Next Reply / Scenario（下一句）** | **只看下一句**是否满足质量/语气/政策 | 聊天历史 + 成功判据 + **正反例** | LLM 评官对比判据与例子 |
| **Tool Call（工具调用）** | 是否调对了工具、参数对不对 | 选工具 + 期望参数 | 三种校验法（见 §3） |

### 2.1 Simulation 细节

- `max turns`：**1–50，默认 5**。
- 可选：环境（多环境时出现）、**聊天历史**（从半途开始，用于测恢复）、**动态变量**（注入测试值而不改 base 配置）。
- **工具 mock 三档**：`Mock none` / `Mock all tools` / `Mock selected tools`。
- **系统工具与工作流工具永不被 mock**。← 这条很关键：它保证"结束通话""转人工"这类副作用在测试里**真的发生**，不会被假装。
- **mock 未命中时的两种兜底**：调真实工具 / 直接返回错误（**不调真实工具**）。该设置仅在至少 mock 了一个工具时出现。

### 2.2 Next Reply 的"正反例"

判据之外**必须/可以**给一段成功例子 + 一段失败例子，LLM 评官据此判。这是它把"判据"从"一句话要求"变成"可对齐的样例对"的做法。

> 与我们 `S2-EVAL-GATE-PROPOSAL` 的判据结构的差别：**例子是判据的一部分，必须与 rubric 一起冻结**——否则"赛后改例子"＝改规则。它没有这个约束（例子存在测试里，测试与判据是两套对象）。

### 2.3 从真实对话一键成用例

打开一条历史会话 → `Create test from this conversation` → 预填上下文 → 补期望行为 → 加入用例集。

> 这是我们"坏例 → 提名 → 案例"链路最接近的对手实现。差别在**谁能提名**：它允许**人**从会话建用例，也允许**模型**用 `flag_issue_for_review` 打标；我们要求"提名 ≠ 真值"，且来源要可区分。

## 3. 工具调用测试：三种参数校验（**本轮更正**）

官方文档明确三种：

| 方法 | 例子 | 性质 |
|---|---|---|
| **Exact Match** | 转接号码 `+447771117777` | 确定性 |
| **Regex Pattern** | 订单号 `^ORD-[0-9]{8}$` | 确定性 |
| **LLM Evaluation** | "应是一条礼貌的、提到已接通的留言" | 概率性 |

### 3.1 勘误（推翻 v0.4 的降级）

| 项 | 原表述 | 现表述 | 依据 |
|---|---|---|---|
| 工具参数级断言 | "UI 实际只有『选工具 + Pass if any tool matches』→ 降为 D 级" | **参数级断言存在且是三法**；后台走查未走到该编辑面板，不等于不存在。**恢复 B 级** | `customization/agent-testing` §Tool Call Testing 明确列出三法并给示例 |

这条更正的意义：**不要把"我没看到"写成"它没有"**。上一轮的降级是方法错误，不是观察错误。

## 4. 概率化：它把"通过"变成"通过率"

| 项 | 事实 |
|---|---|
| 界面 | 运行按钮上的 split-run 控件，可选 3× / 5× / 15× |
| API | `repeat_count`，**2–20**；设置后自动启用失败分桶 |
| 每次运行 | 完全独立：同样的历史/变量，**回复重新生成** |
| 适用范围 | 单条测试、文件夹、整个套件；三类测试都支持（对 Simulation 最有用） |
| 通过率徽标 | **绿 = 100%**；**琥珀 = ≥80%**；**红 = <80%** |
| 失败分桶 | 按失败原因聚类，每桶可展开到原始记录与判官理由。示例："正确路由到计费（4 次）" / "编造了一个支持电话（1 次）" |

官方给的两个使用时机（值得直接引）：

- **发版前**：重跑以确认可靠性没掉（举例"从 95% 掉到 60%"）。
- **诊断抖动**：单次失败可能是噪声；**"五次里错一次"且失败桶有名有姓**，才是可复现问题。

## 5. 成功评估：三值 + 理由

| 项 | 事实 |
|---|---|
| 位置 | agent 的 **Analysis** 页签 |
| 形态 | 每条判据 = identifier + 描述（描述直接送 LLM） |
| 上限 | **每 agent 30 条** |
| 结果 | `success` / `failure` / **`unknown`** + rationale |
| `unknown` 何时出现 | 会话未完成、用户回应含糊、转写缺信息 |
| 用途 | 会话历史里逐条展示；可经 post-call webhook 外送 |

> 三值是它最该被抄的一条：**"判不了"是合法结果**，且被明确建议"监控 `unknown` 比例以判断判据是否需要改"。我们若二值化，等于把"判据不好"伪装成"案例失败"。

## 6. 结构化抽取（data collection）

| 项 | 事实 |
|---|---|
| 类型 | `string` / `boolean` / `integer` / `number` 四种 |
| 每项 | identifier + 类型 + 描述（**描述送 LLM**） |
| 上限 | Trial / Enterprise 每 agent **40 项**；其他档 **25 项** |
| 作用域 | `conversation` / `agent`（`data_collection_scopes`，缺省 conversation） |
| 缺失时 | 返回 null 或空值，**不报错** |
| 输出 | 出现在会话历史，可按项查看 |

> "缺失返 null 不报错"是个重要的默认：它把"抽取不到"当正常态，把判定责任推给下游。我们的 `ChangeProposal` 若依赖抽取结果做条件，就必须自己定义"null 是否算未满足"。

## 7. 护栏：四类，三层，两个旋钮

### 7.1 四类

| 护栏 | 作用 | 保护层 | 延迟 | 成本 | 出口 |
|---|---|---|---|---|---|
| **Focus** | 让 agent 不跑题、贴合系统提示 | 提示加固 | 极小 | 含在内 | 无 |
| **Manipulation** | 检测并阻断提示注入 | **用户输入校验** | 无影响 | 含在内 | **直接终止会话** |
| **Content** | 标记并阻止不当内容 | **回复校验** | 取决于执行模式 | 含在内 | 可配 |
| **Custom** | 执行业务特有政策 | **回复校验** | 取决于执行模式 | **按用量计费** | 可配 |

官方主次关系写得很清楚：**系统提示加固是地基**，输入与回复校验是"漏网之鱼的修正"；关键规则**两处都写**，形成纵深。

配套技巧：模型对 `# Guardrails` 这个标题**格外敏感**，关键行为规则放这个标题下。

### 7.2 两个旋钮（每个 Custom / Content 护栏各一套）

| 旋钮 | 取值 | 代价 |
|---|---|---|
| **执行模式** | `streaming`（默认）/ `blocking` | streaming：**不增加延迟**，但回复可能**已开始播**（语音下约 <500ms 音频已出）才被拦；blocking：**+200–500ms** |
| **触发动作** | `end_call`（默认）/ `retry` | retry **仅 blocking 可用**；最多重试 **3 次**，每次都是"一次完整生成 + 一次护栏评估"，**翻倍计费** |

### 7.3 retry 的反馈文本（可注入系统指令）

支持两个占位符：`{{trigger_reason}}`（自定义护栏取 prompt / 内容护栏取命中的类目）、`{{agent_message}}`（被拦下的那条回复）。

官方给了四个模板，其中一个直接把**工具调用**写进反馈里："…during your next turn you MUST transfer the call to a human operator using the `transfer_to_number` tool."

> 这是它把"护栏"与"转人工"接起来的唯一通道：**不是规则引擎触发转接，而是"告诉模型下次必须转接"**。仍然经过模型。总纲 §8.1-9 记的"失败处置动作枚举"就是这个——四个动作（结束 / 纠正重试 / 转其他 agent / 转人工）都是**通过自然语言反馈驱动**的。

### 7.4 它自己承认的边界

- streaming 模式下**语音可能已播出约 500ms** 才被拦——即"拦得住后半句，拦不住前半句"。
- blocking + retry 在语音上"**表现不够可预测**"，官方建议先用 `end_call`。
- 护栏**不校验工具参数**（只校验回复文本）。
- 触发后"终端用户体验是被挂断/会话结束"，**违规细节不对终端用户展示**。
- **没有申诉流程**，用户只能重新发起会话。

## 8. 监控告警：六个 monitor

| 告警 | 触发条件 | 粒度 |
|---|---|---|
| 会话失败 | 错误占比超阈值 | 会话 |
| 工具失败 | 错误占比超阈值 | **按工具分别跟踪** |
| Webhook 错误 | 错误占比超阈值 | webhook |
| 护栏触发 | 触发占比超阈值 | 会话 |
| 呼叫发起错误 | 错误占比超阈值 | 呼叫 |
| **评估成功分下降** | 平均成功分**低于**阈值 | 评估 |

- 状态三值：`Active` / `Resolved`（不活跃一段时间后**自动解除**）/ `Dismissed`（人工）。
- 阈值可**工作区级设、agent 级覆盖**；未设回落上级，再回落系统默认；范围 0–100%。
- 每个 monitor 可单独启停，并可设"不活跃多少分钟后自动解除"。
- 通知：workspace webhook / Slack / PagerDuty，**每层最多 10 个**；有"发送测试"。事件类型 `convai_alerting_notification`，`event.name` 为 `triggered` / `auto_resolved` / `resolved`。
- 告警历史**保留 90 天**；活跃告警以高优卡片出现在 Spotlight。

> 六个 monitor 里最值得记的是第 6 个：**"评估分下滑"本身就是一条告警**。它把"质量"接进了运维告警，而不是只放在报表里——这是"质量可运维"的最小实现。

## 9. 看板：三处，各管一段

| 位置 | 内容 | 性质 |
|---|---|---|
| **Spotlight**（agent 概览） | 实时/近实时活动、情感分布、主题发现、告警卡片 | 概览 |
| **Analytics**（跨 agent/分支/时段） | 通过率随时间、**最差用例排行**（可按 Test / Branch 分组） | 趋势 |
| **Workflow 图** | 每节点进入次数、平均停留、终止次数、边流量分布；可按 `Node entered` 跳会话 | 结构 |

- **Topic discovery**：把完成会话自动聚成主题，给每个主题的**量 / 情感 / 成功率**，可下钻到具体会话，支持 1 / 7 / 30 天窗口。
- **Sentiment analysis**：正 / 中 / 负三分类，agent 级设置。
- **Smart search**：在历史会话里搜"用户怎么表达某诉求"——官方在写触发器时直接推荐用它找真实措辞。
