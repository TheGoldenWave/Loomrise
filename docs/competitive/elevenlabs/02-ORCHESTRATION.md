## 1. 一句话

它提供**三种编排形态**，并且明确承认它们是一根轴上的三档（不是三个功能）：**系统提示**（全靠模型）→ **Procedures**（一段一段的指令，两种写法）→ **Workflow**（你自己画的图）。三者可以叠加，叠加规则只有一条硬的：**有 Workflow 时，Procedures 从每个节点都可见，不能限定到某节点**。

---

## 2. 三档的取舍（官方给的判据表，可直接用）

| 需求 | 用什么 | 代价 |
|---|---|---|
| 概念验证 | 只用系统提示 | 最快，但单一提示随范围膨胀会失控 |
| 任务允许模型自行调整措辞与顺序 | **自由式 Procedure** | 整段对话在一个上下文里，能跟上意外转折；**吃上下文窗口** |
| 步骤必须每次都一样 | **结构化 Procedure** | 每步按序执行、写法短；表达能力弱于图 |
| 要完全控制复杂分支与边界情形 | **Workflow** | 你自己画图、自己连边，可控但成本最高 |

官方给的默认建议（原句语义）：**自由式 Procedure 是默认选择**——写得最快、读起来像文档、非技术团队能自己维护、跑偏时能自愈。**只有在"跳过或乱序的代价很高"时才上结构化**（身份核验、升级、金钱交易）。

> 这条默认值是它和我们最大的分歧点之一：它把"稳妥"放在**例外**位置，把"能自愈的自然语言"放在默认位置。我们的场景（客服/销售，有可验收终态）恰好是"跳过一步就有代价"的那一侧。

## 3. Procedure：一个独立对象

### 3.1 对象形状

| 字段 | 必填 | 说明 |
|---|---|---|
| `name` | — | **只用于后台显示，从不送进 LLM** |
| `trigger` | 入口流程必填 | 自然语言"何时用我"；**只有 trigger 文本会进上下文，name 与 ID 不进** |
| `content` | 必填 | 自由式＝Markdown；结构化＝JSON 编码的 `steps` 文档 |
| `type` | — | `free_form` / `deterministic`（界面叫 structured）；**创建后不可改** |

**ID 形态**：`agtprc_*`。**作用域**：属于单个 agent，不能跨 agent 共享，不能存为工作区级资源。**复制 agent 时流程被复制而不是共享**，副本拿到新 ID，因此副本内的引用必须改用新 ID。

### 3.2 内联引用（它最有用的一个机制）

自由式流程的 trigger 与 content 里可以内联引用资源，写法是标签：

```text
[tool id="tool_abc123"]
[kb id="kb_abc123"]
[procedure id="agtprc_abc123"]
[system_tool id="end_call"]
{{customer_id}}
```

- 引用会**自动把资源挂到该流程上**（不必先挂到 agent）；纯文字提及只在资源已挂到 agent 时才有效。
- **trigger 里的引用可以按资源输出触发**——原句举例："When `get_user` returns tier 'gold'"。
- 引用资源被删除或失去权限时，标签变"断链"，编辑器顶部 `Errors` 徽标区分为 **invalid**（资源不存在）与 **unavailable**（存在但无权限），并定位到具体步骤。

> 这就是总纲 §8.1-11 说的"流程作为独立对象 + 双向引用"的具体形态。**断链被分成两种**（不存在 / 没权限）这个细节值得抄——我们现在的引用校验只会说"引用无效"。

### 3.3 从 SOP 导入

`+ → From SOP` 上传 `PDF / DOCX / TXT / MD / HTML / EPUB`（≤20 MB），解析器识别**最多 10 条**流程并各生成一个草稿（含生成的 name / trigger / content）。超过 10 条要拆文件。

> 这是我们"资料 → 可交付物"链路上最直接可对标的一个功能：**它把"客户已有的 SOP 文档"当作初始化输入**，而不是让客户从空白开始配。我们 `INTAKE-AND-INITIALIZATION` 的"资料入库"目前停在"存进知识库"，没有"转成流程草稿"这一步。

## 4. 结构化 Procedure：8 种步骤类型（全量）

| 步骤 | API `type` | 必填 | 运行时语义 |
|---|---|---|---|
| **Ask** | `ask` | `instruction` | **唯一会暂停等用户的步骤**；一直问到拿到合适回答 |
| **Tell** | `tell` | `instruction` | 用自己的话讲一件事，**不等回答**，继续下一步 |
| **Say** | `say` | `message`；可选 `message_translations`（按语言码给 `{value}`） | **逐字**说，可逐语言配译文 |
| **Tool** | `tool_call` | `tool_id`、`tool_name`；可选 `instruction`、`schema_overrides`、`on_failure` | 调指定工具；**只有成功/失败两态** |
| **If** | `branch` | `branches[]`（每个含 `condition` + 非空 `steps`）；可选 `fallback` | 按序求值，第一个命中执行；都不中走 `fallback`，无 `fallback` 则**落到 If 之后**（不算错误） |
| **Sub-procedure** | `sub_procedure` | `procedure_id` | 调另一条**同 agent 的**结构化流程；完成后**回到调用者的下一步** |
| **System tool** | `system_tool` | `system_tool_name` | 目前**只有 `end_call`** |
| **Retry** | `retry` | 可选 `max_retries` 1–3，默认 1 | 只在 `on_failure` 内合法，**必须是失败处理器的最后一步** |

### 4.1 嵌套规则（硬约束）

- `If` 以内：可用任意步骤**除 If 与 Retry**。
- `on_failure` 以内：可用 Ask / Tell / Say / Sub-procedure / System tool / **Retry**；**不可用 Tool 与 If**。
- **两个 If 不能相邻**；**If 不能嵌套**；**含表达式的 If 不能紧跟在 Ask 之后**。
- 同一 If 内所有分支**必须同一条件类型**（全 `llm` 或全 `expression`）。
- `end_call` 必须是其所在序列/分支/处理器里的最后一步。

> "两个 If 不能相邻"这条看似古怪，但官方给了原因与解法：有人为了绕过它**在两个 If 之间插一句无关的 Tell**，结果模型开始说它不该说的话。官方明确反对这种"padding"，建议**合并成 else-if 分支**或**挪进子流程**。→ 一个校验规则逼出了坏设计，它自己也承认了。这是我们设计"条件链"时该避的坑：**别用硬约束逼用户拼凑顺序**。

### 4.2 `schema_overrides`：固定工具参数（四类来源）

| `source` | 附带字段 | 行为 |
|---|---|---|
| `constant` | `constant_value` | 永远发这个值 |
| `dynamic_variable` | `dynamic_variable` | 发该变量当前值 |
| `llm` | `prompt`（可选） | 让模型选，可覆盖提示 |
| `omit` | — | 不传该参数 |

键是**工具 schema 里的参数路径**，例如 `request_body.status`。被覆盖的参数**模型看不见也不会去选**。

官方对比写得很直白：*"always set status to pending" 是**请求模型配合**；`constant` 覆盖是**强制且无法跳过**。* → 这就是"提示 vs 契约"的分界线，在同一产品里被并列呈现。

### 4.3 失败处理与 Retry

- **没有 `on_failure` 时，工具失败＝结束对话**（不是"跳过"、不是"告诉用户出错了"）。
- 有 `on_failure`：跑 `fallback` 里的步骤，然后**继续 Tool 之后的下一步**。
- `Retry` 重跑**整个失败处理器（含工具调用）**，每次失败再跑一遍处理器全部步骤；次数用尽**结束对话**。
- `on_failure.branches` 字段存在但官方明说 **"Reserved… Leave it empty"**——即"按失败类型分支"**还没做**。

> 这条对我们很关键：它的工具失败语义是**"要么继续、要么挂断"**，没有"降级为人工/降级为只读"的中间态。我们的 `reconciling`（副作用未知）状态在它这里没有对应物——它连"副作用是否发生"都不区分。

### 4.4 校验规则（10 条，全部在发布/保存草稿时跑）

1. 两个 If 不能相邻
2. If 不能嵌套
3. 含表达式的 If 不能紧跟 Ask
4. 同一 If 内条件类型必须一致
5. Retry 只能在 `on_failure` 内且必须是最后一步
6. `end_call` 必须是所在列表的最后一步
7. `on_failure.fallback` 至少一步
8. Sub-procedure 必须指向同 agent 存在的结构化流程，且不能指向自己
9. `tool_id` 必须是该 agent 的工具、`tool_name` 必须匹配、`schema_overrides` 必须匹配工具 schema
10. `steps`、每个 `instruction`、每个 `message` 都非空

**错误形态**（值得抄）：返回 `400` + `status: "procedure_validation_failed"`，`errors` **按 procedure ID 分组**，每条含 `path` 与 `message`：

```json
{"detail":{"status":"procedure_validation_failed","data":{"errors":{
  "agtprc_6qb...": [{"path":"steps[0].ask.instruction",
                     "message":"Step 1: Ask step requires an instruction"}]}}}}
```

后台同时三重反馈：**Publish 按钮变错误态** + **Procedures 页签出现红点** + **预览无法启动**。

## 5. 运行时语义（六条，官方逐条写明）

| # | 规则 | 含义 |
|---|---|---|
| 1 | **只有 Ask 等用户** | 其余步骤同轮内立即执行并推进；没有"结束本轮"的步骤 |
| 2 | **走到流程末尾不结束本轮** | 回合仍开着，模型可以继续说 |
| 3 | **Tool 步只分成功/失败** | **不能按状态码或响应体分支** |
| 4 | **If 无命中则穿透** | 落到 If 之后，不算错误 |
| 5 | **If 分支不携带状态** | 分支内学到的东西后续步骤不记得，要显式存进工具或动态变量 |
| 6 | **Ask / Tell / Say 不能调工具** | 只有 Tool 步能调 |

> 第 2 条与第 5 条合起来产生一个真实困境：**流程结束不结束回合**，但**分支不携带状态**——所以一个流程跑完了，模型仍然"有权继续说"，而它对刚才在分支里判断过什么一无所知。官方给的唯一解法是"显式持久化"，也就是把流程状态外化成变量。这是它把"流程"与"状态"分开的代价。

## 6. 已知限制（官方自陈）

- 单条流程内容 **≤ 50,000 字符**。
- **只保留最近开始的 5 条流程**在上下文里；超出后，最老的自由式流程的**内容、内联工具、知识库文档一起掉出提示**。
- **不能改类型**；不能跨 agent 共享；复制 agent 后引用要重指。
- **结构化流程不能引用知识库文档**（自由式可以）。
- **无法从指定 workflow 节点启动一条结构化流程**。
- **进入流程有额外延迟**：会先发一次工具调用进入，再沿生成的图走。
- **进入/完成子流程依赖强制工具选择**：主要 OpenAI / Anthropic / Gemini / Grok 家族支持，其他模型或自定义 provider 不保证，可能导致子流程切换与完成不可靠。

> 最后一条是它最诚实的一处：**它的"确定性编排"底下压着一次模型工具调用**。所以"结构化"不等于"确定性"——**进入流程这件事本身是概率的**。这解释了为什么它必须有 `Retry`：不是业务重试，是工程重试。

## 7. Workflow：图

### 7.1 节点类型（API 枚举 + 界面可见）

| 节点 | `type` | 要点 |
|---|---|---|
| Start | `start` | 只有 `edge_order`；检查器里写着"要禁用工作流就断开 start 节点" |
| 子 agent（覆盖） | `override_agent` | `label`、`additional_prompt`、`additional_tool_ids`、`additional_knowledge_base`、`conversation_config`（覆盖）、`entry_behavior`（默认 `auto`） |
| 子 agent（独立） | `standalone_agent` | 不带上级配置，独立执行 |
| Say | —（界面） | **Literal**（逐字，可逐语言译文）/ **Prompt**（按描述生成）两模式 |
| 派发工具 | —（界面） | **保证工具被调用**；有 success / failure 两条专有出边 |
| 更新状态 | —（界面） | 经过即赋值动态变量；与 `update_state` 工具的区别是**不必模型决定** |
| agent 转移 | —（界面） | 转到另一个 agent，可指定目标节点、是否带音色、是否带 TTS 覆盖 |
| 转电话号码 | —（界面） | `transfer_type` 默认 `conference`；`post_dial_digits`（仅 Twilio）；`sip_refer_play_dialtone`；`uui`（RFC 7433） |
| End | `end` | **`outcome` 枚举 `success` / `failure`，默认 `success`** |

> `end.outcome` 是个小而重要的字段：**"这通对话算成功还是失败"在图的终点被显式赋值**。我们目前把"终态"放在业务应用侧的事项状态里（五值投影），没有在编排层直接标注成败——两种做法各有代价，但它的做法让"成功率"可以在平台内直接聚合。

### 7.2 边：四种条件 × 两个方向 × 有顺序

| `type` | 界面名 | 判定性质 |
|---|---|---|
| `unconditional` | None | 确定性 |
| `llm` | LLM Condition | **概率性**（`label` 不送模型） |
| `expression` | Expression | 确定性（**除非** AST 内含 `llm` 节点） |
| `result` | 工具节点专有 | 确定性（`successful: true/false`） |

- **每条边两套条件**：`forward_condition` 与 `backward_condition`。界面是两个页签，回退页签打开时标题反向显示。默认 `None`。
- **顺序即优先级**：`edge_order` 是列表，界面可拖拽，**靠上的先判**。原句："Edges higher in the list will be evaluated first."

### 7.3 表达式 AST

操作数：`String` / `Number` / `True` / `False` / `Null` / `Dynamic Variable` / **`LLM Evaluation`**。
运算符三组：比较（6 个）· 逻辑（`And` / `Or` / `Conditional` 三元）· 算术。

```json
{"type":"or_operator","children":[
  {"type":"dynamic_variable","name":"force_phone_transfer"},
  {"type":"llm","prompt":"Phone condition","value_schema":{"type":"boolean"}},
  {"type":"eq_operator",
   "left":{"type":"dynamic_variable","name":"mode"},
   "right":{"type":"string_literal","value":"dev"}}]}
```

**结构上可辨**：一条边里哪些叶子是概率的（`type:"llm"`）、哪些是确定的，看 AST 就知道。这是全篇最值得借的单点（总纲 §13.4）。**注意它没有 `not` 运算符**——否定只能靠 `not_equals` 或三元绕。

### 7.4 图上的运行数据

Workflow 页签在流程上线后会**把使用数据叠在图上**：每节点进入次数、平均停留时长、终止次数、每条入边/出边的流量分布；节点检查器可直接跳到对话历史（**按 "Node entered" 过滤**）。

> 这是"运行可观测"的最低成本形态：**不建新看板，把数据贴回用户已经在看的那张图**。我们的配置域目前没有等价物，运行数据全在另一个域。

### 7.5 已知缺陷（实测，B+）

- 结构校验实时且阻断（Preview 灰、Publish 变红 Error），**错误态持久化**，刷新后 Undo/Redo 全失效。
- **错误态的边可能打不开检查器**（连续两次鼠标事件超时），修复过程中画布一度整块不渲染（节点从 DOM 消失）。
- **草稿 autosave，但"保存 ≠ 合法"**：错误数据可以留在草稿里。
- `prevent_subagent_loops` 默认 **false**。

## 8. 编译关系（三者不是并列功能）

```
结构化 Procedure  ──编译──▶  workflow.nodes + workflow.edges  ──▶  版本快照
        （编辑态）                  （执行态，Workflow 页签只读可见）
```

- 编译发生在**保存 agent 草稿**或**发布 agent** 时；作者从不手动编译。
- 两个动作都会**校验全部结构化流程**，失败则整体不写入（`400`，按流程 ID 报错）。
- 编译产物在 Workflow 页签**以只读节点呈现**。

> 所以"Procedures"与"Workflow"不是两个功能，是**同一层的两种写法**：轻的写成步骤列表，重的画成图，最后都变成同一份图数据。这解决了"两种编排形态如何共存"的问题——**共存于同一个编译目标**。

## 9. 一步到位的选型建议（我们的场景）

按我们的三个准入（可验收终态 / 资料可授权 / 约束可裁决）反推，它这套的适配情况：

| 我们的需求 | 它这套能否直接满足 | 缺口 |
|---|---|---|
| 步骤必须可复现 | 结构化流程能，但**进入流程靠一次模型工具调用** | 入口不确定性 |
| 条件只能引用已声明字段 | `Expression` 构造器完全支持 | **默认不是它**，要自己把默认反过来 |
| 规则在模型外执行 | `schema_overrides` 的 `constant`、`end.outcome`、`result` 边做到了 | 护栏与失败分支仍是概率 |
| 流程要能被判据引用 | 流程有 ID，但**判据只能按自然语言写** | 判据侧无引用 |
| 图执行必须防环 | 默认不防 | 要反过来 |

## 11. 配置单元：它以什么为单位

前面各节讲"有什么"，本节讲"按什么装"。**它有两套单元，中间隔一次编译**——不把这两套分开，后面所有判断都会错。

| 层 | 单元 | 数量级 | 谁可编辑 |
|---|---|---|---|
| **编辑态** | Procedure 的**步骤**（8 种类型） | 每条流程几步到几十步 | 人（Procedures 页） |
| **执行态** | **节点**（node） | 每个 agent 十几到几十个 | **只读**（Workflow 页签） |
| 执行态子单元 | **出边**（按 `edge_order` 排序） | 每节点 1–5 条 | 只读 |
| 执行态子单元 | **边条件**（forward / backward 各一个） | 每条边 0–2 个 | 只读 |
| 执行态子单元 | **覆盖字段**（提示 / 工具 / 知识 / 模型 / 音色 / 话轮参数） | 每节点 0–7 项 | 只读 |

### 11.1 真正的配置单元是"阶段"，不是"意图"也不是"句子"

一个节点承载的不是"一句话"，也不是"一个任务"，而是**一次接管**：从这一刻起，换成这套提示、这批工具、这份知识、这个模型、这个音色说话，直到某条出边被满足。

所以它的配置本质是一句话：**在什么时刻换谁来说**。

- 不是"逐句编排"（那是脚本），
- 也不是"只配目标"（那是纯提示），
- 而是**在两者之间选了"阶段"这个粒度**——够粗，人还能画得下；够细，能换工具和知识。

选这个粒度的直接后果：**节点内的措辞自由度交给模型，节点间的切换交给结构**。这条分工是它能同时做到"自然"与"可控"的原因。

### 11.2 九处设计巧思

| # | 巧思 | 为什么算巧 |
|---|---|---|
| 1 | **覆盖式继承**：新节点默认全继承上层，只声明差异；未覆盖字段界面标 `Using default` | 配置量随节点数**线性**增长而非乘法；且"这个值是本地定的还是继承的"变成**可见事实**，不靠记忆 |
| 2 | **增量与覆盖分两套字段**（`additional_prompt` / `additional_tool_ids` / `additional_knowledge_base` vs `conversation_config`） | 同一检查器里两种语义，精确但必须读文档。**精确 > 好猜**，尤其当覆盖会整段替换提示时 |
| 3 | **概率判定降级为表达式叶子**（`type:"llm"`） | 一条规则里确定与概率共存，且**哪部分是概率的一眼可辨**。它没把"谁判"做成二选一 |
| 4 | **顺序即优先级**（`edge_order` 列表，可拖拽，靠上先判） | 不需要独立的 `priority` 字段，"先判什么"就是列表顺序——**少一个字段，多一个能被看见的顺序** |
| 5 | **回退是一等边**（`backward_condition`） | 用户改主意不必造"重试节点"或 goto；回退与前进共用同一套条件语言 |
| 6 | **编辑态靠编译连到执行态** | 轻的写步骤、重的画图，最后是同一份数据。绕开了"两种编排形态如何共存"这个难题 |
| 7 | **拓扑关停**（断开 start 即停用） | 少一个"启用"状态位，就少一种"开关忘了关"的事故 |
| 8 | **配置对象＝观测对象**（图上线后叠每节点进入数、停留时长、终止数、边流量） | 不建第二块看板，把数据贴回用户已经在看的那张图 |
| 9 | **终点显式成败**（`end.outcome` = `success` / `failure`） | 让"这通算不算成功"在编排层就有答案，成功率可以在平台内直接聚合，不必等分析管道 |

另有两条不算"巧"但值得记：**Say（逐字）与 Tell（自述）分工**，把"必须一字不差"（法律披露、确认复述）与"可以自由表达"分成两种步骤；**派发工具节点**把"必须调用"从提示里的请求变成结构上的保证。

## 12. 相对我方配置能力的八条缺点

前提：比较对象是 Loomrise 的**事项状态机 + `RunEvent` + 验收判据 + 段落级 `locked`/`mutable`**，不是"谁的图更好画"。以下八条按严重度排序。

### 12.1 没有"状态"这个一等公民（最严重）

- **分支不携带状态**：官方明写"If arms do not carry state forward"——分支里判断过什么，后续步骤不记得，要显式存进工具或动态变量。
- **节点之间没有字段契约**：唯一的跨节点载体是 `dynamic_variables`，一个**无 schema 的键值袋**；谁都能写（工具、`update_state`、节点、**客户端在会话发起时注入**）。
- **没有"这一步必须产出哪些字段"的声明**，也没有校验"下一个节点依赖的字段是否真的会被赋值"。

→ 它的图是**无状态流程图**，状态被压进一个共享 KV。这在小流程里是省事，在长流程里就是"谁都能改全局变量，没人能证明它被改过"。

我方对应物：事项（`TaskItem`）有状态机、有终态投影（五值）、`RunEvent` 是唯一事实流。**状态有契约、有归属、有投影**——这是结构差异，不是功能差异。

### 12.2 只有进入条件，没有完成条件

边只回答"何时走"，不回答"这个阶段算不算完成"。整张图里唯一一次成败判定在 `end.outcome`（默认还是 `success`）。

→ 后果：中间任何一步"做完了但做错了"无法在图内表达，只能等整通结束再判。**图的语义是"走完了"，不是"做对了"。**

我方对应物：每个事项有终态与验收判据，评测可以在中途判。

### 12.3 没有"等外部"的原语

`execution_mode: async` 只是"不阻塞对话"，不是"等一件事做完再继续"。没有委派节点、没有等待回执、没有"超时后走另一条边"。

→ 客服/销售里最常见的形态（提交工单、等审批、等回执、等物流）在这张图上**没有位置**，只能靠工具自己阻塞或靠模型反复追问。

### 12.4 工具失败只有两态

成功 → 继续；失败 → 走 `on_failure` 或**直接结束对话**。没有"副作用已发生但结果未知"。

→ 我们必须要 `reconciling`（副作用未知 → 事项进对账态）。它连这个概念都没有，所以它的失败处理只能"重试"或"挂断"。

### 12.5 校验只到"结构合法"，不到"语义可达"

它校验的是：字段非空、If 不嵌套、两 If 不相邻、`end_call` 在末尾、Sub-procedure 不自指、`tool_id` 匹配 schema——**全是结构**。

它**不校验**：节点是否可达、是否有死路、条件是否互斥/穷尽、**表达式引用的变量是否真的会被赋值**（引用一个永远为 `null` 的 `dynamic_variable` 完全合法）、环（`prevent_subagent_loops` **默认 false**）。

→ 我们"条件只能引用已声明字段"天然排掉最后一类；但"可达性/穷尽性"我们也没有，见 §12.8。

### 12.6 复杂度被模型吸收，而不是被结构吸收

节点越多，每条出边都要模型判断"该走哪条"。官方自己的建议就是"**用能力更强的模型，流程多了才更可靠**"。

→ 这等于承认：**它把编排复杂度转嫁给了模型**。我们的做法相反——确定性规则在模型外裁决，模型只承担被判定的部分。

### 12.7 编辑回路断裂：编译是单向的

步骤 → 编译 → 图，**产物只读**。作者在 Workflow 页签看到的节点改不了；要改必须回 Procedures 页找那条流程。

→ 同一份东西两处呈现、只有一处可改。这不是 bug，是"两种表达共用一个编译目标"的必然代价，但它把"看"和"改"分到了两个地方。

我方对应物：概览与详细配置是**同一对象的两个投影**，任一处改都写回同一草稿。

### 12.8 没有节点级版本，也没有图上的断言点

- **版本粒度是整棵树**：改一个节点 = 新版本；`preview_merge` 能给出字段级 `overridden_fields`，但没有"这个节点这一版变了什么"。
- **测试断不到路径**：三类测试只能整通模拟、判下一句、或断言工具调用；**不能断言"走到了第 3 个节点"**。`Node entered` 是**观测过滤器**，不是判据。

→ 后果：流程改动只能靠"整通通过率"来验证，改坏了要等失败分桶浮出来。

### 12.9 两条不是缺点（避免误伤）

1. **`label` 必填但只给人看**：看着像形式主义，实际是"强制人给节点起有意义的名字"，对协作有用；只是说明**"意图"在它那里不是可计算对象**。
2. **无状态图对短流程更轻**：3–5 个节点的分流场景，状态机是过度设计。它的取舍在短流程里是对的。

### 12.10 如果我们要做图，必须补的四条

由上面 12.1–12.8 反推，且**不推翻"单 Agent 为主、图是例外"的既有结论**——只是在"万一要画图"时，这四条不能省：

| # | 必须补 | 因为 |
|---|---|---|
| 1 | **节点级状态契约**：每个节点声明"读哪些字段、写哪些字段"，保存前校验写入字段确实会被赋值 | 否则状态退化成无 schema 的 KV（12.1、12.5） |
| 2 | **完成条件与进入条件成对**：每个节点既有"何时进"，也有"怎样算完成" | 否则图只能判"走完了"（12.2） |
| 3 | **"等外部"作为一等节点**（委派 / 等待回执 / 超时分支） | 否则客服里最常见的形态无处安放（12.3） |
| 4 | **路径级断言**：测试可断言事件序列/节点路径，不只断言最终结果 | 否则流程改动只能靠整通通过率（12.8） |

前两条可直接进 `HARD-RULE-MODEL` 的"条件引用已声明字段"同一节——它们是同一条原则在图上的延伸：**能被引用的，必须先被声明**。
