# Loomrise 六层配置合同 v0.6

状态：公开设计，2026-10-16。S1 已实现单场景被动响应的最小合同和审计事件，完整六层配置与后续治理仍为规划。本次补充专家内任务蓝图和工具/Schema 渐进披露的目标合同，未修改代码。新增网页客服与自有云交付遵循相同六层，范围和 Gate 见[建设方案](CUSTOMER-SERVICE-DELIVERY-PLAN.md)；适配器、模型、渠道和部署供应商不能改变这些职责边界。

## 1. 设计目标

Loomrise 把一个业务 Agent 拆成六层可版本化配置：`ContextSnapshot`、`RequestRouting`、`Skill/SOP`、`HardRule`、`ToolPolicy`、`Outcome`。

六层不是六段 Prompt，也不是六个必须独立部署的服务。它们分别回答：当前知道什么、正在做什么、应该怎样做、绝不能怎样做、可以调用什么、业务上最终发生了什么。

渐进式上下文加载是横切执行机制，不是第七层。它决定当前轮次把哪些已授权事实、Skill 片段、规则摘要和工具结果提供给模型；它不能改变模型外的权限、确认和结果裁决。

后续将同一原则扩展至任务工作集、能力摘要和 Tool Schema：少量稳定语义入口，先摘要、再任务局部、最后按需证据；不是把所有能力隐藏到一个万能调用器。可见不等于获准执行，工具与结果权限始终模型外重验。

## 2. 六层职责

| 层 | 回答的问题 | 权威内容 | 不负责什么 | S1 形态 |
|---|---|---|---|---|
| `ContextSnapshot` | 当前已知事实是什么，来自哪里，是否仍有效？ | 带来源、时间、有效期和敏感级别的事实快照 | 不把模型猜测升级为事实；不自动等同于长期记忆 | 虚构课程资料、用户已提供字段、当前任务摘要 |
| `RequestRouting` | 当前消息对应哪个业务请求，下一步只做什么？ | 主请求、路由理由、任务代次和下一步候选 | 不授予工具权限；不同时推进多个互斥主请求 | 固定课程咨询或模拟预约任务 |
| `Skill/SOP` | 在当前任务中应采用什么处理策略？ | 适用条件、目标、步骤、退出/转人工条件、引用的知识和工具 | 不决定权限、价格、确认和业务终态 | 一个命中的课程咨询 Skill |
| `HardRule` | 哪些动作必须拒绝、确认、停止或去重？ | 全局/任务/Skill 作用域的禁止、必须、停止和去重规则 | 不承载所有 badcase；不依赖模型分数放行高风险动作 | 少量模型外规则，按稳定 ID 记录 |
| `ToolPolicy` | 什么情况下可以调用哪个工具，如何确认结果？ | 输入/输出约束、权限、确认、预算、超时、幂等和结果证据要求 | 不把供应商私有状态当 Loomrise 业务状态 | 一个模拟预约写入工具 |
| `Outcome` | 业务请求实际处于什么状态，产生了什么结果？ | 按任务类型预先定义的结果、持久副作用及适用的外部结果 ID、失败/未知原因 | 不接受模型口头“已完成”作为证据；不把已回复等同于问题已解决 | 模拟预约结果、无副作用咨询的执行终态或明确失败；完整客服结果证据待补齐 |

受授权资料约束的 FAQ 属于可验收客服任务：核验事实、资料引用和服务范围，无依据时澄清或升级；无需每次答疑创建工单。后续应分别保存答复生成、消息送达/播放、解决确认或未知和人工承接事实。客服会话可包含多个业务请求，会话占用与 `ServiceRequest` 终态分别管理；Widget、Inbox 或云部署均不新增第七个业务配置层。

### 语音交互行为的归属（2026-10-21 定，目标规范）

语音行为**不新增第七层**。按"能不能改、谁改、怎么生效"分四档，`AgentSpec` 只承载 ②b 与 ③：

| 档 | 内容 | 谁能改 | 生效方式 | 为什么这么分 |
|---|---|---|---|---|
| **① 平台契约** | 话轮与打断判定、取消确认、权限流转、"不得声称已完成"、失效结果不播报 | 平台代码 + 边界测试，**业务方不可改** | 随平台版本 | 这些是正确性问题：一旦可编辑，既无法验收也无法归因 |
| **②a 工程参数** | 播报静默窗、失败重试间隔、打断判定窗、首响预算 | **产研**（部署/环境配置） | 即时生效，**不进 `AgentVersion`** | 属链路节奏，与模型、网络、设备相关；业务方无判断依据，进版本会逼成"调参即发版" |
| **②b 体验开关** | 致谢开关（动手前是否说"我查一下"）、进度播报开关与间隔档、通知策略（这条结果说/不说）、静默策略 | **策略运营**（与 ③ 同权限） | 随 `AgentVersion` 冻结，走草稿 → 评测 → 发布 | 业务情境强（销售与客服对"要不要主动汇报进度"要求不同），但可登记、可评测、有默认值 |
| **③ 业务内容** | 人设、语气、话术、知识、SOP | 搭建者 / 策略运营 | 既有内容层规则（含 `locked` / `mutable` 段落） | 本来就是内容层，不因语音改变 |

**②a 的纪律（关键，否则评测不可复现）**：工程参数不随 `AgentVersion` 冻结，但必须

1. **版本化留痕**：每次变更记录变更人、旧值/新值、时间与理由；
2. **进评测冻结四元组**：评测报告固定记录当次参数快照（与模型、解码配置、资料与工具版本同列），参数变了必须重跑基线，不得跨参数比通过率；
3. **同值纪律**：评测环境与生产环境同一参数值，不允许"评测用一套、生产用另一套"。

取舍说明：让 ②a 随版本冻结会更严格，但会把日常调参拖进发布流程；用"留痕 + 快照进报告"换取调参效率，是把可复现性交给证据而不是交给流程。反过来，②b 变了会改业务呈现，所以必须随版本冻结、必须评测。

### 物料检索与文件发送（目标规范，未加入 S1）

独立物料库不新增第七层。物料资产保存原件/派生、授权与有效期，业务审阅后的简介和标签作为 `ContextSnapshot` 按需选择依据，不自动变成业务答疑事实；`RequestRouting` 保留主请求、会话占用与代次关联，`Skill/SOP` 定义适用场景，`HardRule/ToolPolicy` 在执行前重验权限、批准策略、请求条件、数量/渠道限制、物料与派生版本及当前人工/AI 占用。Agent 自动发送默认关闭，人工可独立选择物料发送。

`Outcome/RunEvent` 分别关联发送尝试、文件/简介快照、渠道回执和实际业务结果。压缩成功、简介已审或检索命中均不证明发送完成；消息记录、送达与问题解决分别记账。撤回/过期/改版/占用代次变化使旧选择失效，异步读取后须再次检查。正式合同和后端 Gate 见[物料库与文件发送](MATERIAL-LIBRARY-AND-DELIVERY.md)，现有本地前端仿真不证明真实执行。

## 3. 执行顺序

```text
入站消息/语音轮次
        │
        ▼
ContextSnapshot ──► RequestRouting ──► Skill/SOP
        │                              │
        └──────── 有效上下文加载 ◄──────┘
                                       │
                             HardRule 模型外裁决
                                       │
                              模型提出回答/动作建议
                                       │
                             ToolPolicy 再次校验
                                       │
                              工具执行或等待确认
                                       │
                              Outcome 持久化结果
                                       │
                                RunEvent 留证
```

模型可以提出回答、澄清问题和工具调用建议，但不能绕过 `HardRule`、`ToolPolicy` 或 `Outcome`。文字和语音入口只改变输入输出适配，不改变这条执行顺序。

## 4. 共同配置元数据

每层配置至少应具备：

- 稳定 `id` 与不可覆盖的 `version`；
- 适用 `scope`、触发条件和优先级；
- 来源引用、来源版本、有效期和撤销状态；
- 负责人/审批人和关联 `Case`、`RunEvent` 或 `ChangeProposal`；
- 敏感级别、预算影响和兼容性声明。

已发布版本不可原地覆盖。替换知识、Skill、工具合同或规则后，受影响的评测与发布结论必须重新验证。

## 5. 渐进式上下文加载

S1 采用最小三段式：

1. **常驻基线**：身份、输出合同、全局安全/确认要求和当前任务摘要。
2. **任务局部**：路由命中的任务配置和一个适用 `Skill/SOP`。
3. **按需证据**：回答事实、调用工具或解释结果时，才加载相关知识片段、字段说明或工具结果。

上下文片段不必全部进入模型，但每次选择都必须可解释。S1 的上下文事件至少记录：`context_scope`、`activation_reason`、`source_ref`、`source_version`、`token_estimate` 和 `load_status`（`loaded` / `skipped` / `expired` / `budget_capped`）。

`HardRule` 的完整定义始终由模型外执行；模型只接收当前有效约束摘要。新增规则前先判断失败是否来自路由、资料、加载、Skill、工具语义或真正的硬规则违规，避免把所有 badcase 堆进规则和 Prompt。

后续 Harness 披露的工具集合由角色、AgentVersion、当前任务/Skill 与最新授权决定；记录实际可见 Tool ID、版本/Schema 哈希及输入快照，猜中隐藏工具名也不能调用。Adapter 不支持轮内动态工具时固定每次运行最小子集，扩展时新建快照/运行边界。停止/权限等保护项不能因预算被裁剪，缺失时阻断动作。该工具披露合同未实现；当前 S1 仍固定装配业务工具，不能把三段式上下文验证当作工具发现验收。

## 6. S1 最小合同

S1 固定：一个虚构课程场景、一个模型、一个模拟写入工具、文字/网页语音双入口和单次隔离回放。

- `ContextSnapshot`：只读虚构资料、用户已确认字段、当前任务摘要；不实现长期记忆。
- `RequestRouting`：每轮一个主请求，路由理由写入事件。
- `Skill/SOP`：一个或少量可人工审阅的 Skill，不做自动编排。
- `HardRule`：确认前不得写入、权限/字段不完整不得执行、重复请求必须幂等。
- `ToolPolicy`：模拟工具执行前重验权限、确认版本、任务代次和幂等键。
- `Outcome`：模拟写入成功以实际模拟结果和 `result_id` 为证据；纯咨询可无副作用结束执行，但当前 `success` 不证明答复已送达或问题已解决。失败、取消、超时和未知结果分开记录；完整持久化及客服结果合同仍待补齐。

S1 不实现自动 Skill 生成、长期记忆优化、复杂 Meta Skill 编排或根据运行结果自动发布配置。

## 7. 后续 Skill 自进化

自进化的对象优先是可版本化的 `Skill/SOP`、示例、澄清顺序和有限检索参数，不是权限和安全边界。推荐流程如下：

```text
不可变 RunEvent / Case / 用户反馈
              │
              ▼
        Trajectory 归一化
              │
              ▼
   独立诊断：Skill 缺陷 or 执行失误
              │
              ▼
 Candidate Skill / ChangeProposal
              │
              ▼
        沙箱运行与静态检查
              │
              ▼
 开发集 + 验证集 + 保留集 + 回归/成本门禁
              │
              ▼
       策略门禁通过、人工审批后进入 Registry
              │
              ▼
        灰度、回滚、持续记录 Provenance
```

### 7.1 角色分离

候选 Skill 的作者/提议者、执行 Agent 和评估/审计者应逻辑隔离。允许它们使用相同底层模型，但不能让同一轮上下文既提出修改又自行宣布修改有效。

### 7.2 版本和状态

后续 `SkillManifest` 注册表至少区分 `candidate`、`validated`、`approved`、`released`、`rolled_back` 和 `retired`。候选必须记录来源轨迹、父版本、结构化 diff、依赖 Skill、工具/知识版本、评测环境、成本变化和拒绝/回滚原因。

### 7.3 评测门禁

不能只看一次 validation 分数。候选至少需要：

- 固定开发、验证和保留盲测集；
- 同分布回放、分布外/迁移样本和旧案例回归；
- 硬规则、权限、确认、幂等、结果证据等确定性裁决；
- token、工具调用、延迟和失败回退成本；
- 静态检查、沙箱运行、策略门禁、人工审批和可回滚发布。

策略检查只作前置门禁，不能替代人工发布审批。验证集提升不等于自动发布。没有评测门禁的 Skill 自进化，只是自动修改 Prompt。

### 7.4 不可自动修改的边界

自进化流程不得静默修改：`HardRule` 的权限/安全/停止条件、`ToolPolicy` 的授权范围与副作用等级、确认要求、幂等策略、`Outcome` 语义、发布审批权和数据保留策略。这些内容只能形成待审提案。

### 7.5 经验与 Skill 分层

原始轨迹应保持不可变；失败模式、成功策略和被拒绝方案可以进入持久经验/Wiki 层；只有经过评测的候选才进入 Skill Registry。Skill 回滚不应删除经验和决策历史，避免下一轮重复提交已知失败方案。

长程任务进一步扩展时，使用结构化任务状态、状态补丁和运行时校验，减少把完整历史拼接进每轮上下文。该能力不属于 S1。

## 8. 与现有对象的对应

| 目的 | Loomrise 对象 |
|---|---|
| 运行配置 | `AgentSpec` / `AgentVersion` / `SkillManifest` / `ToolManifest` |
| 执行事实 | `ServiceRequest` / `RunEvent` / `Outcome` |
| 失败与真值 | `Case` / `EvalSet` / `EvalResult` |
| 候选变更 | `ChangeProposal` |
| 发布与撤回 | `Release` 及版本状态 |

本文件定义的是职责和边界，不代表这些对象已经有可运行实现。

## 9. 配置 UI 与可选助手（原则已确认，交互提案未实现）

六层是配置职责，不能成为初次用户必须依次填写的六张表。允许完整手动搭建，也允许可关闭的初始化助手在授权资料范围内整理候选；两种方式共用同一 `AgentSpec` 草稿和校验。业务概览、日常编辑和详细视图均可定位六层原项，默认值、有效值、来源、版本、引用与差异按需展开。详细查看不扩大修改权限，助手建议不静默覆盖人工编辑或本文件 §7.4 的边界。规则字段编辑继续依赖既有合同决策。具体建议与验收需求见[配置后台体验优化](CONFIGURATION-UX-OPTIMIZATION.md)。

## 10. Task 与用户上下文（方向已确认，合同提案未实现）

Task 体系跨时间协调运营策略和会话 TODO，持久事项暂称 TaskItem；其业务尝试仍由 RequestRouting/Skill/HardRule/ToolPolicy/Outcome 处理，不增加第七层。专家默认任务及触达约束作为 `AgentSpec.task_blueprints` 随 AgentVersion 冻结，分别落在既有路由/Skill、规则、工具和结果职责中，不设共享策略库或第二套权限。服务周期幂等初始化符合规则的内部事项，触达先候选再采用；版本发布不重建任务或默迁在途义务。

用户上下文模块将受治理记忆、派生画像和相关事项按主体/用途/来源/版本/有效期装配为 ContextSnapshot/evidence，加载、过滤与压缩留证。任务状态查账本、业务事实查结果/来源权威、权限由模型外检查，不能从记忆或摘要推断。系统提供有界工作集，拟用 `inspect_context/manage_tasks` 展开信息或提交受限实例意图；实际业务动作仍走原合同。允许范围内调整只记录 revision；蓝图、权限、承诺和确定性规则变更仍走专家候选版本评测审批。详细职责与前置 Gate 见[Task 设计](TASK-SYSTEM-DESIGN.md)、[用户上下文设计](USER-CONTEXT-DESIGN.md)及[联合计划](TASK-MEMORY-INTEGRATION-PLAN.md)。
