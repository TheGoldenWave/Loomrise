# 04 · 知识与"记忆"

> 证据等级：**B**（叙述文档）+ **A-**（RAG 参数与默认值）+ **B+**（后台三页签实见）
> 语料篇目：`customization/knowledge-base` `knowledge-base/manage-documents` `knowledge-base/rag` `operate/users` `customization/privacy` `personalization/dynamic-variables` `api-reference/agents/create`
> **本卷不出结论**；判断见总纲 §8.2-6/11、§9 EL-12，以及 `EXPERT-USER-MEMORY-SYSTEM.md`（我们不引用它的记忆模型）。

---

## 1. 一句话

它把知识做成**一条管道**（文档 → 索引 → 检索 → 提示），把"记忆"做成**两个半成品**（一个 Alpha 页签 + 一个没有文档的开关）。**没有独立的记忆对象，也没有"候选/裁决"的概念**——这一层是它最空的地方，也正因为空，最不该拿它做参照。

---

## 2. 知识库：一条管道，两个岔路

### 2.1 两种使用方式（`usage_mode`）

| 值 | 行为 |
|---|---|
| `auto`（默认） | 启用 RAG 且文档已索引 → 走检索；否则**全文进提示** |
| `prompt` | **永远全文进提示**（前提是塞得下） |

约束与阈值：

- **全文进提示的上限约 300,000 字符**（提取后文本）；超过必须走 RAG。
- **文件夹只能走 RAG**——挂一个文件夹到 agent，其下全部文档通过检索可用，因此 **agent 必须启用 RAG 才能用文件夹**。
- 同一份文档可挂到多个 agent（共享维护）。

### 2.2 支持的输入

| 来源 | 说明 |
|---|---|
| 文件 | `pdf` / `docx` / `txt` / `md` / `html` / `epub`，**单个 ≤20 MB** |
| URL | 抓单页；或**启动爬取任务**把整站抓成一个文件夹（异步，有 job ID 可查状态/取消）；有**爬虫 user agent** 说明 |
| 纯文本 | 直接写 |

### 2.3 文档维护里三个值得记的行为

1. **编辑即重建**：直接改文档内容会自动重建内容检索分块与 RAG 嵌入，"搜索与检索保持同步"。
2. **URL 文档的 auto-sync 与手工编辑互斥**：auto-sync 关闭时可手工改；**开启时同步周期接管该文档，手工编辑被阻止**。← 避免"改了又被覆盖"的冲突，用**禁止**解决，而不是用"合并"。
3. **删除/替换是唯一的重建方式**（除直接编辑外）；没有"版本"概念——**知识库文档不进版本快照**。

> 第 3 点是它和我们最大的结构差异：它的 `AgentVersion` 冻结"哪些文档被挂载"，但**文档内容本身不冻结**。也就是说，同一个版本号在两次调用之间，检索到的内容可能已经变了。总纲 §8.1-1 记录"版本=不可变快照"时要带上这个例外——**快照的是引用，不是被引用的内容**。

## 3. RAG：参数与配额（A-）

### 3.1 参数

| 字段 | 典型值 | 含义 |
|---|---|---|
| `enabled` | `true` | 开关 |
| `embedding_model` | `e5_mistral_7b_instruct` | 嵌入模型 |
| `max_vector_distance` | `0.6` | 相似度阈值（越小越严） |
| `max_documents_length` | `50000` | 送进提示的文档内容上限 |
| `max_retrieved_rag_chunks_count` | `20` | 单次检索返回块数上限 |

**延迟代价**：官方写"约 **250ms**"。

### 3.2 索引

- 文档加入启用了 RAG 的 agent 时**自动索引**；大文档需要几分钟，状态在知识库列表可见（`SUCCEEDED` / `FAILED`）。
- 也可显式调 `compute_rag_index` 触发并轮询。
- **小于 500 字节的文档无法索引**，系统会自动改为塞进提示。

### 3.3 配额（按订阅档，单位是"原始文件总大小"）

| 档 | 上限 | 备注 |
|---|---|---|
| Free | 1 MB | 不活跃后索引可能被删除 |
| Starter | 2 MB | — |
| Creator | 20 MB | — |
| Pro | 100 MB | — |
| Scale | 500 MB | — |
| Business / Enterprise | 1 GB | 企业可谈更高 |

> 注意口径：限的是**原始文件总大小**，不是索引体积（索引可以大得多）。这是一条容易被误读的条款。

## 4. 检索模式三档（B+，后台 `Retrieval` 页签）

| 档 | 行为 | 与我们的关系 |
|---|---|---|
| `On demand` | 模型决定何时检索 | 可接受 |
| `Every turn` | 每轮都检索 | 可接受（成本换稳） |
| `Prompt only` | **从不检索**，把够小的文档全文塞进提示 | **与 `source_ref` 溯源直接冲突** |

官方口径（卷首引）：`Prompt only` 下知识库**永不被检索**，只把文档全文塞进提示。这意味着**没有任何出处信息**可以回指。

> 总纲 §8.2-11 已定不借这一档。这里补一条事实依据：它的 `source_attribution`（指示模型报告引用了哪些来源）**默认 `false`**——即"引用出处"在它整个产品里是**双重可选**（检索可选、归属可选），不是默认义务。

## 5. "记忆"：两个半成品

### 5.1 知识库里的 `Memory (Alpha)` 页签（B+）

| 属性 | 事实 |
|---|---|
| 作用域 | **agent 级**，不是 user 级 |
| 能力 | 可搜索 |
| 过滤 | **仅按日期** |
| per-user 维度 | **无** |
| 状态 | 标注 Alpha |

### 5.2 per-agent 设置里的 `user memories`

`operate/versioning` 的实例级设置表里，`privacy` 一行写的是：

> Retention settings, zero-retention mode, and **user memories**.

而全语料 **368 篇中"user memor*"只出现这 1 次**——**没有独立文档页，没有字段 schema，没有作用域/生命周期/删除语义**。

> 因此可以做的最小更正：**不能说"它没有任何 per-user 记忆相关设置"**；准确表述是"**存在一个名为 user memories 的 per-agent 设置，但语义未文档化**"（B 级提及 + D 级语义）。这条已回写总纲 §0.4 修订块。

### 5.3 动态变量不是记忆

`dynamic_variables` 是**会话发起时注入的键值**，可被 `update_state` 工具 / `update state` 节点在会话内改写。它的生命周期是**一次会话**，不跨会话累积，不进任何版本。

> 把它当"记忆"是它文档里最容易误导人的一处——因为工具能把结果写进变量、下一轮又能读到，看起来像"记住了"。但它**在会话结束时消失**，且**没有任何写入裁决**。总纲 §8.2-6 已定不借。

### 5.4 三个概念的实际边界

| 概念 | 作用域 | 生命周期 | 谁能写 | 有裁决吗 |
|---|---|---|---|---|
| 知识库文档 | agent（可跨 agent 共享） | 直到被删/替换 | 人（后台/API/爬虫） | 无 |
| `Memory (Alpha)` | agent | 未文档化 | 未文档化 | 无 |
| `user memories` | 未文档化（疑似 user） | 未文档化 | 未文档化 | 无 |
| 动态变量 | 单次会话 | 会话结束即失效 | 工具/节点/发起时注入 | 无 |

**四者都没有"候选 → 校验 → 裁决 → 生效"的环节。** 写进去就等于生效。

## 6. 用户实体：有 `user_id`，但没有用户画像

`operate/users` 页：列出"跟你的 agent 说过话的所有人"。

| 列 | 内容 |
|---|---|
| User ID | **你在发起会话时传的 `user_id`** |
| Last contact | 最后互动时间（可排序） |
| Agent | 涉及的 agent |
| Conversations | 会话总数（可排序） |

- **搜索是精确匹配**（必须输完整 ID，不支持前缀）。
- 可按日期、agent、branch 过滤（branch 过滤需该 agent 启用版本化）。
- 点进去是该用户按时间排列的会话列表。

> 这是"**用户实体**"而不是"**用户记忆**"：它把同一 `user_id` 的历史会话聚在一起供人看，**但没有把任何内容提炼成可供模型使用的事实**。这两件事必须分开说——总纲 §12 曾因混说而误判过一次。

## 7. 与我们四类记忆的对照（只列表，不评判）

| 我们的分类 | 它的对应物 | 结构差异 |
|---|---|---|
| 业务用户记忆（`subject_id`） | `user_id` + 会话聚合；`user memories`（未文档化） | 它只有"归档"，没有"提炼成候选" |
| 专家记忆（`expert_id`，跨版本） | **无** | 版本升级不继承任何东西 |
| 搭建者个人记忆 | **无**（Architect 的 `agents.md` / `user.md` 明写只影响 Architect） | 我们把它排除在运行时外，它也是 |
| 配置与规则（**不是记忆**） | 系统提示 + Procedures + Workflow | 它把"规则"全放在配置里，没有独立的"规则对象"层（流程有 ID，规则没有） |

> 第三行有一个外部佐证值得记：官方明写 `agents.md` / `user.md` **只影响 Architect，不改运行时**——这正是我们"第 ③ 类记忆排除在运行时之外"的同向证据。

## 8. 矛盾与存疑

| # | 项 | 状态 |
|---|---|---|
| 1 | `Memory (Alpha)` 的作用域是 agent 还是 user | B+ 观测为 agent 级 + 仅日期过滤；无文档，D |
| 2 | `user memories` 的语义（存什么、存多久、能不能删） | 全语料 1 次提及，**无文档**，D |
| 3 | 知识库文档**不进版本**，但"挂载关系"进版本 | A-/B 均可证；这构成本卷最重要的一条边界 |
| 4 | `max_documents_length` 与"全文进提示约 30 万字符"是两个不同额度 | 前者是 RAG 送进提示的上限，后者是 `prompt` 模式的容量上限，勿混 |
| 5 | `source_attribution` 默认关 | 与"引用溯源是默认义务"直接相反，须在引用时标明 |
